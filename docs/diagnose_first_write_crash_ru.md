# `diagnose_first_write_crash.py` — лесенка диагностики краша на первой записи (issue #24966)

## Назначение

Воспроизводимая «лесенка» для локализации падения KiCad на первой IPC-записи после старта сессии
(issue #24966). Пошагово выполняет чтения через kipy (connect → ping → version → open_documents →
get_board → чтение футпринтов → повторное чтение), а на последней ступени — **no-op транзакция**
`begin_commit()` → `update_items([fp])` без каких-либо изменений → `push_commit()` — ровно тот путь,
что реально использует `adapter.commit_with_retry()` в бою, а не голый `update_items()`. После каждой
ступени снимает «пульс» (`ping` + сверка списка PID `kicad.exe`), чтобы точно увидеть, на каком шаге и
в какой момент процесс умер. Лог пишется построчно с flush — последняя строка честна, даже если KiCad
умрёт мгновенно.

Полное описание самого бага (#24966), второго связанного бага (#24970) и остального набора инструментов
охоты за крашами — см. [crash_hunting_ru.md](crash_hunting_ru.md). Этот документ — только про сам
диагностический скрипт.

**Важное исправление (2026-07-26):** раньше ступень 9 делала голый `update_items()` без `begin_commit`/
`push_commit` и проходила чисто там, где реальный `apply` живьём падал на Linux/KiCad 10.0.5 — ровно на
`begin_commit()` для первой транзакции сессии (флипы до этого используют отдельный API-путь,
`run_action("...InteractiveEdit.flip")`, минуя commit — они не «лечат» уязвимое состояние). Теперь
ступень 9 честно оборачивает no-op запись в такую же транзакцию, как в бою, с логом каждого под-вызова
отдельно.

## Три гипотезы

Различает три гипотезы: **H1** — гонка первой записи с ленивой инициализацией (чтения переживаются,
умирает только запись; лечится/сдвигается `--delay`); **H2** — зомби-инстанс от прошлой сессии (в
снапшоте окружения видно больше одного `kicad.exe` или торчат старые `KICAD_API_SOCKET`/
`KICAD_API_TOKEN`); **H3** — падение не привязано к записи, умирает уже на чтении.

## Использование

```bash
# Полная лесенка: чтения + no-op запись (ступень 9) — может уронить KiCad, в этом и цель теста
python -m kicadstamp.diagnostics.diagnose_first_write_crash

# Только чтения (ступени 1-8), без записи — безопасно, если KiCad открыт
python -m kicadstamp.diagnostics.diagnose_first_write_crash --until 8

# Пауза перед записью — проверка гипотезы H1 о гонке
python -m kicadstamp.diagnostics.diagnose_first_write_crash --delay 30

# Повторить no-op запись 3 раза подряд — проверить, стабильна ли запись после первой удачной
python -m kicadstamp.diagnostics.diagnose_first_write_crash --repeat 3

# Свой путь к лог-файлу и таймаут IPC (по умолчанию лог — diag_<timestamp>.log, таймаут 15000 мс)
python -m kicadstamp.diagnostics.diagnose_first_write_crash --log diag.log --timeout-ms 20000
```

## Параметры

- `--until` – выполнить ступени до N включительно (по умолчанию `9`; `8` = только чтения).
- `--delay` – пауза в секундах перед первой записью (проверка гипотезы H1).
- `--repeat` – сколько раз повторить no-op запись (по умолчанию `1`).
- `--log` – путь к лог-файлу (по умолчанию `diag_<timestamp>.log` в текущей директории).
- `--timeout-ms` – таймаут IPC (по умолчанию `15000`).

## Вывод

Построчный лог с вердиктом OK/FAIL и временем каждой ступени, снимок окружения (PID `kicad.exe`,
`KICAD_API_SOCKET`/`KICAD_API_TOKEN`, кандидаты в API-сокеты) до и после лесенки, итоговая сводка по
всем ступеням.

## Зависимости

`kipy` напрямую (не через `kicadstamp.kicad.adapter`). Снимок PID `kicad.exe` на Windows — через
`tasklist`, на остальных ОС — через опциональный `psutil` (не входит в `requirements.txt`; без него
обнаружение зомби-инстансов, гипотеза H2, молча отключается, но сама лесенка чтений/записи работает как
обычно).

## Осторожно

Плату не мутирует (запись — no-op), но на уязвимой сессии (см. issue #24966) сама попытка записи может
**уронить процесс KiCad целиком**. Сохраните открытые файлы перед запуском полной лесенки
(без `--until 8`).

Для краша нужно, чтобы в момент первой записи сессии был открыт **Schematic Editor** — если открыт только
PCB Editor, та же лесенка проходит чисто. Уязвима именно *первая* запись: прогоните лесенку (или реальный
`apply`) сначала при открытом только PCB Editor, а Schematic Editor открывайте уже после этого — обычно
безопасно. Полный разбор этого условия — [crash_hunting_ru.md](crash_hunting_ru.md#24966--краш-ipc-api-на-первой-записи-в-сессии).
