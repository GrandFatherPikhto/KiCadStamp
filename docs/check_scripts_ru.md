# Проверки платы и конфига (`tools/check_*.py`)

Три проверки из командной строки для поиска проблем расстановки на реальной плате. Все только читают.
Каждая принимает **профиль** (его папку или его `.sexp`) и отвечает на один вопрос:

| скрипт | вопрос | нужен KiCad |
|---|---|---|
| [`check_placement.py`](#check_placementpy) | Стоит ли каждая деталь на месте **своего** кластера? Чьё место заняла сдвинутая деталь? | да, с открытой платой этого профиля |
| [`check_config_records.py`](#check_config_recordspy) | Указывает ли каждая запись `.sexp` на деталь **своего** кластера и листа? | да, с открытой платой этого профиля |
| [`check_footprints_vs_library.py`](#check_footprints_vs_librarypy) | Совпадают ли футпринты **сохранённой** платы с библиотекой (3D-модели, полигоны, поля Role/Cluster)? | нет, читает сохранённый файл |

Это скрипты, а не кнопки в GUI, и так задумано: проверка — инструмент для охоты на баг, а не функция
программы. Запускаются из корня проекта виртуальным окружением проекта:

```bash
.venv/bin/python tools/check_placement.py profiles/3ch-awg-tia-v103
.venv/bin/python tools/check_config_records.py profiles/3ch-awg-tia-v103
.venv/bin/python tools/check_footprints_vs_library.py profiles/3ch-awg-tia-v103
```

**Ничего не пишется.** Плата только читается. Две «живые» проверки загружают профиль из временной копии
(относительные пути `../` к схеме в копии переписываются в абсолютные) и потом копию удаляют; папку
профиля они не трогают.

**Открыта не та плата → отказ.** Обе «живые» проверки сравнивают открытую в KiCad плату с `root_sheet`
профиля и при несовпадении отказываются работать (код выхода 2):

```
REFUSED: KiCad has '3CH-AWG-TIA-v103' open, the profile is for 'Test02' — open that board first
```

**Строки, на которые можно не смотреть.** При загрузке профиля могут появиться `N track segment(s) are
shorter than 2 × the position tolerance …` (загрузчик конфига сообщает об очень коротких отрезках меди в
`net_traces`; ничего не удаляется) и `Connected KiCad version … is newer than the API version of
kicad-python` (обычное расхождение версий kipy и KiCad). К проверке они не относятся.

**Что когда запускать:**

* детали после расстановки выглядят разбросанными → `check_placement.py`;
* расстановка отказывает или берёт не ту деталь → `check_config_records.py`;
* DRC пишет `lib_footprint_mismatch`, или после **Tools → Update Footprints from Library** →
  `check_footprints_vs_library.py`, и F8, если он сообщит о потерянных полях.

**Те же три проверки из GUI.** Вкладка **Проверки** рядом с Логом (Вид → Проверки — см.
[docs/gui_ru.md](gui_ru.md), раздел «Проверки») запускает эти же скрипты отдельным процессом и
показывает их вывод: кнопки, коды выхода и отчёты — ровно те, что описаны здесь, а строку статуса
красит код (0 зелёный, 1 жёлтый, 2 красный). Скрипты читают профиль **с диска** — сохрани профиль
(Ctrl+S) перед прогоном, если в GUI есть несохранённые правки, а для
`check_footprints_vs_library.py` сохрани плату в KiCad.

## `check_placement.py`

**Вопрос:** стоит ли каждая деталь на месте, которое ей отводит ячейка её кластера, — а если нет, то на
чьём месте она стоит?

```bash
.venv/bin/python tools/check_placement.py <папка профиля | .sexp профиля> [--slot-mm 0.5] [--plan dryrun.txt]
```

### Как работает

1. Футпринты платы собираются в **экземпляры кластеров**: одинаковое поле `Cluster` и одинаковый
   верхний лист (`Channel_0`, `FPGA`, `MCU` или `/` для корня).
2. Каждому экземпляру сопоставляется ячейка его сущности (`entities` профиля). Экземпляр, у кластера
   которого нет сущности или несколько ячеек, пропускается.
3. Положение экземпляра (поворот, зеркало) находится **голосованием**: каждая пара ролей предлагает своё
   положение через ту же подгонку, что и в программе (`cell_frame.fit_cell_frame`); побеждает
   предложение, при котором больше всего ролей укладывается в 0.05 мм (`RIGID_TOLERANCE_MM`).
4. Роли, не попавшие в большинство, считаются сдвинутыми. Для каждой проверка ищет место **другого**
   экземпляра в пределах `--slot-mm` (0.5 мм) от детали — «украденное» место.
5. Пустые места (роль есть в ячейке, но у экземпляра на плате её нет) проверяются: не стоит ли на них
   деталь другого кластера.

### Вывод

```
board footprints: 336; cluster instances: 73; tolerance 0.05 mm, slot match 0.5 mm
instances checked: 64; clean: 49; with problems: 15; skipped: 9

[PIF_3V3_VCCIO @ FPGA] cell 'pif_3v3_vccio': 3/5 roles agree (rot +0, mirror False)
   MISPLACED C_OUT_BULK (C100) at (100.141, 122.418), its slot (101.445, 93.056) — 29.392 mm off
      → stands on slot C_OUT_BULK of [PIF_1V2_VCCD_PLL @ FPGA] (0.000 mm), whose own part is C98
```

| метка | значение |
|---|---|
| `[КЛАСТЕР @ лист] cell '…': N/M roles agree` | экземпляр и его ячейка; N из M найденных ролей согласны с одним положением |
| `MISPLACED` | деталь вне согласованного положения; строка говорит, где она стоит, где её место и на каком расстоянии |
| `→ stands on slot R of [ДРУГОЙ @ лист]` | сдвинутая деталь заняла место другого экземпляра; `whose own part is X` — та деталь, которая должна там стоять |
| `FRAME NOT TRUSTED` / `PAIR?` | согласны меньше двух ролей (обычно ячейка из двух ролей): что-то не так, но кто виноват — не сказать. Положение подогнано под одну деталь (у неё всегда `0.000 mm off`), вся разница достаётся другой |
| `DUPLICATE role R` | две детали одного экземпляра несут одну роль |
| `TURNED R (X) by …` | деталь на своём месте, но повёрнута относительно ячейки (больше чем на 0.1°) |
| `(absent roles: …)` | роли, которые есть в ячейке, но которых нет у экземпляра на плате |
| `(roles not in the cell: …)` | роли, которые есть у экземпляра, но которых нет в ячейке |
| `--- empty slots taken by another cluster's part ---` | место без своей детали, занятое деталью другого кластера |
| `--- skipped instances ---` | `no entity cell` (нет сущности), `N cells`, `cell '…' missing`, `1 matched role(s) — no frame` (по одной детали положение не вычислить), `no usable pair` |

### Изменения с прошлого прогона

Каждый настоящий прогон (не `--plan`) сравнивает находки с прошлым прогоном **того же профиля** и
запоминает себя в `~/.local/state/kicadstamp/placement_check_<профиль>.json` (состояние машины, вне
`profiles/`). Вкладка **Проверки** в GUI запускает тот же скрипт и потому делит с терминалом одну базу:
строка `NEW` может назвать изменение, сделанное из вкладки (или из терминала), — оба прогона
запоминаются в одном и том же файле.

```
=== CHANGES since the last run ===
   last run: 2026-10-21 09:33:24
   GONE  C30 (C_IN_BYPASS of PIF_3V3_VDD @ MCU) at (186.304, 131.348), 36.399 mm off its slot
   now: 30 problem(s) on the board
```

* `NEW` — появилось с прошлого прогона: действие между прогонами поставило деталь не туда;
* `GONE` — исправилось с прошлого прогона;
* `nothing changed` / `first run — this result is the baseline` — ничего не изменилось / первый прогон,
  он становится базой.

**Как поймать действие, которое сдвигает детали:** приведи плату в порядок, запусти проверку один раз
(это база), потом запускай после каждого действия расстановки (Apply, перерисовка дерева, Redraw
selected). Первое `NEW` укажет на виновное действие.

### `--plan`: проверить расстановку до того, как она случится

```bash
python kicadstamp_cli.py apply profiles/3ch-awg-tia-v103/config.sexp --dry-run > dryrun.txt
.venv/bin/python tools/check_placement.py profiles/3ch-awg-tia-v103 --plan dryrun.txt
```

Проверка читает запланированные положения (строки вида `  C100: (x, y) mm, angle=a` из вывода
dry-run), переносит туда футпринты **в памяти** и проверяет результат. Прогон с `--plan` не
запоминается и изменений не печатает.

### Код выхода

`0` — чисто, `1` — есть находки (какие — сказано в отчёте), `2` — отказ (открыта не та плата). Прогон с
`--plan` отвечает так же; он только не сравнивает с прошлым прогоном.

Код говорит лишь о том, ЕСТЬ ли что-то в отчёте; сам отчёт остаётся истиной. По этому коду красит строку
статуса вкладка **Проверки** в GUI и его же видят цепочки `&&` в оболочке.

## `check_config_records.py`

**Вопрос:** указывает ли каждая запись профиля на деталь **своего** кластера на **своём** листе?

```bash
.venv/bin/python tools/check_config_records.py <папка профиля | .sexp профиля>
```

Номеров деталей (`R15`, `C4`) в конфиге нет: запись адресует деталь тройкой **роль + кластер + лист**.
Проверка отвечает на каждый такой адрес по открытой плате с теми же правилами, что и программа:
кластер — `cluster_matching.cluster_prefix_match` (префикс по сегментам, без учёта регистра), лист —
`sheet_names.sheet_in_path` (`"/"` — корневой лист).

### Что проверяется

| раздел | записи | правило |
|---|---|---|
| сущности | каждая роль ячейки каждой сущности | ровно одна деталь с этой ролью в кластере сущности на листе сущности |
| детали, которых нет ни в одной ячейке | каждая деталь экземпляра кластера, у которого есть сущность | её роль есть в ячейке этого экземпляра |
| явные `refs` | `refs` сущности (роль → номер детали) | деталь есть и несёт эту роль, этот кластер, этот лист |
| якоря | `anchor_role`/`anchor_cluster`/`anchor_sheet` у `net_traces`, mount-узлов, якорей деревьев, `points`, `thermal_via_arrays` | ровно одна деталь |
| концы меди | роли из `pads` медной трассы и из `net_from_role` её дорожек и переходов | роль есть на плате (кластер не требуется: другой конец меди может стоять в другом кластере) |

Списанные (`retired`) сущности и медные трассы не проверяются. Сущности без кластера (адресуются только
номерами или листом) перечисляются в конце как непроверенные.

### Вывод

```
--- entities: cell roles → parts of the entity's cluster ---
[conn_mcu_usart_mcu] cell 'conn_mcu_usart', CONN_MCU_USART @ MCU
   ABSENT    role R_SERIES_TX: the role stands on R15 (MCU @ MCU)

--- parts of a recorded cluster that no cell lists ---
   UNLISTED  Y1 (Role XTAL of XTAL_8MHZ @ MCU): no cell of XTAL_8MHZ @ MCU has it

--- anchors (net_traces, mount nodes, tree anchors, points, thermal vias) ---
   SHEET     tree fpga node 'fpga_22_oscill': anchor FPGA of FPGA @ Channel_0 — resolves to IC1 only because sheet narrowing is soft — the record says 'Channel_0', IC1 stands on FPGA @ FPGA
   117 anchor(s) checked

result: 7 problem(s)
```

| вердикт | значение | что делать |
|---|---|---|
| `ABSENT` | ни одна деталь кластера записи на её листе не несёт эту роль. Строка говорит, где роль стоит на самом деле — `the role stands on R15 (MCU @ MCU)`, — или что её нет ни на одной детали | деталь помечена в схеме не тем кластером (поправить схему, потом F8) или в ячейке устаревшая роль (роль переименована: обновить ячейку) |
| `UNTAGGED` | роль есть на листе записи, но у детали **нет** поля Cluster | поставить Cluster в схеме, F8 — или проверить плату `check_footprints_vs_library.py` (KiCad мог переименовать поле) |
| `AMBIGUOUS` | подходят несколько деталей — расстановка откажет | дать деталям разные роли или сузить запись (лист, кластер) |
| `SHEET` | лист в записи неверный, но она всё равно находит единственную деталь своего кластера на другом листе — потому что лист сужает выбор, только если хоть один кандидат остаётся | исправить `sheet` в записи: сейчас работает случайно и сломается, как только появится второй кандидат |
| `UNLISTED` | деталь экземпляра кластера, роли которой нет ни в одной ячейке этого экземпляра | обычно вторая половина переименованной роли (`ABSENT` OSC + `UNLISTED` XTAL); иначе добавить роль в ячейку или перепометить деталь |
| `PINNED` | запись `refs` у сущности называет несуществующую деталь или деталь с другой ролью/кластером/листом | исправить `refs` |

### Код выхода

`0` — чисто, `1` — есть находки, `2` — отказ (открыта не та плата).

## `check_footprints_vs_library.py`

**Вопрос:** совпадают ли футпринты **сохранённой** платы с библиотекой?

```bash
.venv/bin/python tools/check_footprints_vs_library.py <плата.kicad_pcb | папка профиля | .sexp профиля> [--lib-dir <каталог футпринтов>] [--all]
```

Читает **сохранённый файл**, а не KiCad: сначала сохрани плату. KiCad может быть не запущен. Если
передать профиль, берётся плата рядом с `root_sheet` профиля.

### Каталог библиотеки

Порядок — как у самого KiCad: `--lib-dir`, иначе `$KICAD10_FOOTPRINT_DIR`, иначе та же переменная в
`kicad_common.json`, иначе платформенный дефолт штатной установки (`/usr/share/kicad/footprints`, бандл
приложения на macOS, `%PROGRAMFILES%\KiCad\<версия>\share\kicad\footprints`). `kicad_common.json` и
пользовательский `fp-lib-table` читаются из каталога настроек KiCad **для этой платформы** —
`~/.config/kicad/10.0` на Linux, `%APPDATA%\kicad\10.0` на Windows, `~/Library/Preferences/kicad/10.0`
на macOS. Если ни один из них не каталог, проверка **отказывается** (код 2) и печатает все места, где
искала: прогон, до которого библиотека недостижима, говорит об этом, а не рапортует по каждому
футпринту «не проверено».

### Что проверяется

Для каждого футпринта находится его копия в библиотеке — через `fp-lib-table` проекта и пользователя
(`${KIPRJMOD}` и переменные путей из `kicad_common.json` подставляются), иначе
`<lib-dir>/<библиотека>.pretty`. Затем:

| проверка | что ловит |
|---|---|
| число 3D-моделей | модели, потерянные при повороте футпринтов скриптом через kicad-python 0.8.0 (`FootprintInstance.orientation`; в main kicad-python исправлено, в выпуск ещё не попало) |
| число точек каждого `fp_poly`, по порядку | замыкающая точка полигона, потерянная при IPC `UpdateItems` → DRC `lib_footprint_mismatch` (KiCad, задача #25889) |
| Role/Cluster на месте | поля, потерянные после **Update Footprints from Library** (KiCad, задача #25887) |
| значение `KiLib_Generator` = библиотечному | одно из **наших** полей переименовано в библиотечное `KiLib_Generator` (#25887) — даже если Role/Cluster уцелели (например, `Sim.Pins`) |

### Вывод

```
profile Test04.sexp -> board /home/denis/Projects/KiCad/Tests/Test02/Test02.kicad_pcb
board Test02.kicad_pcb: 12 footprint(s); library /usr/share/kicad/footprints
FIELDS LOST: 8 footprint(s) lack Role or Cluster — KiCadStamp would read them wrong; run F8 (update fields from schematic) BEFORE any placement:
  C1     Role=C_IN_BYPASS      Cluster=—                      KiLib_Generator=LDO_P3V3
FIELD RENAMED: 1 footprint(s) carry KiLib_Generator with a value that is not the library's — some other field of ours was renamed; run F8:
  D1     KiLib_Generator=1=K 2=A                library has SMD_2terminal_chip_molded
result: 3 ok, 9 damaged, 0 not checked
```

| строка | значение | что делать |
|---|---|---|
| `REF lib:name: 3D models 0 of 1` | футпринт потерял 3D-модель | Tools → Update Footprints from Library для этого футпринта (включены только 3D-модели), затем F8 |
| `REF lib:name: fp_poly points [3] vs library [4]` | полигон потерял точку (DRC `lib_footprint_mismatch`) | такое же точечное обновление; для меди безвредно |
| `FIELDS LOST` | нет Role или Cluster; наше значение лежит в `KiLib_Generator` | **F8 до любой расстановки** (KiCadStamp на такой плате и так откажется расставлять) |
| `FIELD RENAMED` | в `KiLib_Generator` не библиотечное значение: переименовано другое наше поле | F8 |
| `fields: ok …; N also carry KiLib_Generator` | Role/Cluster целы; библиотечное поле просто добавилось рядом | ничего |
| `library copy not found — not checked` | копия в библиотеке не найдена | передать `--lib-dir` или проверить fp-lib-table |

`--all` печатает и чистые футпринты.

**Как безопасно делать Update Footprints from Library:** обновлять только нужное (один футпринт или
только 3D-модели), текстовые опции не включать, сразу после — F8, и запустить эту проверку.

### Код выхода

`0` — чисто, `1` — найдены повреждения, `2` — отказ (нет такого файла, не плата и не профиль, или не
найден каталог библиотеки футпринтов).

## `--json PATH`: тот же прогон, для машины

Каждая проверка принимает `--json PATH` (включая `merge_duplicate_mounts.py`). Человеческий отчёт
на stdout не меняется ни на байт, а машинный пишется за ТОТ ЖЕ прогон — одно чтение платы, одна
загрузка конфига (форма живёт в одном месте: `kicadstamp/check_report.py`).

```bash
.venv/bin/python tools/check_placement.py profiles/3ch-awg-tia-v103 --json /tmp/r.json
```

* `schema` — версия формы; читатель, который этого числа не знает, обязан сказать об этом;
* `script`, `when`, `profile`, `board`;
* `result` — `exit` (ровно тот код, что вернула команда), `problems`, `ok`, `skipped`,
  `not_checked` (`ok` = `null` там, где проверка его не считает);
* `sections[]` — все разделы, которые прогон выполнил, в порядке печати, у каждого `problems[]`
  (пустой = «проверено, чисто»); панель пустые разделы не показывает, сводка их перечисляет;
* проблема — `{key, kind, text, refs[], where, to_node}`: `text` — та самая строка stdout,
  `kind` — из закрытого словаря (`MISPLACED`, `TAKEN`, `SHEET`, `ABSENT`, `MODELS`, `FIELDS_LOST`,
  `MERGE`, …), `refs` — части, которые можно подсветить, `to_node` `{tree, node, cell}` — куда
  ведёт «К ноде в дереве», и заполняется только когда проверка это ДЕЙСТВИТЕЛЬНО знает;
* `changes` — NEW/GONE по тому же `key` против прошлого прогона того же профиля
  (`~/.local/state/kicadstamp/<script>_<profile>.json`, на первом прогоне `baseline: true`).
  `check_placement.py` раньше держал `placement_check_<profile>.json` — этот файл всё ещё ЧИТАЕТСЯ,
  поэтому первый прогон после переезда не объявляет всё новым. У сухого прогона merge `changes`
  НЕТ (нечего сравнивать), зато есть `applied` — `false` для сухого прогона или отказа, `true`
  после успешного `--write` — и `refusal` с причиной;
* `notes[]` — строки `SKIPPED` / `NOT_CHECKED` / `INFO`, которые не являются проблемами.
  Футпринт без копии в библиотеке — это заметка `NOT_CHECKED` (и `result.not_checked`), а НЕ
  проблема: «не смогли посмотреть» не должно читаться как «нашли повреждение»;
* `result.problems` — ровно сумма по разделам: кто считает дерево и кто читает заголовок,
  разойтись не могут;
* `to_node` для всего, что про ЭКЗЕМПЛЯР, — это узел дерева, у которого `ref` И ЕСТЬ имя
  сущности (именно так устроены деревья Дениса: mount-узел стоит на паде ХОЗЯИНА, поэтому поиск
  по якорям не находит почти ничего), и `null`, а не догадка, если имя не уникально.

Правило: поменял находки проверки — поменяй её `kind` ЗДЕСЬ и в `check_report.KINDS`; вкладка
Checks переключается по `kind`, а не по прозе.
