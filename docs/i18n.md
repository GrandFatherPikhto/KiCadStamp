# Internationalization (i18n) — gettext/Babel

## Why

The project started fully in Russian (logs, fatal errors, `--help`). Most people trying KiCadStamp are
expected to be English-speaking, so all user-facing output goes through `gettext`, with English as the
source language (`msgid`) and Russian as the translation.

## How it's built

- **Mechanism** — standard `gettext`, extraction/build tool is **Babel** (`pybabel`), not
  `xgettext`/`msgfmt` directly: pure Python, installs via `pip install babel`, no system GNU gettext
  toolchain required (matters on Windows).
- **`kicadstamp/i18n.py`** — everything lives in two functions:
  - `detect_language() -> "ru" | "en"` — detects the language from the environment. The precedence is
    the real POSIX/gettext order, not an invented one: `LANGUAGE` (a gettext extension, colon-separated
    list, highest priority) → `LC_ALL` → `LC_MESSAGES` (the POSIX category specifically for message
    language, more precise than the catch-all `LANG`) → `LANG`. If none is set or none starts with `ru`
    → English. On Windows, where these variables are usually not set at all, there's a fallback to the
    system locale (`GetUserDefaultUILanguage()`/`locale.getlocale()`). Deliberately a binary rule
    (ru/non-ru), not arbitrary multi-language support — simpler and more predictable.
  - `setup_i18n()` — called **once**, automatically, on package import (`kicadstamp/__init__.py`). Loads
    `gettext.translation(...)`, installs `_()` globally in the `i18n.py` module. **Important:** the
    language is fixed for the whole process at the moment `kicadstamp` is first imported — it cannot be
    changed on the fly mid-run (see "Gotchas" below).
- **`locales/<lang>/LC_MESSAGES/kicadstamp.{po,mo}`** — translation catalogs, `en` and `ru`. `.po` is the
  editable text format (human-readable, compatible with Poedit etc.), `.mo` is the compiled binary that
  `gettext` actually loads at runtime.
- **`babel.cfg`** — extraction config, `[python: **.py]` (scan every `.py` file in the project).
- **`tools/update_i18n.py`** — one command for the whole cycle: `pybabel extract` → `pybabel update` (en,
  ru) → `pybabel compile` (en, ru) → deletes the temporary `messages.pot`. Run from the repo root:
  ```bash
  python tools/update_i18n.py
  ```
  Ignores `.git`, `files/`, `old/`, `arch/`, `test_sample/`, `venv/` while scanning (`IGNORE_DIRS` list
  inside the script).

## Adding or changing a translatable string

1. In code — wrap it in `_()`: `logger.info(_("Found {n} components").format(n=n))`. **`msgid` is always
   English** (this matters: if a translation is missing, gettext silently falls back to showing the raw
   `msgid` — if it were Russian and the session language is English, Russian text would leak into an
   English session). f-strings are incompatible with `_()` — `pybabel extract` can't parse them, only
   `_("...").format(...)` or `_("...") % {...}`.
2. Run `python tools/update_i18n.py` — pulls the new `msgid` into both `.po` catalogs.
3. Fill in `msgstr` in `locales/ru/LC_MESSAGES/kicadstamp.po` (the English `.po` usually matches `msgid`
   verbatim). Check what's still missing:
   ```bash
   msgfmt --statistics locales/ru/LC_MESSAGES/kicadstamp.po -o /dev/null
   ```
   For translating a batch of strings at once, `polib` (`pip install polib`) is convenient: load the
   `.po`, iterate entries where `entry.translated() == False or "fuzzy" in entry.flags`, set `msgstr`,
   clear the `fuzzy` flag, `po.save()`. There's no standing tool for this in the repo — it's usually a
   one-off script for a specific batch of strings (see the approach used in past chat sessions/handoffs).
4. Recompile: run `python tools/update_i18n.py` again (it does both update and compile in one pass) — or
   just `pybabel compile -d locales -l ru -D kicadstamp`.

## Gotchas already hit

- **`from ...i18n import _` is a snapshot, not a live reference.** Every module that imports `_` this way
  gets its own copy of the translation function **at the time it is imported**. Since
  `kicadstamp/__init__.py` calls `setup_i18n()` on the package's first import, and every other module is
  imported afterwards, the language ends up fixed once for the whole process. Reassigning
  `kicadstamp.i18n._` mid-run (e.g. via `monkeypatch` in a test) does **not** affect already-imported
  modules — their own `_` stays whatever it was. To exercise a different language, either run a separate
  process with a different `LANG`/`LC_ALL`/`LANGUAGE`, or patch `_` in the specific module
  (`monkeypatch.setattr(some_module, "_", ...)`), not in `kicadstamp.i18n`.
- **Tests that match translated text directly break when the environment changes.** A real case:
  `pytest.raises(ValidationError, match="NO component with this role")` used to pass because the string
  was untranslated (gettext silently returned the raw English `msgid` even under `LANG=ru`). Once the
  string got translated, the same test started matching real Russian text and failed under a `LANG=ru_*`
  test environment. The fix is **not** to patch `_` (doesn't work, see above) but to match both
  languages at once: `match="NO component with this role|НЕТ ни одного компонента с этой ролью"`. This
  fits the project's design (strictly two languages, not arbitrary multi-language) — a bilingual OR
  pattern isn't excessive here, it's exactly the real contract.
- **f-strings are incompatible with extraction** — see above, write directly as `_("...").format(...)`.

## Coverage status (snapshot 2026-07-27)

Modules that actually produce user-facing output (`kicadstamp_cli.py`, `config/loader.py`,
`validation.py`, all of `placement/` including `services/*.py` and `executor/*.py`,
`template_extraction.py`, `registry.py`, `undo.py`, `net_resolution.py`, `sheet_names.py`,
`geometry/*.py`, `kicad/adapter.py`, `exceptions.py`) — **fully wrapped in `_()`**, not a single raw
literal. The `ru` catalog has 609 strings, all translated (0 untranslated, 0 fuzzy as of this snapshot).

**Deliberately not started** (low priority, developer/diagnostic scripts, not seen by a regular user):
`kicadstamp/diagnostics/*.py`, `tools/*.py` — none of them import `i18n` at all.

The detailed rollout plan (broken into parts, with acceptance criteria per part) originally lives in
`techdocs/handoff/i18n_gettext_handoff.md` (internal, not in git).

## Tests

`tests/utils/test_i18n.py` — `detect_language()` (precedence `LANGUAGE > LC_ALL > LC_MESSAGES > LANG`, default
English, the Windows fallback itself isn't unit-tested — it's platform-specific) and `setup_i18n()`
(returns the selected language, actually translates a known string, doesn't crash on an unknown locale
thanks to `fallback=True`).

Any new test that matches an error/log message by text must either match both languages (see "Gotchas"
above) or match a stable, untranslatable marker (a role/net/refdes name — something that arrives via
`.format()`, not the translatable prose itself).
