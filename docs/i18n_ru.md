# Интернационализация (i18n) — gettext/Babel

## Зачем

Проект начинался полностью на русском (логи, фатальные ошибки, `--help`). Ожидается, что пробовать
KiCadStamp будут в основном англоязычные пользователи, поэтому весь пользовательский вывод переведён
через `gettext`, с английским как исходным языком (`msgid`) и русским как переводом.

## Устройство

- **Механизм** — стандартный `gettext`, инструмент извлечения/сборки — **Babel** (`pybabel`), не
  `xgettext`/`msgfmt` напрямую: чистый Python, ставится через `pip install babel`, не требует
  системного GNU gettext-тулчейна (важно для Windows).
- **`kicadstamp/i18n.py`** — вся логика в двух функциях:
  - `detect_language() -> "ru" | "en"` — определяет язык из окружения. Порядок приоритета — реальный
    POSIX/gettext, не выдуманный: `LANGUAGE` (расширение gettext, список через двоеточие, самый высокий
    приоритет) → `LC_ALL` → `LC_MESSAGES` (POSIX-категория именно для языка сообщений, точнее общего
    `LANG`) → `LANG`. Если ни одна не задана/не начинается с `ru` → английский. На Windows, где эти
    переменные обычно вообще не выставлены, — фоллбэк на системную локаль
    (`GetUserDefaultUILanguage()`/`locale.getlocale()`). Намеренно бинарное правило (ru/не-ru), не
    произвольная мультиязычность — так проще и предсказуемее.
  - `setup_i18n()` — вызывается **один раз**, автоматически, при импорте пакета
    (`kicadstamp/__init__.py`). Загружает `gettext.translation(...)`, устанавливает `_()` глобально в
    модуле `i18n.py`. **Важно:** язык фиксируется на весь процесс в момент первого импорта `kicadstamp` —
    поменять его на лету посреди работы нельзя (см. «Грабли» ниже).
- **`locales/<lang>/LC_MESSAGES/kicadstamp.{po,mo}`** — каталоги переводов, `en` и `ru`. `.po` —
  редактируемый текстовый формат (человекочитаемый, совместим с Poedit и т.п.), `.mo` — скомпилированный
  бинарник, который реально грузит `gettext` в рантайме.
- **`babel.cfg`** — конфиг извлечения, `[python: **.py]` (сканировать все `.py`-файлы проекта).
- **`tools/update_i18n.py`** — единая команда на весь цикл: `pybabel extract` → `pybabel update` (en, ru)
  → `pybabel compile` (en, ru) → удаление временного `messages.pot`. Запускать из корня проекта:
  ```bash
  python tools/update_i18n.py
  ```
  Игнорирует `.git`, `files/`, `old/`, `arch/`, `test_sample/`, `venv/` при сканировании (список
  `IGNORE_DIRS` в самом скрипте).

## Как добавить/поменять переводимую строку

1. В коде — обернуть в `_()`: `logger.info(_("Found {n} components").format(n=n))`. **`msgid` — всегда
   на английском** (это принципиально: если перевод отсутствует, gettext молча показывает сырой `msgid`
   — если он будет русским, а язык сессии английский, потечёт русский текст в англоязычную сессию).
   f-строки с `_()` несовместимы — `pybabel extract` их не распознаёт, только `_("...").format(...)`
   или `_("...") % {...}`.
2. Прогнать `python tools/update_i18n.py` — подтянет новый `msgid` в оба `.po`.
3. Заполнить `msgstr` в `locales/ru/LC_MESSAGES/kicadstamp.po` (английский `.po` обычно совпадает с
   `msgid` дословно). Проверить остаток непереведённого:
   ```bash
   msgfmt --statistics locales/ru/LC_MESSAGES/kicadstamp.po -o /dev/null
   ```
   Для массового перевода партии строк удобно использовать `polib` (`pip install polib`): загрузить
   `.po`, пройтись по `entry.translated() == False or "fuzzy" in entry.flags`, проставить `msgstr`, снять
   флаг `fuzzy`, `po.save()`. Готового постоянного инструмента для этого в проекте нет — обычно это
   разовый скрипт под конкретную партию строк (см. пример подхода в истории чата/хендоффах).
4. Перекомпилировать: `python tools/update_i18n.py` ещё раз (он и update, и compile делает за один
   проход) — или отдельно `pybabel compile -d locales -l ru -D kicadstamp`.

## Грабли, на которые уже наступали

- **`from ...i18n import _` — это снимок, не живая ссылка.** Каждый модуль, импортирующий `_` таким
  образом, получает копию ссылки на функцию перевода **на момент своего импорта**. Так как
  `kicadstamp/__init__.py` вызывает `setup_i18n()` при первом импорте пакета, а все остальные модули
  импортируются позже — язык фактически фиксируется один раз на весь процесс. Переустановить
  `kicadstamp.i18n._` в середине работы (например, в тесте через `monkeypatch`) **не** повлияет на уже
  импортированные модули — их собственная `_` останется прежней. Хотите проверить поведение под другим
  языком — либо отдельный процесс с другим `LANG`/`LC_ALL`/`LANGUAGE` в окружении, либо патчить `_`
  точечно в конкретном модуле (`monkeypatch.setattr(some_module, "_", ...)`), не в `kicadstamp.i18n`.
- **Тесты, матчащие переведённый текст напрямую — ломаются при смене окружения.** Реальный случай:
  `pytest.raises(ValidationError, match="NO component with this role")` работал, пока строка была
  непереведена (gettext тихо отдавал сырой английский `msgid` даже при `LANG=ru`). Как только строка
  переведена — тест матчит уже русский текст и падает, если `LANG` тестового окружения `ru_*`. Решение —
  **не** пытаться патчить `_` (см. пункт выше не работает по той же причине), а матчить по обоим языкам
  сразу: `match="NO component with this role|НЕТ ни одного компонента с этой ролью"`. Это соответствует
  дизайну проекта (жёстко два языка, не произвольная мультиязычность) — двуязычный OR-паттерн не
  избыточен, а ровно отражает реальный контракт.
- **f-строки несовместимы с извлечением** — см. выше, писать сразу в форме `_("...").format(...)`.

## Статус покрытия (снимок 2026-07-27)

Модули, реально пропускающие пользовательский вывод (`kicadstamp_cli.py`, `config/loader.py`,
`validation.py`, весь `placement/` включая `services/*.py` и `executor/*.py`, `template_extraction.py`,
`registry.py`, `undo.py`, `net_resolution.py`, `sheet_names.py`, `geometry/*.py`, `kicad/adapter.py`,
`exceptions.py`) — **полностью через `_()`**, ни одного сырого литерала. Каталог `ru` — 609 строк, все
переведены (0 непереведённых, 0 fuzzy на момент этой сводки).

**Сознательно не начато** (низкий приоритет, разработческие/диагностические скрипты, обычный пользователь
их не видит): `kicadstamp/diagnostics/*.py`, `tools/*.py` — ни один файл не импортирует `i18n`.

Подробный план внедрения (по частям, с критериями приёмки) — исходно в
`techdocs/handoff/i18n_gettext_handoff.md` (внутренний, не в git).

## Тесты

`tests/utils/test_i18n.py` — `detect_language()` (приоритет `LANGUAGE > LC_ALL > LC_MESSAGES > LANG`, дефолт
английский, Windows-фоллбэк не тестируется юнит-тестами — платформо-зависим) и `setup_i18n()`
(возвращает выбранный язык, реально переводит известную строку, не падает на неизвестной локали
благодаря `fallback=True`).

Любой новый тест, матчащий сообщение об ошибке/лог по тексту, должен либо матчить оба языка (см.
«Грабли» выше), либо матчить по стабильному, непереводимому признаку (имя роли/net/refdes — то, что
приходит через `.format()`, а не сама переводимая проза).
