# Справочник по YAML-конфигу

Всё про то, как **писать** конфиг KiCadStamp с нуля: корневые поля, каждая секция (`cells:`/`chains:`/
`clone_placements:`/`thermal_via_arrays:`/`points:`), `include:`, `extract_profiles:`/`clone_profiles:`.
Про запуск команд над конфигом — [docs/commands_ru.md](commands_ru.md); про написание расстановки на
Python вместо ручного YAML — [docs/python_ru.md](python_ru.md); про архитектуру модулей/классов за этой
схемой — [docs/architect_ru.md](architect_ru.md).

Каждый пример на этой странице взят из реального, реально загружающегося конфига —
`boards/3ch-awg-tia/profiles/*.sexp`, не придуманный синтаксис. Имена полей соответствуют
`kicadstamp/config/models.py` на 2026-08-01.

## Корневые поля

```yaml
# boards/3ch-awg-tia/profiles/fpga.sexp
registry_path: registries/fpga.json
track_registry_path: registries/fpga.tracks.registry.json
log_file: ../logs/fpga.log
schematic_dir: ../../../test_boards/3CH-AWG-TIA
layer: B.Cu

thermal_via_arrays:
  - ...

include:
  - templates/fpga_pi_filters.sexp
  - fpga_extracts.sexp
  - chains/fpga_spokes.sexp

clone_placements:
  ...
```

| Поле | Тип | Смысл |
|---|---|---|
| `layer` | строка | `F.Cu`\|`B.Cu` — слой по умолчанию только для пути `chains:`/ManualSpoke. У `clone_placements:` свой `layer:` на каждой записи, этим полем не затрагивается. |
| `cells` | словарь | Инлайн-определения `Cell` (см. ниже). Руками пишутся редко — обычно заполняются `extract`; можно разнести по файлам через `include:` (см. ниже). |
| `points` | словарь | Именованные переиспользуемые якоря (см. **Points** ниже). |
| `include` | список | Другие YAML-файлы для подключения — см. **`include:`** ниже. |
| `chains` | список | Правила ManualSpoke — см. **`chains:`** ниже. |
| `clone_placements` | список | Размещения TemplatePlacer — см. **`clone_placements:`** ниже. |
| `entities` | список | Записи Entity — «что» размещения, БЕЗ позиции — см. **`entities:`** ниже. |
| `trees` | список | Деревья размещений — ЕДИНСТВЕННОЕ место, где может жить позиция — см. **`trees:`** ниже. |
| `thermal_via_arrays` | список | Любое число термо-via-сеток, каждая с собственным именем/якорем — см. **`thermal_via_arrays:`** ниже. |
| `place_components` | булево | По умолчанию `true`. `false` — перемещать/создавать via и треки, но не трогать позиции компонентов. |
| `skip_existing_components` | булево | По умолчанию `false`. Пропускать компоненты (и их via/треки), уже стоящие в целевой позиции — дешёвая идемпотентность для повторных прогонов. Примечание (2026-08-31): позиционный пре-чек ТРЕКОВ выполняется независимо от этого флага — он лишь пропускает запланированный трек, который уже существует ровно на этой позиции/цепи/ширине/слое, поэтому никогда не удаляет медь, а только предотвращает буквальные дубликаты. |
| `via_keepout_clearance_mm`, `via_search_step_mm`, `via_search_max_radius_mm`, `via_search_n_directions` | числа | Параметры поиска свободного места, используются только термо-via. |
| `schematic_dir` | строка | Папка с `*.kicad_sch` проекта, для резолва `anchor_sheet`. Относительно расположения самого этого YAML, как `registry_path`. |
| `schematic_files` | список строк | Дополнительные `.kicad_sch`-файлы вне `schematic_dir` (например, корневой лист, если он лежит отдельно). |
| `registry_path`, `track_registry_path` | строки | Явные пути к реестрам расстановки/треков (см. [docs/placement_ru.md](placement_ru.md)). По умолчанию — выводятся из имени/пути самого конфига. |
| `log_file` | строка | Лог-файл для `apply` этого конфига — не нужно каждый раз указывать `--log-file`. Флаг CLI `--log-file`, если задан, побеждает. |
| `board_name` | строка | Опционально. Имя платы (`.kicad_pcb`), для которой этот конфиг, например `3CH-AWG-TIA-v102` (расширение можно опустить). Если задано, `apply` фаталит ДО всех остальных проверок, когда в KiCad реально открыта другая плата, — понятная ошибка «не та плата» вместо вводящего в заблуждение фатала в глубине другой подсистемы (реальный случай: устаревший `schematic_dir`, указывавший на прошлую ревизию платы, всплыл как посторонний фатал `anchor_sheet` в Extract). Сравнение регистронезависимое, по basename без расширения, никогда по полному пути (конфиг и плата живут в разных поддеревьях, пути различаются между машинами). Не задано = проверки нет, старые профили не затрагиваются. |

**Устарело, фатал при загрузке (без тихого фолбэка):** `templates_file`/`template_files` (переименованы
в `cells_file`/`cell_files`, которые сами были слиты в `include:` 2026-08-02 — см. ниже), `cells_file`/
`cell_files` (внешние файлы `Cell` теперь просто перечисляются в `include:`, как и любая другая
разносимая секция — содержимое внешнего файла оборачивается в ключ `cells:`), `target_ref`/`side` в
корне.

## `cells:` — определение переиспользуемой геометрии

`Cell` (до 2026-07-31 — `SpokeTemplate`) — кусок геометрии, описанный **один раз**, в своей локальной
системе координат (`along`/`across`, инвариантной к повороту — всегда описывается при
`rotation_deg=0`), а затем размещаемый (и поворачиваемый/зеркалируемый/сдвигаемый целиком) там, где
используется — спицей `chains:` или записью `clone_placements:`.

`Cell` может быть **листом** (`vias:`/`components:`/`tracks:`), **композитом** (`clone_placements:`,
вкладывающий другие ячейки), или и тем, и другим сразу.

### Лист-ячейка

```yaml
# boards/3ch-awg-tia/profiles/templates/ldo_3v3.sexp — файл, перечисленный
# в include: у power.sexp (внешние файлы Cell оборачиваются в cells:, та
# же форма, что инлайн-блок — cells_file:/cell_files: слиты в include:
# 2026-08-02)
cells:
  p3v3_ldo:
    layer: F.Cu
    vias:
      - offset_along_mm: -7.415
        offset_across_mm: -2.28
        net: GND
        drill_mm: 0.5
        diameter_mm: 1.0
      - offset_along_mm: -7.415
        offset_across_mm: 2.28
        net: '{PWR_IN}'          # {placeholder} — резолвится из params: в момент размещения
        drill_mm: 0.5
        diameter_mm: 1.0
    components:
      - role: LDO_3V3             # матчится по кастомному полю Role, не по конкретному ref
        offset_along_mm: 0.0
        offset_across_mm: 0.0
        angle_deg: 0.0
        net_template: '{PWR_OUT}' # только для матчинга ролей по сетям у ClonePlacement
        net_template_pad: '1'     # опционально: на каком паде резолвленного кандидата эта цепь
    tracks:
      - start_along_mm: -5.04
        start_across_mm: -2.28
        end_along_mm: -7.415
        end_across_mm: -2.28
        width_mm: 0.8
        net: GND
```

- `vias:` — `offset_along_mm`/`offset_across_mm` (локальные), `net:` (`null`/пусто означает
  «наследовать цепь объемлющей цепи» (enclosing Chain) — так умеет только `chains:`/ManualSpoke;
  `clone_placements:` падает фаталом на via без цепи, поскольку у него нет объемлющей Chain,
  чью цепь можно было бы унаследовать), `drill_mm`,
  `diameter_mm`. Та же конвенция `null` и у `net:` в `tracks:` ниже. Чекбокс **"Chain net (null)"**
  в GUI Extract (2026-08-05), напротив каждого нета, пишет ровно это — см. `rule_nets:` у
  `extract_profiles:` ниже, CLI/профильный эквивалент (`--rule-net`).
- `components:` — `role:` (сравнивается с кастомным полем `Role` на плате, **не** refdes — одна и та же
  роль каждый раз может резолвиться в другой реальный компонент), локальный сдвиг+угол, свои `vias:`
  (та же форма, вложенная под компонент), опциональный `layer:` (только когда отличается от слоя самой
  ячейки — например, компонент на обратной стороне в остальном верхнеслойной ячейки), и `net_template:`
  (используется только матчингом ролей по сетям у `clone_placements:` — см. ниже; `chains:`/ManualSpoke
  игнорирует его полностью, матчит роли чисто по `(chain.net, Role)`).
  Опциональный `net_template_pad:` (2026-08-16) — осмыслен только вместе с `net_template:`: на каком
  паде резолвленного кандидата лежит цепь этой роли, для ролей, у реального компонента которых БОЛЬШЕ
  одной не-rule цепи (регулятор/диод/дроссель — LDO VIN/VOUT и т.п.). Без него кнопка «Auto-fill from
  board» в Placer требует у кандидата ровно одну не-rule цепь целиком и пропускает многопадовые роли;
  с ним читается напрямую конкретный пад, детерминированно. На резолвер «по сетям» при apply он НЕ
  влияет (тот уже ищет по заранее известной ожидаемой цепи — число падов ему неважно), и фатально
  при загрузке, если задан без `net_template:` (зеркально проверке
  `net_from_role_pad`-без-`net_from_role` у via/треков).
  Опциональный `net_template_same_as_role:` (2026-08-16) — более безопасная АЛЬТЕРНАТИВА
  `net_template_pad:` (взаимоисключающе с ним, фатально при обоих): называет ДРУГУЮ роль ЭТОЙ же
  ячейки, чья резолвленная цепь (лемма-2-безопасно, ровно одна не-rule цепь) электрически
  ИДЕНТИЧНА цепи этой роли. Электрическая топология (какие цепи — один узел) гарантированно
  переживает клонирование; номер пада — нет: найдено живьём 2026-08-16 — идентифицирующая цепь
  R/C лежала на паде 2 в одном разведённом инстансе и на паде 1 в другом (геометрия идентична,
  проверено — не поворот/зеркало), молча неверно для 3 из 13 ролей. Предпочитайте
  `net_template_same_as_role`, когда lemma-2-сосед есть; экстрактор пишет его автоматически, если
  сосед доступен в той же выборке. Для деталей с фиксированным пиноутом (ИС/диоды/полярные
  конденсаторы) безопасен и `net_template_pad:` — он и продолжает использоваться.
- `tracks:` — только прямые сегменты (без дуг); полилиния — просто несколько идущих подряд записей
  `tracks:` с общей конечной точкой. Пересечения с существующей медью этим инструментом **не**
  проверяются — источник истины тут собственный DRC KiCad, сознательно (см. [docs/geometry_ru.md](geometry_ru.md)).
- `layer:` на самом верхнем уровне ячейки — слой, на котором она была снята; компоненты/треки без
  своего `layer:` наследуют его.
- `anchor_xy:` **или** `anchor_role:` (`+anchor_pad:`) — добавлено 2026-08-06 для редактора ячеек в
  GUI (`CellDock`), **чисто для отображения**: отмечает, какая точка уже И ЕСТЬ локальный `(0,0)`
  ячейки по построению (`offset_along_mm`/`offset_across_mm` = `0.0` — это и есть начало координат,
  независимо от этого поля) — резолвером (`clone_position_calculator.py`) никогда не читается, нужно
  только чтобы человек (или сам редактор) видел, к чему привязывался исходный экстрактор, вместо
  неотслеживаемого факта. Взаимоисключающе; `anchor_role` обязан называть один из `components:` этой
  же ячейки.
- `comment:` — опциональная свободная заметка, видна в редакторе ячеек GUI и маркером на листе
  дерева конфига. Обычное поле схемы (переживает YAML/s-expr round-trip), НЕ YAML-комментарий `#`.
- Каждая запись `components:` **обязана** иметь непустой `role:` — раньше отсутствующий/`null` role
  либо падал голым `KeyError`, либо тихо протаскивался до плейсмента и всплывал невнятной рантайм-
  ошибкой «role None is in cell but not found anywhere on board»; теперь — понятная ошибка загрузки
  (баг найден живьём 2026-08-06).

### Композитная ячейка (рекурсивная, с 2026-07-31)

```yaml
# Cell, содержимое которой — другие cell, а не сырая геометрия
p3v3_ldo_composite:
  clone_placements:
    - name: ldo_reg
      cell: p3v3_ldo        # лист-ячейка выше
      xy: [0.0, 0.0]        # относительно (0,0) САМОГО композита — см. примечание про xy: ниже
      nets:
        LDO_1V2: '+3V3_DIRTY'
      params:
        PWR_IN: '+5V'
        PWR_OUT: '+3V3_DIRTY'
    - name: led_spoke
      cell: led_spoke
      xy: [-2.0, 5.0]
      params:
        PWR_IN: '+3V3'
        PWR_OUT: '/Power/+3V3_LED'
```

Каждая вложенная запись — это `CellPlacement`, **не тот же тип**, что top-level запись
`clone_placements:` (`ClonePlacement`). Он сознательно уже: **закрытая граница**, вообще без
`anchor_ref`/`anchor_role`/`anchor_sheet`/`anchor_cluster`/`anchor_pad`/`by_selection`/
`ignore_selection` — они имеют смысл только для чего-то, привязанного к живой плате, а вложенное
размещение к ней никогда не привязано напрямую. Поля: `name` (обязательно — используется для сборки
собственного ключа этого вложенного элемента в реестре), `cell:` **или** `role:` (тот же смысл, что
`ClonePlacement.cell`/`role`, взаимоисключающие), `xy:`, `rotation_deg:`, `mirror:`, `layer:`, `sheet:`,
`cluster:` (добавлено 2026-08-26 — СОБСТВЕННАЯ идентичность размещения для УЗКОВАНИЯ РОЛЕЙ ВНУТРИ
целла, тот же смысл, что `ClonePlacement.sheet`/`cluster` ниже: когда роль на общей шине (например,
`+3V3` у PI-фильтра) имеет несколько одинаковых физических экземпляров на плате, эти поля сужают их
точно так же, как у top-level `ClonePlacement`; это НЕ внешние якоря — `anchor_*` сознательно
отсутствуют, позиция по-прежнему берётся от родителя). `sheet:` при отсутствии значения
(`null`/не задан) НАСЛЕДУЕТСЯ от охватывающего размещения (top-level `ClonePlacement` на один
уровень выше) и цепочкой через сколь угодно глубокую вложенность (2026-08-26) — поэтому
переиспользуемый композитный целл (одно определение `dac_buf`, клонируемое в `CH0_DAC_BUF`/
`CH1_DAC_BUF`) резолвится по-канально, без зашивания канала во вложенные записи. Задавать явно
стоит только когда вложенное размещение реально живёт на другом листе, чем родитель. `nets:`/
`params:` могут использовать плейсхолдер `{sheet}` в иерархическом пути сети (например,
`/{sheet}/DAC/+3V3_DVDD`) — в момент apply он резолвится в ЭФФЕКТИВНЫЙ sheet этого вложенного
размещения (унаследованный или явный), который инжектится в его собственные `params["sheet"]`
(см. `clone_position_calculator.py::_resolve_one_level`; явный `params["sheet"]` побеждает). Тот
же движок `{placeholder}`, что у `ClonePlacement.anchor_sheet` (`Channel_{channel}`).
`net_overrides:`, `refs:`
— без скоупинга параметров, вложенное размещение никогда не наследует `params`/`nets` от родителя,
та же конвенция, что уже есть у `ClonePlacement.params`.

Зеркалирование **композитной** ячейки (непустой `clone_placements:`) — фатальная ошибка, пока не
реализовано. Зеркалирование **листовой** ячейки работает как всегда.

Композитные ячейки также генерируются автоматически вкладкой **Sub-placements** дока Extract
(2026-08-25, см. [docs/gui_ru.md](gui_ru.md)): когда выделение целиком сметает уже существующее
top-level `clone_placement`, док пишет его ссылкой `clone_placements:` вместо плоского копирования
геометрии. С 2026-08-26 док также переносит `sheet:`/`cluster:` исходного размещения в новую
вложенную запись (собственная идентичность для узиования ролей внутри целла, см. выше) и
шаблонизирует буквальный сегмент `sheet` в скопированных `nets:`/`params:` в `{sheet}` — так что
свежеизвлечённый reusable-композит остаётся по-канальным, а не несёт путь исходного канала. Когда
все sub-placements одного экстракта на ОДНОМ листе, `sheet:` не пишется вообще ни на одном узле
(2026-08-26) — reusable-композит тогда берёт лист через наследование от будущего родителя,
вместо того чтобы навсегда зашить канал этого экстракта во вложенные записи.
Циклический граф ссылок (A → B → A) отклоняется и на загрузке, и — как последняя линия
обороны, для конфигов, собранных в памяти — самим резолвером (чистая `ValidationError` с полным
путём, а не Python `RecursionError`).

> **Читая `xy:` в чужом YAML — одно имя поля в трёх разных системах координат, полезно понимать, в
> какой именно:**
> 1. У `ClonePlacement` **с** якорем (`anchor_ref`/`anchor_role`/`anchor_point`) — плоский сдвиг **от
>    разрешённой позиции якоря**.
> 2. У `ClonePlacement` **без** якоря — **абсолютная** координата платы.
> 3. У `CellPlacement` (вложен в композитную `Cell`) — сдвиг от **локального (0,0) РОДИТЕЛЬСКОЙ
>    ячейки**, никогда не от платы и не от живого якоря.
>
> Правило везде одно («плоский сдвиг, без автоповорота»), но три разных начала отсчёта — прежде чем
> доверять голому числу `xy:`, проверь, есть ли рядом поле `anchor_*`, и находишься ли ты внутри
> определения `Cell` или в top-level `clone_placements:`.

## `chains:` — ManualSpoke (радиальная развязка вокруг одной ИС)

> **Переименование (2026-09-01, план rules_to_chains):** секция `chains:` переименована в `chains:`
> (класс `Chain` → `Chain`). Старый ключ `chains:` по-прежнему ЧИТАЕТСЯ как алиас; новый код пишет
> `chains:`. Перевести существующий профиль на новый ключ можно
> [`tools/convert_rules_to_chains.py`](../tools/convert_rules_to_chains.py).

Самый старый механизм: группа спиц (небольших ячеек, обычно пары декап-конденсаторов), расставленных
радиально вокруг конкретных падов **одного** якорного компонента, забирающих реальные компоненты из
пула по `(net, Role)` — не привязано к конкретному refdes, переживает реаннотацию. **Не** поддерживает
треки между спицами на разных падах (каждая спица самодостаточна).

> **Два `chains:` на одной сети, потребляющие один и тот же пул `(role, cluster)` — фатал
> валидации** (2026-08-20): пул строится заново на каждое цепейо без владения/дистанции, поэтому
> какое цепейо выполнится позже, то молча заберёт компоненты, предназначенные соседу (больше всего
> это заметно при Redraw одной спицы). Исправление: задайте спицам одного из них различающий
> `cluster:`, чтобы каждое цепейо брало компоненты из своего пула.

```yaml
# boards/3ch-awg-tia/profiles/rules/fpga_spokes.sexp
chains:
- net: +3V3_VCCIO
  name: +3V3_VCCIO       # опционально — по умолчанию берётся net, см. ниже
  anchor_role: FPGA
  retired: false
  skip: false
  spokes:
  - pad: '17'
    cell: fpga_cap_pair_spoke
    shift_x_mm: 1.2
    shift_y_mm: -0.5
    rotation_deg: 90.0
    cluster: FPGA_PWR_BANK
  - pad: '26'
    cell: fpga_cap_pair_spoke
    shift_x_mm: 1.2
    shift_y_mm: -2.4
    rotation_deg: 90.0
    cluster: FPGA_PWR_BANK
```

**Поля `Chain`:**

| Поле | Смысл |
|---|---|
| `net` | Обязательно. Цепь, по которой резолвятся компоненты/via каждой спицы (поиск в пуле — `(net, Role)`). |
| `anchor_ref` **или** `anchor_role` (`+anchor_sheet`/`anchor_cluster`) **или** `anchor_point` | Ровно один — якорный компонент, к падам которого крепятся спицы. |
| `name` | Опционально, для `--only`. По умолчанию — `net` (см. `chain_effective_name`). **Не** механизм группировки — не переиспользуй один `name:` в нескольких цепих, чтобы объединить их для `--only`, используй общий `Cluster` (`anchor_cluster`/`spoke.cluster`). Если два цепи резолвятся в одно и то же эффективное имя — фатал при загрузке. |
| `retired` | По умолчанию `false`. `true` = «не существует на плате» — вычищает via/треки этого цепи из реестра. Всегда побеждает `--only`/`--cluster`. |
| `skip` | По умолчанию `false`. `true` = «не трогать в этом прогоне» — сужает работу как `--only`/`--cluster`, но инлайново, без защиты/вычистки реестра в любую сторону. |
| `comment` | Опционально. Свободная заметка, видна в GUI — обычное поле схемы, не YAML-комментарий. |

**Поля `ManualSpoke` (одна запись `spokes:`):**

| Поле | Смысл |
|---|---|
| `pad` | Обязательно. К какому паду якоря цепи крепится эта спица (строка, как в KiCad — `'17'`, не `17`). |
| `cell` | Обязательно. `Cell` (должна быть листом), которую размещает эта спица. |
| `shift_x_mm`/`shift_y_mm` | Сдвиг в мм в абсолютных координатах платы от центра пада к собственному началу координат спицы (не локальный/не повёрнутый — подбирается визуально для каждой спицы). |
| `rotation_deg` | Поворот итогового начала координат и всего содержимого ячейки. |
| `cluster` | Опционально — сужает, к какой физической записи пула резолвится роль, когда одной комбинации net+Role недостаточно. |
| `retired`/`skip` | Тот же смысл, что у `Chain`, но в рамках только этой спицы. |

## `clone_placements:` — ClonePlacement (TemplatePlacer)

> **Миграция (2026-08-30):** `clone_placements:` — это ЛЕГАСИ-путь размещений, живёт ещё во время
> миграции, чтобы живые профили продолжали работать. Новые профили используют `entities:` + `trees:`
> (см. ниже); [`tools/convert_placements.py`](../tools/convert_placements.py) конвертирует легаси-профиль
> (запускать на КОПИИ — сначала создаётся `.bak` с датой-временем).

Применяет `Cell` в новом месте — в отличие от `chains:` (якорь всегда пад ИС), якорь тут — просто имя
(`anchor_id` в реестре — `f"name:{name}"`), так что это механизм и для повторяющихся многокомпонентных
секций (pi-фильтры, DAC-каналы, LDO-подсистемы), и для одноразовых.

```yaml
# boards/3ch-awg-tia/profiles/fpga.sexp
clone_placements:
  - name: p3v3_vccio_pi_filter
    retired: false
    skip: false
    cell: fpga_in_pi_filter
    anchor_cluster: Pi_Filter_3V3_VCCIO
    anchor_role: FPGA
    anchor_pad: '139'
    xy: [-6.0, -6.0]
    params:
      PWR_IN: '+3V3'
      PWR_OUT: '+3V3_VCCIO'
```

**Позиционирование — два режима:**
- **С якорем** (задан `anchor_ref`/`anchor_role`(+`anchor_sheet`+`anchor_cluster`)/`anchor_point`) —
  начало координат = центр `anchor_pad`, если задан, иначе центр якорного футпринта, или собственная
  позиция резолвнутой `Point` для `anchor_point`. `xy:` тогда — плоский сдвиг от этого (без
  автоповорота — см. примечание про `xy:` выше), `rotation_deg` поворачивает только содержимое ячейки.
- **Абсолютный** (якорное поле вообще не задано) — `xy:` обязателен, буквальная координата платы.

**Роль → реальный компонент — три режима:**
- **По сетям** (повторяющиеся секции — pi-фильтры, DAC-каналы), когда заданы `params`/`nets`, ИЛИ
  с Фазы 2, шаг 2.3 — когда неявный режим (без `params`/`nets`/`by_selection`) может авто-вывести
  весь целл на живой плате: каждая
  роль внутри ячейки резолвится против реальной цепи через `nets:` (буквальное `role: net`) и/или
  `params:` (заполняет `{placeholder}` в собственных `net_template:`-полях ячейки, тот же механизм
  подстановки, что у `net:` у via/треков). С Фазы 2, шаг 2.1 это ОПЦИОНАЛЬНЫЕ override-ы: роль без
  явной цепи авто-выводит ожидаемую цепь с живой платы (`derive_role_nets` — единственная цепь
  уникального инстанса, либо единственная не-rule-цепь, общая для всех кандидатов), а ЛИТЕРАЛЬНАЯ
  локальная `/Channel_0/...` в `net_template` префикс-ремапится на целевой канал (семантика
  `TwinMap.twin_net`). Неоднозначные кандидаты (2+ матчащих на резолвленную цепь)
  сужаются каскадом собственный `sheet` этого размещения → его собственный `Cluster` (его `name:` —
  НЕ `anchor_sheet`/`anchor_cluster`, те сужают только якорь, см. «С якорем» выше) → текущее
  выделение на плате → физическая близость к якорю → фатал, в этом порядке — точный каскад см. в
  докстрингах `clone_role_resolver.py`.
- **По выделению** (редкие, одноразовые секции — одна MCU): явно с `by_selection: true` (нужно,
  когда `params` присутствует только ради резолва цепей via/треков и иначе был бы ошибочно принят
  за режим «по сетям»), либо — для неявного случая без `params`/`nets` — только когда целл НЕ может
  авто-вывестись на живой плате (Фаза 2, шаг 2.3: настоящая одноразовая секция без однозначного
  инстанса-источника). Роли резолвятся против того, что сейчас выделено на живой плате в
  PCB-редакторе.
- **По тегу Cluster** (только одиночный компонент — задан `cluster:`, добавлено 2026-08-06):
  ЕДИНСТВЕННЫЙ компонент, уже помеченный этим полем Cluster (проставлен заранее — например, через
  дерево компонентов в GUI или fieldstool) — без выделения, без сетей, без каскада сужения. Ноль или
  больше одного совпадения — фатал (Cluster задуман уникальным на экземпляр, в отличие от Role —
  разделяемой категории). `nets`/`params`/`by_selection` тут бессмысленны и фатальны, если заданы
  вместе с `cluster`.

**Полный справочник полей:**

| Поле | Смысл |
|---|---|
| `name` | Обязательно — фолбэк-идентичность в реестре, цель для `--only`, фигурирует в каждом диагностическом сообщении. |
| `sheet` | Опционально. Собственный лист — сужает неоднозначные Cluster+Role ВНУТРИ целла, когда этот целл клонируется между переиспользуемыми листами (переиспользуемый иерархический лист клонирует ОДИНАКОВЫЕ пользовательские поля на каждый экземпляр, так что различить две физические копии может только лист — например, одна секция PI-фильтра на канал). НЕ `anchor_sheet` — тот сужает только поиск внешнего якоря (см. `anchor_role` выше). Распил 2026-08-15 из `anchor_sheet`, завершающий распил `anchor_cluster` от 2026-08-14 — та же конвенция (Sheet, Cluster, Role). С 2026-08-16 GUI-сужение Auto-fill/Nets/Params (PlacerDock) тоже питается этим же `sheet` при живом поиске кандидата — неоднозначность Cluster+Role на переиспользуемом листе сужается в GUI так же, как на apply-времени. |
| `xy` | Обязательно. См. режимы «с якорем»/«абсолютный» выше и примечание про `xy:`. |
| `cell` **или** `role` **или** `cluster` | Ровно один. `cell:` — ссылка на `cells:` (инлайн или через `include:`). `role:`/`cluster:` оба синтезируют временную одно-компонентную ячейку на лету (для размещения, не стоящего отдельного файла ячейки) — `role:` матчит живое поле Role (категория, неоднозначность сужается), `cluster:` матчит уже проставленное поле Cluster напрямую (задуман уже уникальным, сужение не нужно). |
| `rotation_deg` | По умолчанию `0.0`. Поворачивает содержимое ячейки (режим с якорем) или всё целиком (абсолютный режим). |
| `anchor_ref` / `anchor_role`(+`anchor_sheet`+`anchor_cluster`) / `anchor_point` | Опционально, взаимоисключающие — см. **Позиционирование** выше. |
| `anchor_pad` | Опционально, имеет смысл только с заданным якорем — сужает якорь до конкретного пада вместо центра футпринта. |
| `nets` | ОПЦИОНАЛЬНО (Фаза 2, шаг 2.1): `{role: буквальная_цепь}` — явный маппинг ролей по сетям; при отсутствии ожидаемая цепь роли авто-выводится с живой платы. |
| `params` | `{placeholder: значение}` — заполняет `{placeholder}` в `net_template:`/via/track полях `net:` ячейки; само наличие (даже с пустым `nets`) выбирает режим «по сетям», если не задан `by_selection: true`. |
| `net_overrides` | ОПЦИОНАЛЬНО (Фаза 2, шаг 2.1): `{резолвленная_цепь: замена}` — финальная строковая подмена после остального резолва цепей, для случаев, которые система плейсхолдеров не может выразить напрямую. |
| `refs` | `{role: refdes}` — явное переопределение, минуя поиск по цепям целиком; последний довод, когда кандидаты электрически неразличимы. |
| `retired` / `skip` | Тот же принцип, что у `Chain` — см. выше. `retired` всегда побеждает `--only`/`--cluster`. |
| `by_selection` | По умолчанию `false`. Принудительно включает режим по выделению, даже когда есть `params`/`nets`. |
| `ignore_selection` | По умолчанию `false`. Поэлементный аналог `--no-selection` из CLI: считает живое выделение в GUI пустым для СОБСТВЕННОГО резолва ЭТОГО размещения, независимо от глобального флага — ИЛИ-композиция с ним. |
| `layer` | `F.Cu`\|`B.Cu`\|не задан (наследовать слой ячейки, разместить как есть). |
| `mirror` | По умолчанию `false`. Зеркалирует всю конструкцию — противоречие с `layer` (mirror без смены слоя, или наоборот) — фатальная ошибка при загрузке, поскольку физически бессмысленно. |
| `comment` | Опционально. Свободная заметка, видна в GUI — обычное поле схемы, не YAML-комментарий. |

**Устарело, фатал при загрузке:** `origin_x_mm`/`origin_y_mm` (переименованы в `xy: [x, y]`), `side`
(заменён на явные `layer:`+`mirror:`).

## `entities:` — «что» размещения, без позиции

С 2026-08-30 семейство бывш. `clone_placements:` делится на ДВА понятия (действующая грамматика:
[`techdocs/handoff/deepseek/design_2026_08_30_entity_placement_grammar.md`](../techdocs/handoff/deepseek/design_2026_08_30_entity_placement_grammar.md)):

1. **`Entity`** (эта секция) — всё о вещи, КРОМЕ того, где она стоит: `cell` (форма),
   `nets`/`params`/`net_overrides` (электрика) и идентичность инстанцирования
   (`cluster`/`sheet`/`retired`/`skip`/`ignore_selection`/`by_selection`/`refs`/`layer`/`mirror`/
   `comment`). **Поля позиции (`xy`/`anchor_*`/`rotation`) у Entity запрещены — фатал при загрузке,
   а не молчаливое игнорирование.**
2. **Размещение = узел `trees:`** — см. **`trees:`** ниже. `node.ref` для `kind "placement"` резолвится
   в `Entity.name`; позиция узла (`xy`/polar/`rotation`) — это то, где стоит Entity.

То есть «Entity, на которую не ссылается ни один узел дерева» — это легальная, явно *не размещённая*
сущность.

```sexp
(entities
  (entity
    (name "DAC_BUF_CH0")                    ; ОБЯЗАТЕЛЬНО — уникально во всём include-графе;
                                            ;   идентичность для --only / реестра
    (cell "dac_buf")                        ; ОБЯЗАТЕЛЬНО — ссылка на cells:
    (nets (ROLE1 "NET1") (ROLE2 "NET2"))    ; опц. role -> net
    (params ("{PH}" "value"))               ; опц. значения {placeholder}
    (net_overrides (ROLE "NET"))            ; опц. финальное переименование
    (cluster "CH0")                         ; тег Cluster, пишется на плату при Apply
    (sheet "Channel_0")                     ; опц. — собственная идентичность для сужения ролей
    (retired true) (skip true) (ignore_selection true) ; опц., по умолчанию false
    (by_selection true)                     ; опц. per-instance резолв по выделению
    (refs (ROLE "R1"))                      ; опц. per-instance role -> ref
    (layer "F.Cu")                          ; опц.; mirror — только вместе со сменой слоя
    (mirror true)
    (comment "note")))
```

| Поле | Смысл |
|---|---|
| `name` | ОБЯЗАТЕЛЬНО — уникально во всём include-графе; идентичность для `--only`/реестра (заменяет эффективное имя `ClonePlacement`). |
| `cell` | ОБЯЗАТЕЛЬНО — ссылка на `cells:` (форма для размещения). |
| `nets` | Опц. `{role: буквальная_цепь}` — тот же маппинг ролей по сетям, что и `ClonePlacement.nets`. |
| `params` | Опц. `{placeholder: значение}` — заполняет `{placeholder}` в `net_template:`/via/track полях `net:` ячейки. |
| `net_overrides` | Опц. `{резолвленная_цепь: замена}` — финальная подмена после остального резолва цепей. |
| `cluster` | Опц. (в отличие от `ClonePlacement`) — тег Cluster, пишется на плату при Apply; entity может существовать «не размещённой» (без узла дерева) и без тега. |
| `sheet` | Опц. собственный лист — сужает неоднозначные Cluster+Role внутри ячейки между переиспользуемыми листами. |
| `retired` / `skip` | Опц., по умолчанию `false` — та же конвенция, что у `Chain`. |
| `ignore_selection` | Опц., по умолчанию `false` — поэлементный аналог `--no-selection`. |
| `by_selection` | Опц., по умолчанию `false` — per-instance резолв ролей по выделению. |
| `refs` | Опц. `{role: refdes}` — per-instance явное переопределение, минуя поиск по цепям. |
| `layer` / `mirror` | Опц. — та же перекрёстная проверка, что у `ClonePlacement` (mirror без смены слоя, или наоборот — фатал при загрузке). |
| `comment` | Опц. свободная заметка, видна в GUI. |

## `trees:` — ЕДИНСТВЕННОЕ место, где может жить позиция

С 2026-08-30 секция `trees:`, которую редактирует TreesDock, — это также **хранилище размещений**
для entity: узел с `kind "placement"`, чей `ref` — это `Entity.name`, И ЕСТЬ размещение этой entity —
«где стоит» = `позиция родителя + офсет узла`, ровно семантика `node_position`
(`kicadstamp/tree_position.py`). Отдельной секции `placements:` НЕТ.

```sexp
(tree (name "dac_buf_ch0")
  (anchor (origin))                            ; абсолют, или:
  ; (anchor (ref "CONN_PM5V"))                 ;   по refdes (external = только живая плата)
  ; (anchor (role "FPGA") (sheet "...") (cluster "...") (pad "A1"))
  ; (anchor (point "P1"))
  (node (ref "DAC_BUF_CH0") (kind placement) (xy 10.0 20.0) (rotation 90.0)
        (children ...)))                       ; вложенные узлы образуют жёсткую группу
```

- `kind "clone"` переименован в `kind "placement"`; при загрузке `"clone"` по-прежнему принимается как
  алиас `"placement"` на время миграции. Виды узлов `chain`/`coordinate`/`point`/`external` не меняются.
- `node.ref` для `kind "placement"` резолвится в `Entity.name`, а не в старый список `clone_placements:`.
- Плоское одиночное размещение = дерево с одним узлом под `(anchor (origin))` или
  компонентным/точечным якорем.
- Правило «один ref не более чем в одном узле» означает, что Entity всегда 1:1 со своим узлом дерева —
  Entity не может стоять в двух местах.

**`(anchor (ref ...))` может указывать на Entity** — тогда дерево якорится на placement-узле ДРУГОГО
дерева (перекрёстный entity-анкор, «живая» фаза 4.1). Поскольку у Entity нет собственной позиции,
такая база якоря резолвится РЕКУРСИВНО при материализации: найти (единственное) дерево, чей узел
`kind "placement"` ссылается на эту Entity, разрешить ЕГО базу якоря (origin/ref/role/снова ref на
Entity — рекурсия), затем применить поверх офсет найденного узла. Рекурсия защищена от циклов;
Entity без узла размещения, размещённая более чем в одном узле или цепочка, замыкающаяся сама на
себя, — это КОНФИГ-ОШИБКА (фатал, никогда не пропускается молча).

**Встраивание деревьев через модуль (2026-09-02, plan_2026_09_02_tree_module_embedding.md):** узел
`trees:` может также иметь `kind "module"` — его `ref` — это ИМЯ ДРУГОГО дерева, которое встраивается
как жёсткий суб-лейаут (например, дерево `fpga` встраивает дерево `ch0_dac_buf`). Собственные
`xy`/`polar`/`rotation` module-узла задают положение его МАРКЕРА в родителе; опциональные
`(pivot-xy x y)` или `(pivot-polar r a)` (взаимоисключающие, только для module) говорят, какая точка
ВНУТРИ собственной локальной системы координат referenced-дерева должна лечь ровно на маркер (если
нет — origin referenced-дерева). Module-ref — это имя дерева, НЕ конфиг-запись — он исключён из
файлового правила «один ref не более чем в одном узле», поэтому ОДНО дерево-ребёнок можно встраивать
в РАЗНЫХ родителей; дубль ВНУТРИ одного родителя, неизвестный/сам-себя ref и цикл модулей (A⊃B⊃A) —
конфиг-фаталы (проверяются на link/Save). При встраивании собственный якорь referenced-дерева
ИГНОРИРУЕТСЯ — его контент раскладывается от pivot-инвертированного маркера (чистая геометрия,
применяется как неперсистентный override позиции в полной перерисовке).

## `tree_instances:` — одно дерево-шаблон, инстанцируется по листам схемы (2026-09-02)

`Channel_1/2` у `DAC_BUF` — та же геометрия, что у `Channel_0`: те же cells/clusters/roles,
отличаются ТОЛЬКО листом схемы (`Channel_1`/`Channel_2`). Копировать-вставлять всё дерево и его
записи `entities:` N раз — значит молчаливый дрейф при первом же изменении геометрии.
`tree_instances:` объявляет дерево ОДИН раз — обычная запись `trees:` плюс её Entity-записи (с
СВОИМ реальным `sheet`/`anchor sheet`, чтобы шаблон оставался «живым» и перечитывался с платы по
Role+Sheet+Cluster) — и инстанцирует его на каждый повтор:

```yaml
tree_instances:
  - template: dac_buf_tpl        # имя существующей записи trees: (шаблон)
    name: ch1_dac_buf            # имя генерируемого дерева
    sheet: Channel_1             # подставляется в генерируемые копии
```

Расширение выполняется внутри `load_config()`, сразу после `include:` + `sheet_templates:` и до
любого per-entry загрузчика: каждая декларация материализует ПОЛНОЕ дерево (глубокая копия шаблона —
у каждого узла `ref` получает суффикс `__{instance.name}` рекурсивно, `sheet` role-якоря становится
листом экземпляра) плюс по одной Entity на `placement`-узел шаблона (глубокая копия, переименованная
в новый ref, `sheet` = лист экземпляра) и по одной записи `net_traces:` на `net_trace`-узел (см.
ниже). Материализованные записи обычны для всех потребителей (embedding/redraw/apply) и проходят ТЕ
ЖЕ `_load_tree`/`_load_entity`/`_load_net_trace`, duplicate-name, один-рекорд-на-net, rule-2 и
layer/mirror проверки, что и рукописные — ничего не валидируется дважды.

- **Это НЕ отдельный файловый формат:** `tree_instances:` живёт ТОЛЬКО в основном (dict) конфиге
  (НЕ в s-expr-формате `*.trees` — там вообще нет Entity-записей). Это обычная секция-список,
  мержится через `include:`.
- **Шаблон остаётся редактируемым и «живым» (обычное дерево):** его Entity-записи СОХРАНЯЮТ свой
  собственный `sheet` — он нужен для живого перечитывания по Role+Sheet+Cluster (Q2, пересмотрен
  2026-09-02), — а СГЕНЕРИРОВАННАЯ копия безусловно получает `sheet` экземпляра. Расширение только
  делает `deepcopy`; шаблон и файл на диске никогда не мутируются.
- **Ограничения v1.1 (каждое — фатал при загрузке):** якорь шаблона обязан быть `role`; каждый узел
  шаблона — `kind "placement"` (или без kind/auto) и обязан ссылаться на существующую запись
  `entities:`, ЛИБО `kind "net_trace"` и ссылаться на существующую запись `net_traces:` по имени
  сети. (Узлы chain/coordinate/clone/module внутри шаблона по-прежнему не поддерживаются.)
- **Узлы net_trace внутри шаблона (v1.1):** `ref` узла `kind "net_trace"` — это реальная сеть платы
  (например `/Channel_0/DAC/+3V3_AVDD`), которая обязана остаться валидным именем сети для
  планировщика/KiCad — поэтому она НЕ суффиксируется `__{instance.name}`, как placement-ref. Вместо
  этого ВЕДУЩИЙ СЕГМЕНТ (лист) сети заменяется на `sheet` экземпляра (`/Channel_1/DAC/+3V3_AVDD`) —
  независимо в `net` самой записи, в каждом `tracks[].net` и каждом `vias[].net`; `anchor_sheet`
  сгенерированной копии `net_traces:` безусловно выставляется в `sheet` экземпляра. Старый лист
  берётся из `sheet` role-якоря шаблонного дерева — сеть, чей ведущий сегмент не совпадает с ним,
  даёт фатал (это не медь данного шаблона), никогда не переписывается молча. Разные по листу сети
  экземпляров бесплатно проходят существующую проверку «один рекорд на net».
- **Сгенерированные экземпляры никогда не персистятся** как литеральные записи `trees:`: Save в
  TreesDock пишет только рукописные деревья, а нетронутая секция `tree_instances:` регенерирует
  экземпляры при каждой загрузке — без дублей. Геометрия экземпляра правится через шаблон (в доке
  Trees) и через `name`/`sheet` декларации (Tools → **Instances…**, см. GUI-доки).
- `name` обязан быть уникальным среди ВСЕХ деревьев (коллизия — с рукописным деревом или другим
  экземпляром — это обычный duplicate-name фатал при загрузке).

## `sheet_templates:` — объявить группу один раз, инстанцировать по листам

`Channel_0/1/2` — три инстанса одного и того же переиспользуемого листа (DAC + OpAmp):
Cluster/Role-метки ОДИНАКОВЫ на всех инстансах (fieldstool тегирует файл листа, а не конкретный
инстанс), различает их только `sheet:`/`anchor_sheet:`. Вместо копипасты одних и тех же записей
`clone_placements:`/`coordinate_placements:` N раз — N независимых списков, которые молча
рассинхронизируются при любом изменении Channel_0 — объявляем один раз и даём `load_config()`
размножить по листам:

```yaml
sheet_templates:
  channel:
    sheets: [Channel_0, Channel_1, Channel_2]
    coordinate_placements:
    - cluster: OP_AMP
      role: OP_AMP
      # name: генерируется автоматически на лист (см. «Идентичность» ниже)
      sheet: self
      x_mm: 9.0
      y_mm: 0.0
      rotation_deg: 270.0
      anchor_role: AD_DAC
      anchor_sheet: self
    clone_placements:
    - name: PIF_AVDD          # Cluster-тег — expansion его НЕ трогает никогда
      cell: dac_pi_filter
      sheet: self
      xy: [2.0, 1.0]
      rotation_deg: 90.0
      anchor_role: AD_DAC
      anchor_pad: '18'
      anchor_cluster: AD_DAC
      anchor_sheet: self
      params:
        FB_PI_FLT: /$SHEET/DAC/+3V3_AVDD
```

Expansion выполняется внутри `load_config()`, сразу после разрешения `include:` и до любого
поэлементного загрузчика — к моменту, когда `_load_clone_placement`/`_load_coordinate_placement`
и проверки дубликатов имён видят данные, сгенерированные записи неотличимы от написанных руками.

**Зарезервированные подстановки, ТОЛЬКО внутри блоков `sheet_templates:` (нигде больше в схеме):**
- `sheet: self` / `anchor_sheet: self` → буквальное имя генерируемого листа (`Channel_0`/`Channel_1`/...).
  Намеренно НЕ автозаполняется пропущенный `anchor_sheet:` — запись `anchor_role: FPGA` не должна
  получать `anchor_sheet:`, которого не просила (FPGA — единственный, не-листовой инстанс);
  подставляется только явный `self`, отсутствующее поле остаётся отсутствующим.
- `$SHEET` внутри строковых значений (`params:`/`nets:`/`net_overrides:`) → та же подстановка,
  для иерархических путей сетей вида `/$SHEET/DAC/+3V3_AVDD`.

**Идентичность** (`placer_name:` у `clone_placements`, `name:` у `coordinate_placements` — НЕ
собственный `name:` у `clone_placements`, это Cluster-тег, его expansion не трогает никогда),
разводится по `len(sheets)`:
- `len(sheets) == 1` → identity берётся БУКВАЛЬНО из шаблона (или штатный дефолт,
  `{cluster}/{role}` для coordinate_placements) БЕЗ какого-либо префикса — именно это делает
  одно-листовую регрессию байт-в-байт нулевой.
- `len(sheets) >= 2` → identity генерируется ВСЕГДА как `{sheet}_{base}` (base — явно заданное
  значение, или тот же дефолт), ПЕРЕЗАПИСЫВАЯ то, что написано в шаблоне — уникальность на лист
  гарантируется структурно, поскольку проверка дубликатов имён смотрит на effective name, а тот
  `sheet` не учитывает.

`sheet_templates:` — dict-секция, поэтому мержится через `include:` так же, как `cells:`/`points:`
(фатал на дублирующееся имя шаблона в разных файлах — см. `include:` ниже).

## `thermal_via_arrays:` — термо-via-сетки

```yaml
# boards/3ch-awg-tia/profiles/fpga.sexp
thermal_via_arrays:
  - name: fpga_thermal
    retired: false
    skip: false
    anchor_role: FPGA
    pad: '145'
    net: GND
    rows: 4
    cols: 4
    margin_mm: 0.5
    pattern: grid
    drill_mm: 0.3
    diameter_mm: 0.5
```

Настоящий список (2026-08-02, обобщено, когда появилась вторая ИС с термо-via — AD9707, по одной на
канал) — та же форма, что `chains:`/`clone_placements:`: любое число записей, каждая со своим именем/
якорем/`retired`/`skip`, и каждая может жить в своём файле через `include:` (`thermal_via_arrays` —
объединяемая списочная секция, как `chains`/`clone_placements`). `name:` **обязателен** у каждой записи
(используется для `--only` и идентичности в реестре `f"thermal:{name}"`) и должен быть **уникален по
всему списку** (иначе фатал при загрузке — `--only` не сможет различить одноимённые записи).

| Поле | Смысл |
|---|---|
| `anchor_ref` / `anchor_role`(+`anchor_sheet`+`anchor_cluster`) / `anchor_point` | Ровно один — ИС, чья термо-площадка получает сетку. |
| `pad` | Какой пад якоря — термо-площадка (сетка центрируется на нём). |
| `net` | По умолчанию `GND`. |
| `rows`/`cols` | Размеры сетки. |
| `margin_mm` | Отступ от края пада до первой via. |
| `pattern` | `grid` или `staggered`. |
| `drill_mm`/`diameter_mm` | Размеры via. |
| `retired` | По умолчанию `false`. Тот же смысл «не существует», что и везде. |
| `skip` | По умолчанию `false`. Тот же смысл «не трогать в этом прогоне», что и везде. |
| `comment` | Опционально. Свободная заметка, видна в GUI — обычное поле схемы, не YAML-комментарий. |

**Устарело, фатал при загрузке:** старый одиночный `thermal_via_array:` (словарь, не список —
переименуй в `thermal_via_arrays:` и оберни блок в YAML-список), `target_ref` (переименован в
`anchor_ref`), старый `enabled:`
(переименован и обратен по смыслу `retired:` — `enabled: true` ≠ `retired: true`, не делай буквальный
find-and-replace в старом конфиге, перепроверь исходный смысл).

## `net_traces:` — медь одной сети, «следующая» за якорным падом

Ответ на «я вручную развёл шину FPGA↔DAC и не хочу заново разводить её каждый
раз, когда двигаю FPGA»: захватывает ВСЮ живую медь одной сети (дорожки +
переходные отверстия) как ЛОКАЛЬНЫЕ смещения от якорного пада, а затем
пересчитывает её ЖИВЬЁМ на каждом `apply`/Redraw из *текущей* позиции якоря —
сдвинь якорь в KiCad, запусти `apply --only=<net>` — и вся трассировка сети
последует за ним (старая медь удаляется реестром, новая создаётся на новой
позиции). Одна запись = ОДНА сеть (никаких списков сетей внутри записи —
списки в этом проекте живут в единственном месте, в спицах).

```yaml
# boards/3ch-awg-tia/profiles/net_traces.sexp  (подключить через include:)
net_traces:
  - net: DAC_DB0            # имя сети — оно же идентификатор для --only
    anchor_role: FPGA       # якорный футпринт по Role (поиск по всей плате)
    # anchor_sheet: ...     # опционально — сузить поиск Role по листу
    # anchor_cluster: ...   # опционально — сузить по Cluster (префиксное совпадение)
    # anchor_pad: '42'      # опционально — якорь на центр этого пада, а не футпринта
    tracks:
      - start_along_mm: 1.0
        start_across_mm: 2.0
        end_along_mm: 3.0
        end_across_mm: 4.0
        width_mm: 0.2
        net: DAC_DB0
        layer: F.Cu
    vias:
      - offset_along_mm: 5.0
        offset_across_mm: 6.0
        net: DAC_DB0
        drill_mm: 0.3
        diameter_mm: 0.6
    # retired: true   # «на плате сейчас не существует» (защита реестра снимается)
    # skip: true      # «пропустить только этот прогон» (защита реестра остаётся)
```

- **`net`** (обязательно) — имя сети. Уникально на запись (фатал при загрузке,
  если две записи на одну сеть). Локальные иерархические сети сохраняют полную
  форму `/Channel_0/...`.
- **`anchor_role`** (обязательно) — поле Role якорного футпринта, ищется по
  ВСЕЙ живой плате (не по выделению мышкой) и на этапе extract (origin), и на
  этапе apply (anchor) — тот же поиск `resolve_footprint_by_role`, что у
  Chain/ClonePlacement. Опциональные `anchor_sheet`/`anchor_cluster` сужают
  неоднозначность роли, опциональный `anchor_pad` переносит точку якоря с
  центра футпринта на центр конкретного пада.
- **`tracks`/`vias`** — медь как локальные (along/across) смещения от точки
  якоря — ровно та же форма `TemplateTrack`/`TemplateVia`, что в `cells:`.
  Сеть ВСЕГДА записана явно на каждом элементе (нет охватывающего Chain, из
  которого можно было бы унаследовать сеть).
- **`retired`/`skip`** — та же конвенция, что во всех секциях.
- **`comment`** — опциональная свободная заметка, видна в GUI (обычное поле
  схемы, не YAML-комментарий).
- **`--only=<net>`** выбирает ровно одну запись для Redraw; реестр даёт
  идемпотентность (повторный прогон с неподвижным якорем создаёт 0 новых
  объектов).

Извлечение — это CLI-команда, а не `extract` по выделению:
`kicadstamp_cli.py extract-net --net DAC_DB0 --anchor-role FPGA [--anchor-pad 42]
--output <config.sexp>` — добавляет/заменяет запись под `net_traces:`.

**Замечание по дизайну (см. `techdocs/handoff/deepseek/plan_2026_08_21_net_traces.md`):**
намеренно НЕ пара `Cell`+`ClonePlacement` — трассировка сети по построению
одноразовая (нет переиспользования на нескольких якорях), поэтому два слоя
косвенности были бы чистыми накладными расходами. Поля origin на extract и
anchor на apply — ОДИН И ТОТ ЖЕ набор, отсюда одна плоская запись.

## `points:` — именованные переиспользуемые якоря

```yaml
# boards/3ch-awg-tia/profiles/points.sexp
points:
  p3v3_ldo_origin:
    anchor_role: C_OUT_BYPASS
    anchor_cluster: In_Pi_Filter_Pos
    anchor_pad: '1'
```

Затем на неё ссылаются по имени из `Chain`/`ClonePlacement`/`ThermalViaArrayConfig`:

```yaml
clone_placements:
  - name: 3v3_ldo
    cell: p3v3_ldo
    anchor_point: p3v3_ldo_origin
    xy: [-50.0, 35.0]
```

`Point` резолвится один раз, кэшируется, и все, кто ссылается на неё через `anchor_point:`, получают ту
же резолвленную позицию — добавлено 2026-07-31 как настоящий узел графа зависимостей размещения (не
текстовая подстановка), так что порядок/свежесть в рамках прогона обрабатываются автоматически, так же
как любая другая якорная зависимость.

| Поле | Смысл |
|---|---|
| `name` | Ключ под `points:` — не отдельное поле, просто способ ссылки. |
| `anchor_ref` / `anchor_role`(+`anchor_sheet`+`anchor_cluster`) **или** `anchor_pad` | Живой якорь на плате, те же поля/резолв, что у `Chain`/`ClonePlacement`. |
| `anchor_point` | Цепочка к другой, уже определённой точке по имени — точки могут ссылаться друг на друга (цикл ловится тем же алгоритмом графа, что ловит любой другой якорный цикл). |
| `xy` | Буквальная, абсолютная координата платы — вообще без живого якоря. **(0, 0) здесь — угол листа чертежа, не какая-либо физическая точка платы** — для этого см. `anchor_origin` ниже. |
| `anchor_origin` | `'grid'` (Place > Set Grid Origin, чисто визуально — ни один экспортируемый файл на это не смотрит) или `'drill'` (Place > Drill/Place Origin, auxiliary axis — drill/position-файлы всегда считаются от неё, Gerber — опционально, через свою галочку в диалоге экспорта). Читается ЖИВЬЁМ через kipy, не литерал из конфига. |
| `shift_x_mm`/`shift_y_mm` | Сдвиг в мм в абсолютных координатах платы поверх `anchor_ref`/`anchor_role`/`anchor_point`/`anchor_origin` (не поверх `xy:` — фатал, если заданы оба, просто отредактируй буквальную координату). |
| `comment` | Опционально. Свободная заметка, видна в GUI — обычное поле схемы, не YAML-комментарий. |

Ровно одно из `{anchor_ref или anchor_role, anchor_point, xy, anchor_origin}` должно быть базой —
иначе фатал при загрузке. Собственный `anchor_point:` у `Chain`/`ThermalViaArrayConfig` требует, чтобы
указанная точка резолвилась в настоящий футпринт (без сдвига, не `xy:`-литерал, не на базе
`anchor_origin`, и не через цепочку, где есть что-то из этого) — им нужно найти конкретный пад по
номеру именно на нём; `ClonePlacement` нужна только координата, так что там подходит любая `Point`,
включая `anchor_origin`.

## `include:` — разбиение профиля на файлы

```yaml
# boards/3ch-awg-tia/profiles/power.sexp
include:
  - points.sexp
  - power_extracts.sexp
  - pn5v_filters.sexp
  - p3v3_ldo.sexp
```

Каждая запись — либо строка-путь, либо `{path: <строка>, enabled: <булево>}`, чтобы выключить целый
подключаемый файл, не удаляя и не закомментировав его.

- **Списочные секции** (`chains`, `clone_placements`, `thermal_via_arrays`) — конкатенируются: сначала
  записи этого файла, затем каждого подключённого, в порядке перечисления. (Реальный порядок размещения при `apply`
  решается отдельно, по настоящим якорным зависимостям, не по порядку в YAML — см.
  [docs/placement_ru.md](placement_ru.md).)
- **Словарные секции** (`cells`, `points`, `extract_profiles`, `clone_profiles`) — объединяются
  ключ-за-ключом, **фатал** при повторе ключа в двух разных файлах — подключаемые файлы задуманы как
  по-настоящему независимые подсистемы, так что повтор имени куда вероятнее ошибка копипаста, чем
  намеренное перекрытие.
- **Любой другой top-level ключ** (`layer:`, `schematic_dir:`, `registry_path:`,
  …) внутри *подключаемого* (не корневого) файла не имеет определённого цепи слияния между файлами
  и является **фатальной** ошибкой — перенеси его в корневой конфиг. (Раньше это тихо отбрасывалось —
  реальный, неоднократно встречавшийся класс багов на `boards/3ch-awg-tia`, теперь ловится при
  загрузке.)
- Циклы и diamond-инклюды (один и тот же файл достижим дважды) — оба фатальны.

`include:` общего назначения, используется и `load_config()` (`chains`/`clone_placements`/
`thermal_via_arrays`/`cells`/`points`), и собственным загрузчиком профилей CLI (`extract_profiles`/
`clone_profiles`), так что один файл подсистемы может нести смесь всего, что ему нужно — так же теперь
устроены и внешние файлы `Cell`: перечисли файл в `include:` и оберни его содержимое в ключ `cells:`
(`cells_file:`/`cell_files:`, отдельный механизм другой формы, были слиты в `include:` 2026-08-02 —
один способ разнести ЛЮБУЮ секцию по файлам вместо двух несовместимых).

## `extract_profiles:` / `clone_profiles:` — сохранённые аргументы `extract`/`clone-extract`

Не часть `Config`/`load_config()` — отдельный, только-CLI механизм (`kicadstamp_cli.py extract
--profiles ... --profile ...`) для сохранения повторяющихся вызовов `extract`/`clone-extract` как
именованных YAML-записей вместо перепечатывания длинных списков флагов. Полный разбор на уровне CLI —
[docs/commands_ru.md](commands_ru.md); синтаксис:

```yaml
# boards/3ch-awg-tia/profiles/power_extracts.sexp
extract_profiles:
  p5v_pi_filter:
    name: 5v_pi_filter
    output: boards/3ch-awg-tia/profiles/templates/power_pi_filters.sexp
    params:
      PWR_IN: '+5V_DIRTY'
      PWR_OUT: '+5V'
    net_template:
      '+5V_DIRTY': '{PWR_IN}'
      '+5V': '{PWR_OUT}'
```

Записи `extract_profiles:` принимают: `name`, `output`, `params`, `net_template`, `net_template_role`,
`rule_nets`, `origin_by_via_net`, `origin_by_component_role`, `origin_by_component_pad`,
`origin_by_component_cluster`, `origin_by_component_sheet` — неизвестные
ключи фатальны (опечатанный ключ, например `origin-by-via-net` с неверным разделителем, раньше тихо
игнорировался). `clone_profiles:` (для `clone-extract`) принимает: `net`, `pcb`, `channel`, `output`.

`params`/`net_template`/`net_template_role`/`rule_nets` — **ОПЦИОНАЛЬНЫЕ override-ы**
(Фаза 1/2, 2026-08-28): цепи via/треков резолвятся из ролей (`net_from_role`),
bridging-роли авто-выводят свой `net_template`, а `{param}`-паттерны каналов
обнаруживаются автоматически — эти ключи нужны только для редких ручных
исключений (soft-deprecate, сохранены ради обратной совместимости).

`rule_nets:` (2026-08-05, `--rule-net LITERAL`, повторяемый) — список литеральных имён нетов, для
которых у совпавшего via/track пишется `net: null` вместо литерала (или алиаса) — см. заметку про
`vias:` выше о том, что там значит `null`. Полезно только для целлы, которую планируется размещать
через **`chains:`**/ManualSpoke сразу в НЕСКОЛЬКИХ Chain с разными нетами (например, пара
развязывающих конденсаторов, переиспользуемая на разных силовых рейлах) — `net_template`/`params`
(`{PLACEHOLDER}`) это механизм для ДРУГОГО случая, переиспользования через `clone_placements:`, и для
`chains:`/ManualSpoke ничего не делает (у `ManualSpoke` вообще нет поля `params:`, против которого
можно было бы резолвить шаблон). Фатально, если один и тот же нет одновременно в `rule_nets:` и в
`params`/`net_template` — на каждый нет выбирается что-то одно.

`output:` можно задать один раз в корне файла как фолбэк для каждого профиля внутри, если все они
пишут в один и тот же файл ячеек — профилю, которому нужен другой, достаточно переопределить его
напрямую.
