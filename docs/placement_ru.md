# `kicadstamp/placement` – Планирование и исполнение расстановки

## Назначение

Директория `placement/` содержит основную логику расстановки компонентов, создания via и дорожек (треков). Она координирует все этапы процесса:

1. **Планирование** – расчёт целевых позиций компонентов, via и треков на основе шаблонов спиц для трёх типов размещений:
   - **`ManualSpoke`** (цепи `chains`) – привязка к падам целевого компонента (IC) с автоматическим подбором refdes через пул ролей (`ComponentPool`). Треки в этом режиме **не поддерживаются**.
   - **`ClonePlacement`** (клонируемые секции) – многократное применение шаблона (`cell:`, обязателен) в разных местах платы с разрешением ролей по выделению или по явным цепям (`CloneRoleResolver`). Поддерживает **треки** (дорожки) в составе шаблона.
   - **`CoordinatePlacement`** (`coordinate_placements`) – перемещение одного УЖЕ существующего футпринта (по точному совпадению Cluster+Role) в абсолютную позицию или относительно якоря другого компонента. Без шаблона, via/треков и без реестра — см. отдельный раздел ниже.
2. **Исполнение** – применение перемещений, создание via и треков на плате через адаптер KiCad, с разделением на **три фазы** (сначала перемещения, затем via, затем треки) и обязательным перечитыванием платы между фазами.
3. **Логирование и откат** – сохранение информации об операции в JSON для команды `undo` (включая треки).
4. **Проверка коллизий** – упрощённая проверка перекрытий компонентов (опционально); коллизии треков **не проверяются** (полагаемся на DRC KiCad).
5. **Идемпотентность** – пропуск уже существующих via, треков и компонентов, уже стоящих на целевых позициях (через `skip_existing_components` и реестры расстановки для via и треков). С 2026-08-31 позиционный пре-чек ТРЕКОВ (`filter_existing_tracks`, см. `kicadstamp/registry.py`) выполняется в Фазе 3 **безусловно** (не только под `skip_existing_components`): он только пропускает (skip-only, никогда не удаляет/не усыновляет чужую медь), поэтому повторный редрайв одной и той же ячейки через два разных механизма — например legacy `clone_placement` И Entity, материализованную деревом, — больше не накапливает буквальные дубликаты под разными registry-ключами.
6. **Усыновление владения при первом прогоне (БАГ 3, 2026-09-05)** – реестр — ЕДИНСТВЕННЫЙ источник владения медью; `reconcile()` удаляет строго по ключу, поэтому живая медь, не записанная в реестр под ключами текущего прогона, не может быть вычищена. Свежий / скопированный профиль (его `tracks/<stem>.tracks.registry.json` / `registry/<stem>.registry.json` пусты), указывающий на уже разведённую плату, оставлял старую медь осиротевшей при ПЕРВОЙ перестановке (дубль на новом месте + остатки на старом). Фикс: `adopt_matching_unowned` (см. `kicadstamp/registry.py`) выполняется ПЕРЕД каждым reconcile (Фаза 2 via / Фаза 3 треки) и записывает в реестр любой планируемый-но-незарегистрированный via/трек, уже лежащий РОВНО в планируемой позиции, — обобщение net_trace-специфичного `adopt_net_trace_copper`. Безопасно по построению (никогда не удаляет, не крадёт медь, принадлежащую другому ключу; только геометрически-тождественную), в стабильном состоянии — no-op. После первого redraw БЕЗ переезда медь регистрируется, и последующая перестановка переносит её (удалить старый UUID + создать новый), а не дублирует. GUI-перерисовка также предупреждает при пустом реестре и живой меди на плате («зарегистрировать существующую медь?»). Ограничение (принято): если ПЕРВЫМ действием является уже переезд, старая медь не совпадает ни с одной планируемой геометрией и не может быть усыновлена — сначала выполни один redraw без переезда (см. подсказку).

Все сервисы используют адаптер `kicad/adapter.py`, геометрические утилиты `geometry/` и пакет конфигурации `config/`.

## Entity и Placement (2026-08-30) — «что» vs. «где»

С 2026-08-30 семейство бывш. `ClonePlacement` делится на ДВА понятия (действующая грамматика:
`techdocs/handoff/deepseek/design_2026_08_30_entity_placement_grammar.md`):

1. **`Entity`** (секция конфига `entities:`) — всё о вещи, КРОМЕ того, где она стоит: `cell` (форма),
   `nets`/`params`/`net_overrides` (электрика) и идентичность инстанцирования
   (`cluster`/`sheet`/флаги/`layer`/`mirror`/`refs`). **Полей позиции у неё нет в принципе** —
   `xy`/`anchor_*`/`rotation` у Entity запрещены.
2. **Размещение = узел `trees:`** (`TreeNode`, `kind "placement"`) — `ref` узла — это `Entity.name`,
   а его `xy`/polar/`rotation` (резолвится как `позиция родителя + офсет узла`, см.
   `kicadstamp/tree_position.py::node_position`) — это то, где стоит эта Entity.

Деревья — ЕДИНСТВЕННОЕ хранилище позиций; отдельной секции `placements:` НЕТ. Плоское одиночное
размещение — это дерево из одного узла под `(anchor (origin))` или компонентным/точечным якорем.
`kind "clone"` переименован в `kind "placement"` (`"clone"` по-прежнему грузится как алиас во время
миграции), а `node.ref` для `kind "placement"` резолвится в `Entity.name` вместо старого списка
`clone_placements:`.

На apply-времени `materialize_entity_placements` (`kicadstamp/placement/entity_placement.py`) проходит
по связанным деревьям и создаёт временные абсолютные `ClonePlacement` (поля Entity + живьём
резолвленная абсолютная позиция), которые питают ТУ ЖЕ цепочку planner/executor, что и легаси
`clone_placements:` — то есть сплит Entity/Placement — чисто рефакторинг модели данных: механизм
исполнения не меняется.

Якорь дерева `(anchor (ref ...))` может сам указывать на Entity (placement-узел ДРУГОГО дерева) —
раз у Entity нет позиции, база якоря резолвится РЕКУРСИВНО: база якоря размещающего дерева
(origin/ref/role/снова ref на Entity — рекурсия, защита от циклов) + офсет этого узла. Entity без
узла размещения, размещённая более чем в одном узле или через цепочку, замыкающуюся в цикл, — это
КОНФИГ-ОШИБКА (фатал, никогда не пропускается молча).

Дерево БЕЗ `(anchor ...)` вообще (2026-08-31, план tree_self_anchor_from_entity; переработано
2026-09-05, design_2026_09_05 v2) получает АВТО-якорь: единственный корневой узел
`kind "placement"` указывает на Entity, а ролью якоря становится MOUNT-роль её ячейки
(`anchor_role`; для ещё не мигрированной legacy-ячейки — единственный компонент на хранимом (0,0),
старый «нулевой слот»), суженная собственными `sheet`/`cluster` этой Entity, и резолвится ЖИВЬЁМ
ровно как явный `(anchor (role ...))` (`anchor_pad` переносит базу на этот пад). Явный
`(anchor ...)` всегда имеет приоритет; авто применяется ТОЛЬКО при отсутствии анкора (буквальный
`(anchor (ref "self"))` — это по-прежнему прежний cycle-fatal). Неоднозначность конфига (нет
mount-роли И 0/2+ нулевых слотов, или 0/2+ корневых placement-узлов) — fatal всего прогона, никогда
не тихая догадка; живой сбой резолва роли (роль не найдена/неоднозначна на плате) — обычный
per-tree skip.

Top-level узел `kind "placement"`, чья mount-identity Entity совпадает с собственным ЯВНЫМ
`(role ...)` якорем дерева, — это САМО-ДУБЛЬ (2026-09-06, план `tree_root_rotation_drift`): узел и
якорь резолвятся в ОДНУ и ту же физическую деталь, поэтому его redraw может «крутить» якорь —
cell узла повторно добавляет `angle_deg` своего mount-слота поверх того самого угла, который только
что был прочитан как якорь (например, -90.0 у cell `conn_pm5v` под якорем CONN_PM5V дерева
"power"). «Извлечь дерево из выделения» больше не создаёт такой узел (отмеченный кластер,
совпадающий с явным якорем, пропускается — якорь резолвится независимо от списка узлов), а Trees
dock подсвечивает уже существующий дубль, чтобы его можно было безопасно удалить. Сама
материализация узел не обходит; единственный корневой узел `is_auto`-дерева структурно обязателен
и дублем не считается никогда.

Замечание о захвате при извлечении (2026-09-06): когда «Извлечь дерево из выделения»
автопозиционирует узел, он пишет офсет узла в ЛОКАЛЬНОМ кадре якоря (`xy`) и его `rotation` =
(живой угол mount − запечённый угол mount) − живой угол якоря (нормализован в (−180, 180]), где
запечённый угол mount — это `angle_deg` mount-слота cell (cell хранят абсолютные углы платы; для
авто-выведенной cell, генерируемой в момент save, слагаемое сокращается до `−угол якоря`). Поэтому
дерево, извлечённое при ненулевом угле якоря, перерисовывается на месте, а не «доворачивается»
вокруг якоря второй раз. Легаси-дерево, чьи узлы захвачены при якоре 0°, корректно только пока
якорь стоит на 0° — восстанови угол якоря или пере-извлеки дерево (тем же именем), чтобы заново
захватить его уже исправленным кодом.

**Миграция легаси-профиля:** `tools/convert_placements.py` переписывает `clone_placements:` в
`entities:` + деревья размещений на месте (запускать на КОПИИ — сначала создаётся `.bak` с
датой-временем) и переписывает уже существующие узлы `kind "clone"` в `kind "placement"`. См.
[docs/commands_ru.md](commands_ru.md) и [docs/config_ru.md](config_ru.md).

### `channel-copy` (вариант Б, живая плата) — четвёртый путь расстановки

Наряду с тремя конфиг-управляемыми типами расстановки выше есть
`kicadstamp/channel_copy.py` — модуль ВЕРХНЕГО уровня (не часть `placement/`),
который копирует ВСЮ расстановку канала (компоненты + via + дорожки) с
исходного канала на один или несколько каналов назначения **через живой
IPC-адаптер**, применяя одну жёсткую трансформацию (якорь + поворот +
опциональное зеркало). Карта близнецов строится по UUID-цепочкам
`fp.sheet_path.path`, а не по именам Role — поэтому повторяющиеся Role-схемы
между PIF-инстансами внутри канала не мешают (это структурный предел, из-за
которого монолитная extract-клетка неприменима к целому каналу).
Идемпотентность строится на позиции+цепи (0.01 мм / 0.1°), реестр не
затрагивается, а для идемпотентности треков переиспользуется `track_matches`
(общий позиционный предикат). CLI: `channel-copy` — см.
[docs/commands_ru.md](commands_ru.md).

## CoordinatePlacement («тупой разместитель»)

`coordinate_placements:` перемещает существующий футпринт — найденный по
точному совпадению Cluster+Role (Role должна быть уникальна внутри одного
экземпляра Cluster) — в целевую позицию/поворот. Без шаблона, без списка
смещений, без via/треков и без участия реестра: перемещение идемпотентно по
построению. Три взаимоисключающих режима позиции (полная семантика полей —
в докстринге `CoordinatePlacement` в `kicadstamp/config/models.py`):

- **Декартов (абсолютный)** – `x_mm`/`y_mm` + ОБЯЗАТЕЛЬНЫЙ `rotation_deg`.
- **Полярный (абсолютный, вокруг фиксированного центра)** –
  `center_x_mm`/`center_y_mm`/`radius_mm`/`angle_deg`; `angle_deg` по умолчанию
  становится `rotation_deg`.
- **Относительно якоря** (добавлено 2026-08-12, консолидация Группы 0 —
  перенесено 1:1 из прежних режимов `role:`/`cluster:` у `ClonePlacement`,
  которые удалены): `anchor_ref`/`anchor_role` (+ `anchor_sheet`/`anchor_cluster`)
  или `anchor_point` задают ДРУГОЙ, стационарный компонент/точку, а `x_mm`/`y_mm`
  (декартов) или `radius_mm`/`angle_deg` (полярный) становятся СМЕЩЕНИЕМ от
  этого якоря — или от его `anchor_pad`. Именно так размещается резистор
  «относительно конкретного пада FPGA»: `anchor_role: FPGA, anchor_pad: A17,
  radius_mm: ..., angle_deg: ...`.

`sheet` — ОПЦИОНАЛЬНО (2026-08-15), сужает Cluster+Role до ОДНОГО физического
экземпляра, когда один и тот же лист клонируется/переиспользуется (например,
одна секция PI-фильтра на канал), а Cluster сам по себе одинаков на всех
копиях — переиспользуемый иерархический лист клонирует ОДИНАКОВЫЕ
пользовательские поля на каждый экземпляр (Denis, живьём: AD_DAC/IC2
существует одинаково на каждом клонированном листе канала). Отличается от
`anchor_sheet` в режиме «относительно якоря» выше — тот сужает ДРУГОЙ, якорный
компонент, а не собственную идентичность этого размещения. Та же конвенция
(Sheet, Cluster, Role), что и во всём проекте.

`comment` — ОПЦИОНАЛЬНАЯ свободная заметка, видна в GUI (обычное поле схемы,
не комментарий `;` в файле).

`anchor` (`'center'`/`'pad'`, самореференсный, только в абсолютных режимах) и
`anchor_pad` (свой пад в абсолютных режимах, пад ЯКОРНОГО компонента в режиме
«относительно якоря» — та же семантика, что у Chain/ClonePlacement) описаны в
докстринге `CoordinatePlacement`.

Когда один и тот же набор записей CoordinatePlacement/ClonePlacement нужно
объявить один раз и размножить по переиспользуемым листам (Channel_0/1/2),
используйте секцию `sheet_templates:` вместо копипасты записей — см.
[docs/config_ru.md](config_ru.md).

## Файлы и функции

### `__init__.py`

Экспортирует публичные классы для удобного импорта:
```python
from .executor import BatchExecutor
from .planner import PlacementPlanner
from .commands import MoveCommand, ViaCommand, TrackCommand, PlacedComponentInfo
```

---

### `commands.py`

Определяет структуры данных (DTO) для передачи информации между компонентами.

| Класс | Поля | Описание |
|-------|------|----------|
| `MoveCommand` | `ref`, `position`, `angle`, `layer` | Команда перемещения/поворота компонента. |
| `ViaCommand` | `position`, `drill_mm`, `diameter_mm`, `net_name`, `owner_ref`, `registry_key` | Команда создания переходного отверстия. `registry_key` – для реестра (см. `registry.py`). |
| `TrackCommand` | `start`, `end`, `width_mm`, `net_name`, `layer`, `owner_ref`, `registry_key` | Команда создания прямого отрезка дорожки. `registry_key` – для реестра треков (`TrackRegistry`). |
| `PlacedComponentInfo` | `ref`, `dest`, `angle_deg`, `layer` | Информация о размещённом компоненте. `layer` может быть `None` (наследуется глобальный). |

**Используются в:** `planner.py`, `executor/`, `manual_position_calculator.py`, `clone_position_calculator.py`, `via_planner.py`, `registry.py`.

---

### `collision.py`

Упрощённая проверка коллизий между компонентами (по кругам-приближениям). Использует реальные bounding box'ы через адаптер для вычисления радиусов (половина диагонали bbox). **Коллизии треков не проверяются** – это сознательное решение (полагаемся на DRC KiCad).

| Функция | Описание |
|---------|----------|
| `compute_radii(footprints, adapter)` | Вычисляет радиусы для списка футпринтов (батч-запрос через адаптер). |
| `footprints_overlap(pos1, r1, pos2, r2, margin_mm)` | Проверяет перекрытие двух кругов с запасом. |
| `check_collisions(moves, all_footprints, adapter, ignore_refs, margin_mm)` | Проверяет коллизии между перемещаемыми компонентами и остальными. Возвращает список конфликтных пар (ref1, ref2, расстояние). |

**Используется в:** `executor/move_executor.py` (опционально, при включённой проверке).  
**Примечание:** может давать ложные срабатывания, отключается флагом `--no-collision-check`.

---

### `interfaces.py`

Определяет абстрактные интерфейсы для калькуляторов позиций и планировщиков via.

| Интерфейс | Метод | Описание |
|-----------|-------|----------|
| `IPositionCalculator` | `compute_raw_positions(target_fp, chains, side)` | Расчёт позиций компонентов и via для `ManualSpoke` (на основе падов IC). |
| `IViaPlanner` | `plan_vias(planned_components, planned_vias, target_fp, target_layer)` | Планирование via (термовиа + фильтрация через реестр). |

**Используются в:** `planner.py`, `manual_position_calculator.py`, `via_planner.py`.

---

### `planner.py`

**Класс `PlacementPlanner`** – главный координатор. Координирует расчёт позиций и via для `chains` (через `ManualPositionCalculator`) и `clone_placements` (через `ClonePositionCalculator`). Применяет логику пропуска уже стоящих на месте компонентов (`skip_existing_components`). Разделяет планирование на три фазы: `plan_moves()`, `plan_vias()`, `plan_tracks()`.

| Метод | Описание |
|-------|----------|
| `__init__(adapter, config)` | Инициализация, определение глобального слоя для ManualSpoke. |
| `_already_in_place(ref, dest, angle_deg, layer)` | Проверяет, находится ли компонент уже на целевой позиции (с учётом слоя, позиции и угла). Допуски: 0.01 мм по координатам, 0.1° по углу. |
| `plan_moves()` | Вызывает `ManualPositionCalculator.compute_raw_positions()` для `chains` и `ClonePositionCalculator.compute_raw_positions()` для `clone_placements`, объединяет результаты. Применяет `skip_existing_components` к компонентам. Сохраняет `_planned`, `_planned_vias`, `_planned_tracks` для последующих фаз. Возвращает `MoveCommand[]`. |
| `plan_vias()` | Вызывает `ViaPlanner.plan_vias()` с сохранёнными данными. Возвращает `ViaCommand[]`. |
| `plan_tracks()` | Возвращает сохранённые `_planned_tracks` (без дополнительной обработки; коллизии не проверяются). |
| `plan()` | Обратно совместимая обёртка (вызывает все три фазы подряд). Не рекомендуется для боевого использования. |

**Используется в:** `kicadstamp_cli.py` для получения плана.

### `executor/` – Исполнитель команд

Директория `executor/` разбита на модули для улучшения читаемости и тестируемости.

#### `executor/base.py`
Содержит общие утилиты:
- `layer_to_str(layer)` – преобразует `BoardLayer` в строку `"F.Cu"` или `"B.Cu"`.

#### `executor/operation_logger.py`
Отвечает за запись JSON-логов операций для `undo`.

| Метод | Описание |
|-------|----------|
| `__init__(log_dir)` | Создаёт папку `logs/`. |
| `write_operation_log(move_log, via_log, track_log)` | Записывает JSON-файл с временной меткой, включая треки. |

#### `executor/flip_manager.py`
Управляет переворотом (flip) компонентов через `adapter.flip_selected` с батчированием.

| Метод | Описание |
|-------|----------|
| `flip_if_needed(moves)` | Проверяет, какие компоненты требуют флипа, выполняет его батчами и возвращает обновлённый словарь `ref->footprint`. |

#### `executor/move_executor.py`
Применяет перемещения компонентов. Включает проверку коллизий, флип и батчирование.

| Метод | Описание |
|-------|----------|
| `execute_moves(moves, check_collisions, collision_margin_mm)` | Выполняет перемещения. Возвращает `(failed_refs, move_log)`. |

#### `executor/via_executor.py`
Создаёт via на плате. Использует реестр via для записи созданных via (`registry.record_created`).

| Метод | Описание |
|-------|----------|
| `execute_vias(vias, registry)` | Создаёт via батчами. Возвращает `(failed_via_owners, via_log)`. |

#### `executor/track_executor.py`
Создаёт треки на плате. Использует реестр треков (`TrackRegistry`).

| Метод | Описание |
|-------|----------|
| `execute_tracks(tracks, registry)` | Создаёт треки батчами. Возвращает `(failed_track_owners, track_log)`. |

#### `executor/batch_executor.py`
Фасад, объединяющий все фазы исполнения и управляющий логированием.

| Метод | Описание |
|-------|----------|
| `__init__(adapter, config, batch_size)` | Инициализация. |
| `execute_moves(moves, ...)` | Вызывает `MoveExecutor.execute_moves()` и сохраняет лог перемещений во внутренний буфер. |
| `execute_vias(vias, registry)` | Вызывает `ViaExecutor.execute_vias()` и сохраняет лог via во внутренний буфер. |
| `execute_tracks(tracks, registry)` | Вызывает `TrackExecutor.execute_tracks()` и **записывает единый JSON-лог** (объединяя перемещения, via и треки). |
| `execute(moves, vias, tracks, ...)` | Обратно совместимая обёртка (вызывает все фазы подряд). Не рекомендуется для боевого использования. |

**Важно:** лог операции записывается только после выполнения `execute_tracks()`, так как треки – последняя фаза. Если треков нет, вызывается `execute_tracks([])` для завершения логирования.

### `services/`

#### `services/component_pool.py`
**Класс `ComponentPool`** – подбирает refdes для ролей в `ManualSpoke`. Строится один раз на цепейо (`chain.net`) и разбирается спицами по очереди.

| Метод | Описание |
|-------|----------|
| `__init__(adapter, net_name, roles)` | Строит пул: читает все футпринты с полем `Role`, подключённые к `net_name`, сортирует по естественному числовому порядку. |
| `pop(role, spoke_pad)` | Забирает следующий компонент с ролью. Если пул исчерпан – `ValidationError`. |
| `remaining_count(role)` | Возвращает количество оставшихся компонентов. |

**Используется в:** `manual_position_calculator.py`.

#### `services/clone_role_resolver.py`
Разрешает роли для `ClonePlacement`. Поддерживает два режима:
- **по выделению** – считывает роли из выделенных компонентов. В одном прогоне может быть только один такой клон (из-за ограничения KiCad на одно выделение). С Фазы 2, шаг 2.3 это фактически явный режим `by_selection: true` — неявный клон (без `nets`/`params`) автоматически выбирает «по цепям», когда его целл авто-выводится на живой плате.
- **по цепям** – ищет компоненты по ожидаемой цепи. Ожидаемая цепь роли (Фаза 2, шаг 2.1): явные
  `nets:` → `net_template` ячейки (с плейсхолдерами; литеральная локальная цепь `/Channel_0/...`
  авто-префикс-ремапится на целевой канал, семантика `TwinMap.twin_net`) → авто-вывод с живой платы
  (`derive_role_nets`: единственная цепь уникального инстанса, либо единственная не-rule-цепь,
  общая для всех кандидатов). Литеральный `net_template` ячейки (без `{param}`, не `/Channel_N/...`)
  — это fallback ИСХОДНОГО инстанса, а не селектор: когда у размещения есть собственный cluster и
  живая плата даёт детерминированную цепь роли на нём, эта живая цепь побеждает
  (`derive_role_nets` live_pad, 2026-09-05) — cell, извлечённый с одной шины питания, безопасно
  переиспользуется на другой шине без утаскивания компонентов исходного инстанса
  (см. `tests/test_clone_reuse_cell_across_power_rails.py`). `net_template` ячейки с
  неразрешённым `{placeholder}` (нет подходящего `params`) НЕ считается явным источником — он
  уходит в путь живого авто-вывода
  (Фаза 4, шаг 4.3) вместо fatal — так что `nets:`/`params:`/`net_overrides:` — ОПЦИОНАЛЬНЫЕ
  override-ы. В случае неоднозначности использует каскадное сужение: явные `refs` → выделение → лист
  иерархии → **физическая близость к якорю** (если отрыв по расстоянию достаточен, выбирается
  ближайший кандидат). Это позволяет различать электрически одинаковые фильтры на общей шине.
  GUI-сужение Auto-fill/Nets/Params (PlacerDock) с 2026-08-16 использует ту же размерность `sheet`
  при живом поиске кандидата.
- **Два механизма сопоставления, не смешиваются** (Фаза 2, шаг 2.2): путь «по сетям» НИКОГДА не
  применяет net-matching (Кун) к ВЫБОРУ ИНСТАНСА — N одинаковых инстансов на общей/глобальной цепи
  дизамбигуируются только каскадом (sheet → Cluster → selection → proximity); если они действительно
  неразличимы — честный фatal, а не «догадка» Куном. Кун+SCC (соответствие Role↔Net из
  `net_matching`) — механизм ПОЛНЫХ двухкластерных снимков, используемый для верификации переноса
  трассировки (`channel_copy`/`clone-plan`), где полные снимки существуют, а не для выбора среди
  одинаковых компонентов в apply.

Функции:
- `clone_uses_selection_mode(clone, *, adapter, cell, sheet_names)` – определяет режим (учитывает `by_selection`, `nets`/`params` и — Фаза 2, шаг 2.3 — доступность однозначного инстанса-источника на живой плате: неявный клон, чей целл авто-выводится, выбирает «по цепям», иначе — «по выделению»).
- `resolve_roles_by_selection(adapter, template, clone_name)` – по выделению.
- `resolve_roles_by_nets(adapter, template, clone, anchor_position)` – по цепям с учётом близости к якорю; ожидаемые цепи авто-выводятся с живой платы, когда не заданы явно (Фаза 2, шаг 2.1).
- `resolve_anchor_by_role(adapter, clone)` – находит якорь по полю `Role` (альтернатива `anchor_ref`).

**Используется в:** `clone_position_calculator.py`.

#### `services/clone_position_calculator.py`
**Класс `ClonePositionCalculator`** – расчёт абсолютных позиций компонентов, via и треков для `ClonePlacement`. Использует `apply_clone_geometry` и `clone_role_resolver`.

| Метод | Описание |
|-------|----------|
| `_resolve_anchor(clone)` | Возвращает абсолютную точку якоря (центр пада или футпринта) или `None`. Учитывает `anchor_ref`/`anchor_pad`, `anchor_role`/`anchor_sheet`. |
| `compute_raw_positions(clone_placements)` | Для каждого клона определяет режим, получает `role_to_ref`, вызывает `apply_clone_geometry` (с учётом `mirror`), возвращает `(PlacedComponentInfo[], ViaCommand[], TrackCommand[])` с корректными `registry_key` (anchor_id формируется на основе физической привязки). |

**Используется в:** `planner.py`.

#### `services/manual_position_calculator.py`
**Класс `ManualPositionCalculator`** – расчёт позиций компонентов, via и треков для `ManualSpoke` на основе падов IC. Реализует `IPositionCalculator`. `TemplateTrack.net = None` наследует `chain.net` (та же конвенция, что и у `TemplateVia`) — именно это позволяет одному шаблону (например, `cap_pair_standard`) переиспользоваться в цепих с разными цепями.

| Метод | Описание |
|-------|----------|
| `compute_raw_positions(chains)` | Для каждого цепи строит `ComponentPool`, для каждой спицы вызывает `apply_spoke_geometry`, возвращает `(PlacedComponentInfo[], ViaCommand[], TrackCommand[])`. |

**Используется в:** `planner.py`.

#### `services/via_planner.py`
**Класс `ViaPlanner`** – реализует `IViaPlanner`. Отвечает за:
- Фильтрацию существующих via через реестр (сверка с реальными via на плате, `adapter.get_vias()`).
- Планирование термовиа (массив под термопадом) с поиском свободных мест через `find_free_point`.

| Метод | Описание |
|-------|----------|
| `_via_already_exists(existing_vias, position, net_name)` | Проверяет существование via с заданной цепью и позицией (допуск 0.01 мм). |
| `plan_vias(planned_components, planned_vias, target_fp, target_layer)` | Фильтрует `planned_vias` через `skip_existing_components` (сверяет с реальными via на плате), строит keepout, вызывает `_plan_thermal_vias`. |
| `_build_keepout(target_fp, planned, exclude)` | Строит keepout из падов IC и компонентов. |
| `_plan_thermal_vias(planned, target_fp, keepout, existing_vias)` | Генерирует термовиа с поиском свободных мест. |

**Используется в:** `planner.py` (после перемещений).

## Примечания по использованию

- **Трёхфазный процесс** (обязателен для корректного учёта термовиа и идемпотентности):
  1. Выполнить `plan_moves()` → `execute_moves()`.
  2. Выполнить `adapter.refresh_board()`.
  3. Выполнить `plan_vias()` → `execute_vias()` (с реестром via).
  4. Выполнить `plan_tracks()` → `execute_tracks()` (с реестром треков).
  Это реализовано в `kicadstamp_cli.py:cmd_apply()`.

- **Коллизии** – проверяются только для компонентов (опционально); треки не проверяются (полагаемся на DRC KiCad). Отключается флагом `--no-collision-check`.

- **Логирование операции** – сохраняется в `logs/operation_*.json` и используется `undo` (включая треки). Запись происходит после выполнения `execute_tracks()`.

- **Dry-run** – отображает перемещения, via и треки. Термовиа могут слегка отличаться из-за keepout, но это нормально.

- **Идемпотентность** – включение `skip_existing_components: true` позволяет безопасно перезапускать скрипт. Реестры via и треков предотвращают дублирование (сверка с реальными объектами на плате).

- **Автоматический подбор refdes** – для `ManualSpoke` через `ComponentPool` по полю `Role`. Для `ClonePlacement` – два режима (выделение или цепи) с разрешением неоднозначности по близости к якорю (включая `refs` для крайних случаев).

- **Клонирование секций** – для многократно повторяющихся шаблонов используйте `clone_placements` (ожидаемые цепи авто-выводятся с живой платы с Фазы 2, шаг 2.1; явные `nets`/`params` остаются опциональными override-ами; с Фазы 2, шаг 2.3 неявный режим сам выбирает «по цепям», если целл авто-выводится) и запускайте без выделения; для штучных экземпляров – явный режим «по выделению» (`by_selection: true`), выделяя компоненты в KiCad перед запуском.

- **Треки** – поддерживаются только в `ClonePlacement`. При извлечении шаблона (`extract`) треки попадают в шаблон автоматически (если выделены). При клонировании они создаются вместе с компонентами и via.

- **Слой размещения** – для каждого компонента может быть свой (per‑placement), для `ManualSpoke` используется глобальный `layer` из конфига. При зеркалировании (`mirror`) слои инвертируются.

- **Якорь по роли** – вместо `anchor_ref` можно использовать `anchor_role` (поле Role якорного компонента). Это устойчиво к перенумерации. Дополнительно можно сузить поиск с помощью `anchor_sheet` (префикс локальной цепи) или `anchor_pad`.
- **Явные refs** – в `ClonePlacement` можно задать `refs: {role: refdes}` для крайних случаев, когда кандидаты неразличимы ни по цепям, ни по выделению, ни по близости к якорю.
