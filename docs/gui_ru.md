# PyQt6 GUI

Постоянно открытое окно, задуманное чтобы держать его рядом с KiCad во время работы — не
одноразовый скрипт, как CLI. Обёртка напрямую над `kicadstamp.explore`/`kicadstamp.author`/
`KiCadBoardAdapter`/`ApplyPipeline` — ничего из логики размещения/экстракции здесь заново не
изобретено, всё то же, что делает CLI. Про сам формат YAML и механику размещения —
[docs/config_ru.md](config_ru.md); про CLI-эквиваленты каждого действия ниже —
[docs/commands_ru.md](commands_ru.md).

## Запуск

```bash
python kicadstamp_gui.py [--timeout-ms 20000] [--verbose]
```

`--verbose` сразу включает галочку Verbose в доке Log (см. ниже) — DEBUG-уровень детализации
виден с первого запуска, не нужно включать постфактум, когда что-то уже пошло не так.

## Раскладка

Восемь доков, сгруппированных в два таба плюс статус-бар:

- **Слева** (табы): **Components** (дерево Role/Cluster) и **Cells** (список извлечённых Cell).
- **Справа** (табы): **fieldstool**, **Files**, **Extract**, **Placer**.
- **Снизу**: **Log**.
- **Статус-бар**: состояние соединения, кнопка Reconnect/Refresh, галочка Always on top, галочка
  Tray icon, кнопка Open fieldstool, кнопка KiCad processes....

Кнопка **KiCad processes...** открывает список всех запущенных `kicad.exe` (PID, статус Windows
"Not Responding"/"Running", заголовок окна) — ярлык вместо «открыть Task Manager, найти зависший,
убить руками» (добавлено после случая, когда зависший `kicad.exe`, оставшийся живым рядом со
свежим, блокировал IPC-подключение свежего). Никогда не автоматически: у kipy нет способа
проверить ни один процесс KiCad на несохранённые изменения, так что закрытие — всегда выбор и
подтверждение человека, не эвристическое решение инструмента (см. `gui/kicad_processes_dialog.py`).

Ничего сюда не «пушится» из KiCad — у kipy 0.7.1 нет событий изменения выделения/платы, поэтому
«живое» тут означает опрос: медленный таймер (~2с) при разрыве соединения только переподключается
и НИКОГДА сам не перестраивает дерево (в ранней версии перестраивал — видимое дёрганье на
неизменной плате было хуже, чем просто ничего не делать); быстрый таймер (~400мс) следит за
выделением НА плате и отражает его в дереве. Полная перестройка снапшота — только по явному
действию: кнопке в статус-баре (**Reconnect** пока не подключено, **Refresh** пока подключено).

У окна есть **строка меню** с двумя top-level меню, построенными ПО ФУНКЦИИ, а не по доку: **File**
(Open/New/**Save**/**Discard unsaved changes...**/Recent/Close/Quit — см.
[docs/hotkeys_ru.md](hotkeys_ru.md)) и **View** (2026-08-27, по одному переключаемому пункту на
каждый top-level док, чтобы закрытый док можно было вернуть без перезапуска).

## Модель сохранения (staging, 2026-09-01)

Каждая правка конфига в GUI сначала попадает в **рабочий набор** в памяти
(`kicadstamp/config_working_set.py`) — дерево конфигурации, коллекторы имён, `load_config` и Redraw
читают отложенное состояние сразу («сработало»), но **ничего не пишется в файлы конфига, пока
File > Save (Ctrl+S) не закоммитит весь проект**. Это закрывает прежний разрыв, когда у редактора
деревьев был контролируемый Save с бэкапом, а все остальные доки писали свои конфиги в реальном
времени.

- **File > Save (Ctrl+S)** сбрасывает рабочий набор на диск атомарно: сначала валидирует
  отложенный граф (`load_config`) ДО записи — межфайловая нестыковка прерывает сохранение без
  записи; делает бэкап каждого изменённого файла в `history/` (рядом с root-конфигом, с датой,
  никогда не перезаписывает); пишет каждый файл через temp + `os.replace()`; затем инвалидирует
  кэши и обновляет доки.
- **File > Discard unsaved changes...** сбрасывает рабочий набор и перезагружает все доки с диска.
  Сознательно НЕ откатывает шаги Redraw, уже применённые к живой плате (для этого — свой Ctrl+Z в
  KiCad / кнопка Undo по operation-логам).
- **●** в статус-баре (и у пункта File > Save) означает, что в проекте есть несохранённые
  изменения конфига. При переключении/закрытии проекта с грязным рабочим набором сначала
  спрашивается Save/Discard/Cancel.
- Кнопки Save у отдельных доков УБРАНЫ (2026-09-01, шаг 6): КАЖДЫЙ док авто-стейджит свою запись
  на точках коммита — blur/Enter поля, выбор в комбо, переключение чекбокса, действие
  Add/Update/Remove строки или структурная правка дерева. Placer авто-стейджит тоже, с **тихим
  пропуском**: невалидный частичный placement никогда не стейджится (рабочий набор не держит
  невалидных записей, и графовая валидация на глобальном Save остаётся целой), ошибки не спамятся
  на каждом blur — запись стейджится, как только её поля заполнены.

## Дерево компонентов

Два источника данных, одно дерево, переключаются галочкой **Not yet applied**:

- **Не отмечено (по умолчанию) — живая плата.** Группирует текущий снапшот футпринтов по **Role**
  (плоско) или **Cluster** (иерархически, split по `/` — `Channel_1/PI_FILTER` реально вложен под
  `Channel_1`, та же логика сравнения по префиксу сегментов, что используется во всём конфиге).
  Клик по листу (один компонент) или по группе (всё, что под ней) — выделяет это **на реальной
  плате**; работает и в обратную сторону — выделение мышью в редакторе PCB KiCad подсвечивается
  тут. Клик по **узлу-группе Cluster** (только в режиме группировки Cluster, только по группе — не
  по листу) заодно заполняет поле Cluster в доке Placer. С 2026-08-13 лист в режиме группировки
  **Cluster** показывает свою роль рядом с рефом — `C1 (C_IN)` (Denis: «в дереве Components
  дописывать кроме Рефа — роль (если есть)»): в этом режиме роль больше нигде не видна, а в режиме
  **Role** она уже родительская группа, поэтому не повторяется.
- **Отмечено — не применённые (схема).** То же дерево, та же группировка/фильтр, но данные берутся
  из уже распарсенного `.kicad_sch`-списка компонентов [таба fieldstool](#таб-fieldstool) — и, с
  2026-08-03, только те ref'ы, у которых ПРЯМО СЕЙЧАС есть реальное расхождение Role/Cluster между
  схемой и живой платой (тот же diff, что показывает Pending changes). Компонент, чьи схема и плата
  уже совпадают — в том числе сразу после успешного Apply — тут больше не показывается вообще
  (найдено живьём: компоненты оставались в списке даже когда применять было уже нечего, что читалось
  как баг рядом с уже существующей панелью Pending changes). Компонент, которого вообще не было в
  живом снапшоте платы в эту сессию (не с чем сравнивать), тоже не показывается, даже если он реально
  есть в схеме. Компоненты с рассинхроном Role/Cluster между юнитами (внутри самой схемы) помечаются
  ⚠. Клик по листу или группе тут стейджит target в fieldstool (то же самое, что раньше делал клик в
  собственном, теперь удалённом, дереве fieldstool) и разворачивает таб fieldstool вперёд. Обновляется
  автоматически при каждом Rescan в fieldstool, а также при каждом изменении diff схема/плата (свежий
  тик поллинга, или запись через Stage/Clear all).

Выбор группировки и переключатель живая/схема запоминаются между запусками. **Filter** ищет по
ref/role/cluster в обоих режимах; галочка **regex** переключает с подстроки на регистронезависимый
regex (некорректный паттерн просто подсвечивает поле красным, не роняет GUI и не прячет всё подряд).

## Вкладка Cells

Плоский список имён Cell, прочитанный из файла, назначенного роли **Cells** в Files (см. ниже).
Клик по имени кормит поле Cell дока **Placer**.

## Таб fieldstool

Первый правый таб целиком встраивает GUI [fieldstool](fieldstool_ru.md), обёрнутое в одну доку
(`gui/docks/fieldstool_dock.py`) — второго процесса/окна нет, это теперь единственный способ
запустить fieldstool (отдельный вход `fieldstool_gui.py` существовал до 02.08.2026, удалён как
чистое дублирование этого таба). Дока **Pending changes** (03.08.2026: дифф схема-vs-плата по
Role/Cluster — см. [fieldstool_ru.md](fieldstool_ru.md#2-apply-kicad-должен-быть-закрыт)) теперь
общая с главным окном, прилеплена табом к **Log** внизу, а не своя внутри этого таба. `BoardConnection`
и единый поллинг 2с/400мс — общие с основным GUI (один клиент kipy, один REQ-сокет — второй
независимый таймер на том же соединении перемежал бы запросы). Собственного дерева компонентов у
него нет — режим «не применённые» [основного дерева компонентов](#дерево-компонентов) закрывает эту
задачу, когда он встроен сюда (собственное дерево fieldstool, `fieldstool/gui/tree.py`, удалено
01.08.2026).

Этот таб заменил **Bulk edit** (тоже удалена 01.08.2026) — та дока проставляла Role/Cluster прямо
через живой PCB IPC на этом же месте без какого-либо дальнейшего шага сохранения — такая запись
PCB-only и тихо затиралась собственным «Update PCB from Schematic» KiCad, поскольку `Role`/`Cluster`
реально живут в схемном символе. Собственная кнопка Stage у fieldstool (и Clear all/Delete selected
основного дерева компонентов) сегодня тоже пишут через такой же живой IPC, но именно дифф Apply
реально сохраняет изменение в `.kicad_sch` — тот самый недостающий шаг, которого у Bulk edit не
было.

## Files

Файловое дерево (корень по умолчанию — `boards/`, меняется) для выбора YAML/JSON конфигов, плюс
три именованные **роли**, из которых остальные доки берут свой целевой файл:

| Роль | Кто использует | Что туда попадает |
|---|---|---|
| **Cells** | Extract (пишет), Placer/вкладка Cells (читают) | `extract` пишет результат в ключ `cells:` этого файла. |
| **Extractor** | Extract | Структурный root-конфиг, куда пишутся записи `extract_profiles:`. |
| **Placer** | Extract (только прописывает ссылки), Placer | Структурный root-конфиг, куда пишутся записи `clone_placements:` — тот самый файл, на который указал бы настоящий `apply`. |

Чтобы назначить роль: кликнуть файл в дереве, затем **«Use selected»** на строке нужной роли.

**Все три роли можно держать в одном файле** — все три имеют один и тот же «структурный» формат
(`extract_profiles:`/`cells:`/`include:`/`clone_placements:` как соседние ключи, раз
`cells_file:`/`cell_files:` слиты в `include:` 2026-08-02 — см. [docs/config_ru.md](config_ru.md)).
Отдельный файл на роль — просто дефолтная привычка, а не требование, навязанное где-либо.

## Config tree

Дерево, отражающее фактический граф `include:` файлов, начиная с одного корневого конфига —
выбирается через **Open Root file...**/**New Root file...**/выпадашку **Recent**. Каждый файловый
узел показывает свои собственные секции (Cells/Clone placements/Thermal via arrays/Points/Chains/
Extract profiles/Clone profiles) и свои include-файлы, рекурсивно.

С 2026-09-03 (план tree_ui_state_persistence) свёрнутые вручную ветки ЗАПОМИНАЮТСЯ: каждый refresh
(Save где угодно в приложении перестраивает дерево) по умолчанию всё разворачивает — новая запись
всегда видна — и затем заново сворачивает ровно те ветки, что вы свернули; то же состояние
переживает перезапуск приложения (хранится как список «отклонений» в `gui_state.json`).

С 2026-08-30 (сплит Entity/Placement, фаза 5.6) каждый файловый узел также показывает категории
**Entities** и **Trees**. Клик по листу **Entities** переключает док Placer в Entity-режим с
загруженной этой Entity (`set_selected_entity`); **двойной клик** по листу Entities открывает
немодальный диалог «Редактировать шаблон» с этой Entity (её электрические поля, см. раздел
[Tools](#tools)); категория **Trees** — только навигационная: редактирование живёт в доке Trees.

Правый клик по любой записи даёт:
- **Rename...** — переименовывает запись; для Cells/Points ещё и переписывает каждую ссылку на
  неё (`cell:`/`anchor_point:`) по всему графу include:, а не только в файле, где запись объявлена.
  `F2` на листе делает то же самое (см. [docs/hotkeys_ru.md](hotkeys_ru.md)).
- **Delete...** — удаляет запись, предварительно бэкапя весь файл, в котором она лежала
  (с меткой времени, рядом с оригиналом — повторное удаление никогда не затирает предыдущий бэкап).
  Для Cells/Points сначала сканируется весь граф include: на предмет ссылок; если что-то нашлось,
  диалог подтверждения перечисляет их и спрашивает, удалить ли заодно и эти ссылающиеся записи
  (отказ отменяет удаление целиком, а не оставляет висячую ссылку).
- **Export.../Export selected...** — выделить одну или несколько записей (мульти-выбор включён
  только для этого) и скопировать их в отдельный файл через Save-диалог. Оригиналы остаются на
  месте нетронутыми. Если у целевого файла уже есть содержимое, спрашивается — смержить
  экспортируемые записи в него или перезаписать файл целиком.

Правый клик по файловому узлу даёт **Add cell.../Add point.../Add chain.../Add placer.../Add
thermal via pad.../Add included file...**, а также **Remove this file** (мягко отключает свою
запись в `include:`, сам файл не удаляется), если это не корень. С 2026-08-13 блок «Add ...»
стал **контекстным по секции**: правый клик по категории или листу показывает только «Add»
этой секции (cells → Add cell, chains → Add chain, ...); у Clone profiles и Extract profiles нет
ни одного «Add» (у extract_profiles нет отдельной Add-формы — профили теперь чисто
CLI/конфиг-секция, с 2026-09-01 док Extract удалён); клик по заголовку файла по-прежнему
показывает все (решение Дениса — иначе в свежем файле без единой секции нельзя было бы создать
первую сущность). С 2026-09-01 единственная точка входа захвата — пункт подменю
**Инструменты → Деревья → Извлечь дерево...** (см. ниже): он сам генерирует записи `cells:` из полностью
выделенных кластеров и пишет межкластерную медь в `net_traces:`, так что старый отдельный диалог
Extract и пункты **New Extract...** удалены.

Клик по любому узлу ещё и переключает Detail dock на панель ЭТОГО узла (Chain → Rules, ...; обычный
клик по файлу больше не ведёт на страницу Project — с 2026-09-01 вкладка Project переехала в
диалог). С 2026-08-21 доки-редакторы больше не спрашивают **в какой файл писать** — каждая
новая запись (Chain/ClonePlacement/CoordinatePlacement/ThermalViaArray/Point/Cell/ExtractProfile/
NetTrace) пишется в ОДИН корневой файл проекта (тот, что показан в панели Project), без файлового
пикера в форме. Граф `include:` полностью поддерживается для ЧТЕНИЯ: дерево конфига и
автодополнения/списки всех доков показывают записи из ЛЮБОГО подключённого файла. Чтобы вынести
кусок конфига в отдельный файл — используйте контекстное меню дерева **Export...** (см. ниже).

С 2026-08-15 файловые/именные комбобоксы всех доков остаются живыми: файл,
добавленный/удалённый через дерево («Add included file...»/«Remove this file»), запись,
переименованная/удалённая там же, ЛИБО новая сущность, созданная собственным Save дока-
редактора (например, «Add cell...» в CellDock + Save) — сразу видна в комбобоксах всех
остальных доков, без переключения корня и без перезапуска GUI (broadcast `graph_changed`, см.
plan_2026_08_15_graph_changed_broadcast.md).

## Trees

Таб **Trees** (табифицирован с Config tree, та же левая группа) — ручной редактор опциональной
секции `trees:` root-конфига. Одна вкладка на дерево, каждая — вложенный
список узлов относительно собственного якоря дерева. С 2026-09-03 (план
plan_2026_09_03_trees_menu_tools.md) у дока НЕТ цельно-деревного тулбара: все действия уровня
дерева вынесены в верхнее меню **Инструменты → Деревья**: **Извлечь дерево...** / **Извлечь
кластер...** (новое дерево из выделения платы), **Создать дерево...** (пустое ручное дерево —
бывший доковый «Add tree…»), **Переименовать дерево...** / **Удалить дерево...** (аналог
"Delete node" для всего дерева, с подтверждением Yes/No, дефолт No), **Позиция якоря**,
**Перерисовать выбранное** / **Перерисовать всё дерево**, **Full redraw (all trees and modules)...**
и **Экземпляры...**. В доке остаются вкладки, чекбокс-выбор поддеревьев и read-only индикаторы
(живая позиция якоря + несохранённые изменения ●). Структурное
редактирование — через контекстное меню узла (Add child / Add sibling / Reread current position /
Edit node… / Delete node / Rename… / Move to…); в меню anchor-псевдокорня — **Add node** и **Set
anchor…**. Диалог **Set anchor…** покрывает все шесть режимов якоря: **Origin (board 0,0)**,
**Config record** (имя из конфига, резолвится при Save; фильтр **Kind** сужает список ref до одного
раздела — Entity/Chain/Coordinate/Point/Clone/All; это только помощник пикера, в грамматике у якоря
нет kind), **External refdes** (живой компонент платы вне конфига), **Auto (derive from Entity's own
cell)** (без явного `(anchor ...)` — выводится на материализации из нулевого слота ячейки
Entity-корня), **Role** (роль + опциональные sheet/cluster/pad) и **Point** (имя записи `points:`).
Внешний выбор сохраняется с явным маркером `external`, поэтому НИКОГДА не резолвится против имени
записи конфига: refdes, совпавший с именем конфиг-записи (например, устаревший
`coordinate_placement` с именем `"fpga"`), не может перехватить якорь (2026-08-28). Поскольку
ref-якорь, указывающий на СОБСТВЕННЫЙ Entity-корень дерева, никогда не резолвится (гарантированная
самоссылка), список Config record исключает такую Entity, когда дерево уже размещает её своим
единственным top-level узлом `kind="placement"` (2026-08-31) — а если из-за исключения секция Entity
опустела, рядом появляется подсказка про режим Auto вместо пустого комбобокса. Save дополнительно
закрывает пути, которые диалог не видит (якорь поставлен, пока дерево было пустым, а корневой узел
добавлен/отредактирован позже, либо отредактированный вручную `.sexp`): та же самоссылка тихо
заменяется на Auto-якорь с уведомлением в статус-бар/лог. Редактирование
существующего якоря (**Set anchor…** на дереве, где якорь уже есть) предзаполняет диалог текущим
режимом и полями, поэтому мелкая правка (например, смена sheet у role-якоря) не требует
пересоздавать якорь с нуля. Смещения узлов вводятся вручную или
считываются с живой платы кнопкой **Read current
position** в диалоге Add/Edit node — это пассивное чтение живой позиции, которое НЕ валидирует
инвариант FORK-1 всего дерева, поэтому посторонний существующий узел с конфликтующим инлайн-anchor
его не блокирует. Родитель-Entity (узел `kind="placement"`) резолвит свою живую позицию/поворот
через дерево, которое его размещает — та же рекурсивная композиция «база якоря + node-path»,
что и у материализации на Apply — поэтому превью смещения работает и для резолвящегося
родителя-Entity. Entity, которую (пока) не размещает ни одно дерево, фолбэчится на собственный
единственный zero-offset-компонент (local (0,0)) своей ячейки (та же деривация, что у авто-якоря),
поэтому «Read current position» для, например, fpga_flash работает даже ДО сохранения узла,
который её разместит; предупреждает только Entity БЕЗ placement-узла И без читаемого zero-offset
(либо размещённая дважды / в цикле), с тем же фатальным текстом материализатора (2026-08-31).
Ничего не пишется на диск до **Save**, который заменяет всю секцию `trees:`
root-конфига через единый config_writer (сначала делается свежий `.bak`); линковка и валидация
выполняются при Save через `kicadstamp.link_trees`.

С 2026-09-03 (план tree_node_own_anchor) диалог Add/Edit node стал ДВУХВКЛАДОЧНЫМ: **General** (всё
перечисленное выше — Kind/Ref/Offset/Pivot/Rotation/Read current position/Name/Group) и новая вкладка
**Position**, которая выбирает, ОТ ЧЕГО отсчитывается смещение узла. **Relative to parent** (по
умолчанию) сохраняет прежнее поведение (от якоря дерева для верхнеуровневого узла, от охватывающего
узла для ребёнка). **Relative to component** вместо этого привязывает узел к выбранному живому
компоненту: выбираете **Role** (опционально сужаете **Sheet**/**Cluster** и сдвигаете на конкретный
**Pad**) — смещение `xy`/`polar` узла отсчитывается от живой позиции/поворота этого компонента, а
собственные дети узла продолжают наследовать этот frame. В грамматике это пишется как вложенный
`(anchor (role ...) [(sheet ...) (cluster ...) (pad ...)])` внутри узла — пер-узловой `own_anchor`;
допустима только role-форма (origin/ref/point/external бывают только у якоря дерева). **Read current
position** в компонентном режиме диффуется от выбранного компонента (а не от родителя), так что
набранное смещение считается от правильной базы.

Двойной клик по любому НЕ-module узлу дерева сразу открывает его EDIT-диалог (фаза B, план
tree_node_phaseB 2026-09-03); module-узел по-прежнему переключает на вкладку своего дочернего дерева.
EDIT-диалог закрывается ТОЛЬКО через **Close**: **Apply** записывает форму на узел на месте (помечает
док dirty, остаётся открытым — на диск ничего не пишется до Save), а **Redraw** сначала применяет
форму, затем ставит РЕАЛЬНЫЙ компонент этого узла на живой плате в его (отредактированную) позицию
конфига — один фоновый прогон ApplyPipeline `--only`, UI не блокирует. Неприменённые правки при Close
теряются. Add-диалоги остаются модальными OK/Cancel (до создания узла нечего применять/перерисовывать).

С 2026-09-03 (план tree_ui_state_persistence) запоминаются и АКТИВНАЯ ВКЛАДКА, и развёрнутость узлов
каждого дерева: rebuild больше не сбрасывает на первую вкладку и не схлопывает все деревья обратно —
какая вкладка активна и какие узлы развёрнуты, восстанавливается по имени/ref, и всё это переживает
перезапуск приложения (`gui_state.json`).

Списки кандидатов комбобоксов **Ref:** (Add/Edit node) и **Set anchor…** обновляются автоматически
в момент изменения include-графа или сохранения новой/переименованной Entity/Cell/Chain/... в любом
entity-доке — рестарт приложения или смена root не нужны (2026-08-31). Обновление только
перечитывает конфиг за списками диалогов; редактируемые деревья при этом не трогаются совсем,
включая их несохранённые правки.

Комбобокс **Ref:** в диалоге Add/Edit node фильтруется по **Kind**: при конкретном **Kind**
(`clone`/`chain`/`coordinate`/`point`) показываются только имена записей ЭТОГО раздела, а в режиме
**auto** — все placeable-имена: уникальные для одного раздела — как есть, а имя, встречающееся в
2+ разделах, — по одной записи на раздел с префиксом `{kind}:{name}` (например `rule:X`, `clone:X`).
Выбор такой записи с префиксом автоматически ставит **Kind** на этот раздел и подставляет чистое
имя — узел, оставленный в auto с коллизионным ref, был бы фатален при линковке («0 или 2+
совпадения»). **External** оставляет комбобокс свободным текстом для живого refdes платы
(2026-08-29, plan_2026_08_29_trees_node_kind_filtered_combo.md).

С 2026-08-30 (фаза 5.5) диалог добавления узла авто-нумерует ref НОВОГО узла, когда набранный ref —
не одно из размещаемых имён конфига И уже используется другим узлом где-то в деревьях:
`_unique_ref` дописывает `_1`/`_2`/…, чтобы дерево никогда не сохраняло дубликат ref (иначе фатал
при link-времени).

Добавить узел, чья запись всё ещё несёт собственный inline-якорь
(`anchor_ref`/`anchor_role`/`anchor_point`/`anchor_origin`), можно всегда — **Save никогда на этом
не падает** (FORK-1 больше не выполняется на link/Save). **Redraw selected** (или **Redraw whole
tree**) по такому узлу ТЕПЕРЬ перерисовывает его — с информационным, НЕ блокирующим
предупреждением: собственный `anchor_role` записи продолжает работать для обычного (не-деревного)
Apply/Redraw как раньше, а этот tree redraw двигает его лишь ВРЕМЕННО, через не персистентный
override, ничего в записи не переписывая (2026-08-29,
plan_2026_08_29_fork1_rigid_redraw_override.md — ОТМЕНЯЕТ прежнее цепейо, которое такие узлы
пропускало). Так что `CH0/1/2_DAC_BUF` каналов могут жить в дереве `fpga` и перерисовываться как
жёсткая группа БЕЗ снятия их `anchor_role`.

**Redraw whole tree** (Инструменты → Деревья) перерисовывает ВСЕ узлы текущего дерева одним
кликом, без ручной отметки чекбоксов. **Anchor position** (Инструменты → Деревья) обновляет
read-only индикатор текущей живой абсолютной позиции/поворота якоря дерева на плате, показываемый
в строке статуса дока (origin-якорь: тривиально (0,0)/0°; требует живого соединения с KiCad;
иначе — «unavailable»).

**Redraw selected — это жёсткая группа** (2026-08-29, plan_2026_08_29_tree_live_rigid_redraw.md):
узел, которым владеет дерево (без inline-якоря), ставится на своё ЖИВОЕ-захваченное смещение от
родителя, пере-проецированное в ТЕКУЩУЮ позицию/поворот родителя — так что сдвиг/поворот якоря
(или родительского узла) и Redraw выбранных зависимых двигает их вместе, причём смещение
поворачивается ВМЕСТЕ с родителем. Смещение читается с платы живьём в момент Redraw (не из
сохранённых `xy`/`polar`, которые остаются fallback-ом для узла без живого присутствия); собственные
поля записи никогда не перезаписываются — движение применяется через per-run, не персистентный
override позиции (Вариант 1, см. §3/§4 плана).

**Встраивание деревьев через модуль (2026-09-02, plan_2026_09_02_tree_module_embedding.md):** выбор
**Kind = module** в диалоге узла встраивает ДРУГОЕ дерево как жёсткий суб-лейаут. Список **Ref:**
переключается на ИМЕНА других деревьев — минус текущее, минус те, что это дерево уже встраивает, и
минус те, что замкнули бы цикл модулей — а offset/rotation узла задают положение МАРКЕРА встроенного
дерева. Второй, только для module, набор **Pivot (child frame)** говорит, какая точка ВНУТРИ
собственной локальной системы координат referenced-дерева должна лечь ровно на маркер (пусто =
origin referenced-дерева); кнопка **From child node...** копирует туда offset существующего узла
дерева-ребёнка. Module-ref никогда НЕ авто-нумеруется и не считается «занятым» record-ref (одно и
то же дерево-ребёнок можно встраивать в РАЗНЫХ родителей; недопустим только дубль ВНУТРИ одного
родителя — конфиг-фатал на Save). Дабл-клик по module-узлу открывает вкладку referenced-дерева; у
дерева, которое встраивают другие, появляется по одному пункту **«⇐ встроено в {parent}»** на
каждого родителя (дабл-клик возвращает на его вкладку). Модуль-aware ПОЛНАЯ перерисовка — рекорды
всех деревьев плюс контент каждого активного модуля, раскладка от живого якоря каждого дерева
(role/auto/origin/point/ref) — запускается из **Инструменты → Деревья → Full redraw (all trees and
modules)…** (только пункт меню, новых кнопок в доке нет); пункты **Redraw selected / Redraw whole
tree** в том же подменю **Инструменты → Деревья** остаются одно-деревными.

**Экземпляры дерева (`tree_instances:`, 2026-09-02, plan_2026_09_02_tree_instances.md; опциональная
ось `cluster:` 2026-09-03, plan tree_instances_cluster):** дерево + его Entity-записи можно объявить
ОДИН раз как ШАБЛОН и инстанцировать по листам схемы (и, опционально, по кластерам) декларациями
`tree_instances:` (см. доки конфига). Каждый сгенерированный экземпляр виден здесь как обычная
вкладка, узлы которой — глубокая копия шаблона: refs с суффиксом `__{instance.name}`, в копии Entity
и в role-якорь подставлен `sheet` экземпляра (а если задан — и `cluster` декларации). Вкладки
экземпляров — **ТОЛЬКО ДЛЯ ЧТЕНИЯ**: их
контекст-меню узла не предлагает Add/Edit/Delete/Rename/Move (геометрия принадлежит шаблону +
декларации), Rename/Delete дерева отказывают — но **Redraw** работает как обычно (экземпляры —
полноценно размещаемые деревья). На вкладке экземпляра сверху — пункт **«⇐ экземпляр {template}
(sheet={sheet})»**; у дерева-шаблона — по пункту **«→ экземпляр: {name}»** на каждый экземпляр;
дабл-клик переключает в обе стороны (тот же примитив навигации, что и «⇐ встроено в»). **Save
никогда не пишет сгенерированные экземпляры** как литеральные записи `trees:` — нетронутая секция
`tree_instances:` регенерирует их при каждой загрузке (без дублей). Короткие декларации правятся
через **Инструменты → Деревья → Экземпляры...**: выбери шаблон (сам экземпляр шаблоном быть не
может) и редактируй его
строки {name, sheet, cluster?} — колонка **Cluster** ОПЦИОНАЛЬНА (пустая = унаследовать кластер
шаблона без изменений); непустое значение подставляется в `cluster` сгенерированных копий и в
role-якорь, зеркально `sheet`. Диалог только сохраняет декларации, экземпляры материализуются при
следующей загрузке.

**Инстанцировать из Cell… (2026-09-03, plan instantiate_from_entity):** добавить ЕЩЁ ОДИН физический
кластер того же рода В текущее дерево, не дублируя геометрию — выбери СУЩЕСТВУЮЩУЮ Cell (напр.
pif_p2v5_vcca) как внутреннюю расстановку группы (её components/vias/tracks живут в Cell один раз; новая
Entity лишь ссылается на неё через cell:), задай имя новой Entity для нового кластера (напр.
PIF_1V2_VCCINT) и адресуй её по Sheet/Cluster. Узел размещения сдвинут на xy от якоря дерева (у дерева
должен быть задан якорь): либо вручную, либо — галочка «Взять из выделения» — из текущего выделения на
плате (геометрический центр выбранной группы, если все её футпринты из ОДНОГО кластера; несколько
кластеров в выделении — ошибка; пустое выделение — вручную). Новая Entity не несёт явных refs: роли
нового кластера разрешаются на Apply по (Cluster, Sheet). Точки входа: Инструменты → Деревья →
«Инстанцировать из Cell...» и контекстное меню якоря текущего дерева. Всё staged — на диск только при
File > Save.

У того же диалога есть вторая вкладка, **Извлечь новую Cell из выделения** (2026-09-04, plan
instantiate_new_cell_from_selection): когда в текущем выделении на плате ровно ОДИН полностью
выделенный кластер (та же детекция, что у «Extract cluster...» — частичное выделение никогда не
извлекается молча, ср. plan_2026_09_03_fpga_oscill_missing_copper_and_cell_import.md), вкладка
позволяет ИЗВЛЕЧЬ расстановку кластера как новую Cell прямо здесь — без отдельного похода в
«Extract cluster...» — и добавить узел размещения в один клик. Cluster/Sheet кластера
авто-заполняются в адресацию; имя новой Cell по умолчанию — slug кластера (редактируется; имя,
которое уже есть в `cfg.cells`, отклоняется). Точка отсчёта внутренней геометрии Cell («Точка
отсчёта геометрии») — либо «Относительно zero-slot» (по умолчанию; переносимая конвенция, подходит
любому размещению узла), либо «Абсолютно (центр выделения), поворот 0», чья точка отсчёта — тот ЖЕ
геометрический центр, что у позиционирования «Взять из выделения», поэтому итоговая позиция
воспроизводится точно. «Абсолютно» гарантировано только вместе с «Взять из выделения» (диалог
предупреждает, а не блокирует — Cell потом можно поправить вручную).

## Settings

**Settings** (2026-08-15, план `configurator_panel`; переработан 2026-09-01, план
`project_settings_dialogs`) — отдельный **модальный диалог**: открывается из меню **Инструменты →
Настройки...**. В нём чистые GUI-настройки приложения ДЛЯ ЭТОЙ МАШИНЫ — GUI-фасад над
`gui_state.json` из [`gui/settings.py`](gui/settings.py), сознательно НЕ проектный конфиг. Диалог
«Project» (RootMetadataDock) редактирует YAML проекта в версионируемом файле проекта; этот диалог
его никогда не трогает. Всё здесь — локальное состояние конкретной машины (то же хранилище, что
уже используют `last_root_file`/`window_geometry`/`tree_group_by`).

Диалог — двупанельный браузер: **дерево категорий слева** (General / Appearance / KiCad / Config
tree / Hotkeys / MCP server) и соответствующая страница настроек справа. Настройки применяются
**явно** кнопками **OK / Apply / Cancel**: изменение виджета — только черновик, пока его не
закоммитит **Apply** (сохраняет и остаётся открытым) или **OK** (сохраняет и закрывает);
**Cancel** (или крестик окна) отбрасывает черновик. Побочные эффекты (флаг поверх-всех, значок в
трее, пере-применение подсветки, таймаут подключения, переназначение горячих клавиш) срабатывают
только на Apply/OK.

- **Always on top** / **Tray icon** (страница **General**) — два чекбокса, которые раньше стояли
  прямо в статус-баре, переехали в Settings (2026-08-15); сама ЛОГИКА окна-поверх-всех / значка в
  трее не изменилась и осталась в `MainWindow` (`_set_always_on_top`/`_set_tray_enabled`) — браузер
  просто переизлучает их переключения из `apply()`, а `DockHub` заводит их обратно. В статус-баре
  теперь только статус-метка и кнопки Reconnect/Open fieldstool/KiCad processes...
- **Style** (страница **Appearance**, 2026-09-03, план `qt_style_setting`) — выбор имени
  Qt-стиля, которым рендерится весь GUI. **System default** (первый, особый пункт) означает
  «вообще не вызывать `setStyle()`» — сегодняшнее поведение, системная Qt platform-theme
  интеграция не трогается. Остальные пункты — стили, доступные НА ЭТОЙ машине/сборке Qt
  (`QStyleFactory.keys()`, например `Fusion`/`Windows`) — никогда не хардкод-список, на разных
  ОС он разный. Хранится как `gui_state.json["qt_style"]` (отсутствует/`None` = System default)
  и применяется И на старте (`apply_saved_qt_style` в `kicadstamp/gui_main.py`), И живьём на
  Apply/OK (`QApplication.setStyle()`). Fatal-safety как у `window_geometry`/`dock_state`:
  сохранённое имя, которого нет на этой машине (например `gui_state.json`, синхронизированный с
  другой ОС), тихо игнорируется и откатывается на System default — ничего не ломает. Известное
  ограничение Qt (не наше): после живого переключения стиля в рамках одной сессии возврат на
  System default не может гарантированно восстановить самый первый стиль — подпись под
  комбобоксом рекомендует перезапуск для гарантированно чистого результата.
- **Color scheme** (страница **Appearance**, внутри группы **Style**, 2026-09-03, план
 `color_scheme_setting`) — второй, независимый рычаг для той же Linux-проблемы «белый-на-белом»:
 встроенный **QPalette**-оверрайд поверх стиля. **None** (первый пункт) означает «без
 палитры-оверрайда» — системная/темическая палитра. Единственная встроенная схема сегодня —
 **Airy**, та самая палитра, что использует схема `airy` из qt6ct (значения зашиты в
 `gui/color_schemes.py` — буквальная копия `/usr/share/qt6ct/colors/airy.conf`, НЕ читается с
 диска в рантайме, поэтому работает на любой машине/сборке; тот же принцип «сшить в приложение»,
 что и у иконки). Хранится как `gui_state.json["color_scheme"]` (отсутствует/`None` = без
 оверрайда) и применяется И на старте (`apply_saved_color_scheme`, после qt_style-оверрайда), И
 живьём на Apply/OK (`QApplication.setPalette()`). Fatal-safety как у `qt_style`: сохранённое имя,
 которое не называет ни одну встроенную схему (например `gui_state.json`, синхронизированный с
 другой машины/версии), тихо игнорируется и откатывается на None — ничего не ломает. В отличие от
 `qt_style`, возврат на **None** здесь ЧИСТО восстанавливает исходную палитру (примитивная
 палитра снимается в свойство `original_palette` приложения на старте, до любых оверрайдов).
 Подсказка: кастомные цвета надёжнее всего работают со стилем Fusion (информационная — стиль
 автоматически не переключается).
- **Highlight color** (страница **Appearance**) — одна схема подсветки для ВСЕХ ТРЁХ мест: активная
  вкладка Detail dock,
  выбранный элемент Config tree и выбранный элемент Components tree. **System palette** использует
  `palette(highlight)` темы ОС; **Custom** (через **Pick color...**) — буквальный цвет. Хранится
  как `highlight_mode` (`"system"`/`"custom"`) + `highlight_color` (hex) в `gui_state.json`,
  применяется при старте и сразу при изменении. Раньше оба дерева были голыми нативными
  `QTreeView`, чей selection на Windows был еле виден (тот же баг «еле видно», найденный при этом
  обсуждении).
- **KiCad connection timeout** (страница **KiCad**) — ЕДИНСТВЕННЫЙ пользовательский таймаут (`DEFAULT_TIMEOUT_MS`,
  `kicadstamp/constants.py`), редактируется в мс. Пишется прямо в `connection.timeout_ms`, который
  `BoardConnection` читает при каждом connect, так что применяется к СЛЕДУЮЩЕМУ подключению, не
  трогая открытое. Внутренние защитные тайминги (`_CONNECT_TIMEOUT_GRACE_S`, `_CLOSE_TIMEOUT_S` из
  pynng_safety, пинг single-instance) сознательно НЕ выставляются — один из них буквально только
  что закрыл живой фриз GUI (см. `handoff_2026_08_15_pynng_close_timeout.md`).
- **Hotkeys** (страница **Hotkeys**, 2026-08-30, план `dock_toolbars_menus_hotkeys` Этап 1) — по
  одному редактору комбинации на каждое QAction-действие (пока это пять действий дока Project:
  Open/New/Save/Add.../Remove — см. `gui/hotkeys.py`). Переназначение пишет
  `gui_state.json["hotkeys"]` как `{action_id: shortcut}` и применяется к живому действию на
  Apply/OK; пустой редактор возвращает дефолт из кода. Полный список — в
  [docs/hotkeys_ru.md](hotkeys_ru.md).
- **MCP server** (страница **MCP server**) — гейт raw-записи `kicad_raw_move_footprint`, который
  headless MCP-сервер читает из `gui_state.json` (см. [docs/mcp_ru.md](mcp_ru.md)); эквивалент
  переменной окружения `KICADSTAMP_MCP_ALLOW_RAW_WRITE=1`.

## Extract

Специальный док/диалог Extract удалён в Фазе F (2026-09-01) — его функцию поглощает
**Инструменты → Деревья → Извлечь дерево...** ниже (авто-генерация `cells:` из полностью выделенных
кластеров и захват межкластерной меди в `net_traces:`), а ручное редактирование `cells:`
остаётся во вкладке **Cells** Detail-dock. Секция `extract_profiles:` остаётся чисто
CLI/конфиг-понятием: `kicadstamp_cli.py extract --profile` (`cli_extract.py`, `extract_writer.py`)
по-прежнему её читает.

Старый пункт **Инструменты → Перечитать выделенное...** слит в **Извлечь дерево...**: его диалог
перечисляет каждый ПОЛНОСТЬЮ выделенный кластер (все его компоненты на плате в выделении, по
тегу Cluster + листу) с его сущностью и Cell, галочки по умолчанию стоят; по OK каждый
отмеченный кластер перечитывается — текущее расположение его компонентов/via/треков заново
записывается в cell с рецептом из extract_profiles (params/origin/net_template_role/rule_nets),
если он есть, иначе авто. Чужая медь, захваченная area-select, отбрасывается
connectivity-фильтром экстрактора (СВОЯ применённая медь кластера остаётся — без registry). Так
три канала PIF_AVDD (Channel_0/1/2, один cell) различаются: лист из выделения выбирает инстанс.

В подменю **Инструменты → Деревья → Извлечь дерево...** (2026-09-01) строится НОВОЕ дерево из
текущего выделения — никакого «экстракта в дерево» нет (экстракт не пишет в `trees:`); это
собственное
дерево выделения. Выдели группу кластеров на плате и запусти. Модальный диалог из трёх вкладок:
**Кластеры** (полностью выделенные кластеры, галочки по умолчанию стоят, с живым превью ΔX/ΔY
смещений после выбора якоря), **Якорь** (комбо корневого кластера, которое предзаполняет
Sheet/Cluster/Role из собственной сущности кластера — «существующий якорь кластера» — либо явное
сужение Sheet/Cluster/Role/Pad в `TreeAnchor`) и **Дорожки и переходные между кластерами**
(межкластерные сети — выделенная медь, чья сеть касается 2+ кластеров — с галочками на сеть и
мастер-галочкой «выбрать всё/снять выделение»). По OK каждый отмеченный кластер становится
top-level нодой `kind="placement"` с `ref` = именем его Entity и `xy` = живая позиция Entity минус
живая база якоря (автопозиционирование, как «Reread current position» — дерево фиксирует текущую
геометрию относительно якоря; без живого чтения нода сохраняется без `xy`, и позиции читаются
живьём при apply). Отмеченные межкластерные сети захватываются как записи `net_traces:` рядом.
Новое дерево пишется в секцию `trees:` корневого конфига через тот же `config_writer` (backup +
round-trip `link_trees`); TreesDock и Config-дерево обновляются сразу. Строки, у кластера которых
нет Entity или cell, помечаются и блокируют OK; пустое/дублирующееся имя дерева или отсутствие
Role тоже блокируют OK.

Пункт подменю **Инструменты → Деревья → Извлечь кластер...** (2026-09-03) — более узкий собрат
**Извлечь дерево...** для случая, когда нужен ТОЛЬКО один полностью выделенный кластер как
отдельная плоская Entity (+ её Cell, генерируемый из собственного выделения кластера, если его
ещё нет) — БЕЗ узла дерева, БЕЗ якоря и БЕЗ захвата `net_traces:`. Тот же детект кластера, что у
**Извлечь дерево...** (полностью выделенный кластер = все его компоненты на плате в выделении, по
Cluster-тегу + листу), открывает маленький модальный диалог на один кластер: выбери кластер, а имя
Entity предзаполняется — авто-выведенное, когда она новая (редактируется, с обычной валидацией
дубликатов имён), read-only, когда Entity для этого кластера + листа уже существует
(переиспользуется, никогда не дублируется). По OK Entity пишется в `entities:` корневого конфига
(а новый Cell — в `cells:`) через тот же `config_writer`; Config-дерево обновляется сразу. Entity
не хранит позицию, поэтому её размещение (ручной узел дерева, шаблон `tree_instances:` и т.д.) —
отдельный следующий шаг: «Извлечь кластер...» никогда не пишет позицию.

Меню **Инструменты → Расставить термо-виа...** (2026-09-01) и контекстное меню Config
(«Add thermal via pad...», а также клик по листу `thermal_via_arrays`) открывают отдельный
(не-модальный) **диалог Thermal via** — свежая пустая форма для «Add ...», с предзаполнением
записи при клике по листу. Это та же форма, что была на странице Detail-dock: выбери якорь
(ref/role + cluster или именованную Point), пад, цепь и геометрию сетки, затем **Redraw**, чтобы
разместить via на живой плате (ApplyPipeline `only=[name]` — диалог остаётся открытым для
итеративной подгонки), и **Save**, чтобы записать запись `thermal_via_arrays:` (диалог сам
закрывается после успешного Save).

**Origin**/**Net aliases**/**Net template role**/**Sub-placements**/**Existing** ниже теперь живут
во вкладках (2026-08-04: раньше стояли одна под другой в одной колонке, чья минимальная высота
была СУММОЙ минимумов всех секций сразу — док не мог сжаться меньше этого, даже когда большая
часть секций сейчас не нужна). `QTabWidget` считает размер только под текущую вкладку, поэтому
док теперь свободно сжимается; вкладки **Net template role** и **Sub-placements** скрываются
целиком (не только содержимое), пока реально не понадобятся. С 2026-08-31 сети при экстракте
определяются автоматически (net_template роли пишется из её собственных не-rule сетей — см.
ниже), поэтому вкладки **Net aliases**, **Net template role** И **Existing** скрыты по умолчанию
тоже (профили/целлы выбираются из Config-дерева); галочка **Show advanced net settings**
возвращает их для ручных override-ов.

- **Куда пишется** — успешное извлечение пишет Cell в секцию `cells:` корневого файла проекта
  (а при «Also save as extract_profile» — рецепт профиля в секцию `extract_profiles:` того же
  файла). Бывшие выпадашки Cell file/Profile file/Placer file убраны (2026-08-21): всё, что
  производит док Extract, теперь попадает в один корневой файл.
- **Cell name** — по умолчанию slug текущего Cluster выделения (`PWR/DAC0` → `pwr_dac0`), если из
  этого Cluster ещё ничего не извлекалось; если уже есть подходящий ключ в Cells/Extractor —
  побеждает он. Никогда не перетирает то, что уже напечатано руками.
- **Origin** — Bounding box (по умолчанию, левый нижний угол выделения) / Component role (+
  опционально pad и — с 2026-08-31 — опционально **Cluster**/**Sheet**, чтобы сузить
  неоднозначную роль, встречающуюся в нескольких Cluster/каналах) / Via net.
- **Net aliases** — настоящий `QTableWidget` (2026-08-06, раньше был самодельный grid — Denis: «у
  нас в экстракторе net-aliases, не таблица»), по строке на каждую сеть, найденную на падах
  выделенных компонентов. Сами строки не добавляются/удаляются руками — набор сетей целиком
  диктуется текущим выделением на плате и пересобирается на каждый тик слежения за выделением;
  редактируемы только ячейки **Alias** и **Chain net** внутри строки. Непустой алиас становится
  `{PLACEHOLDER}` в записанной Cell (питает `params:` для обратного резолва — см.
  `net_template`/`params` в [docs/config_ru.md](config_ru.md)). У каждой строки есть чекбокс
  **"Chain net (null)"** (2026-08-05), взаимоисключающий с полем алиаса — если поставить его,
  via/track этой сети пишется как `net: null`, и целла, размещённая через `chains:`/ManualSpoke,
  наследует нет того конкретного Chain, под которым она размещена (см. `rule_nets:` в
  [docs/config_ru.md](config_ru.md)) — механизм переиспользования ОДНОЙ и той же целлы сразу на
  нескольких Chain с разными силовыми рейлами, чего алиасинг через `{PLACEHOLDER}` тут не умеет (у
  ManualSpoke нет `params:`, против которых можно резолвить шаблон).
- **Net template role** — появляется только когда пады компонента касаются **2+ разных не-rule
  сетей** (мостиковая деталь — дроссель, ферритовая бусина, предохранитель, перекинутый между
  двумя рельсами). С 2026-08-31 net_template роли выводится автоматически — первая по сортировке
  сеть, у которой есть алиас (параметризуется), либо первая не-rule сеть литералом, — поэтому
  экстракция по умолчанию больше не блокируется, а сама вкладка скрыта; она появляется (когда
  включены расширенные настройки), чтобы при желании переопределить авто-дефолт ручным пиком.
- **Sub-placements** (2026-08-25) — появляется, когда area-select под новый Extract сметает
  существующее, уже извлечённое top-level `clone_placement` (например PIF-фильтр питания) вместе с
  компонентами новой целлы. Вместо плоского копирования геометрии этого размещения в новую целлу
  (копия молча рассинхронизируется с оригиналом, как только одно из них переразместят на другом
  канале) док сам его распознаёт: для каждого top-level `clone_placement` из конфига Placer-файла
  он резолвит живые board-items размещения (тем же `resolve_clone_board_items`, что и фича
  Re-extract) и проверяет, покрыто ли выделением ВСЁ множество — кандидатом становится только
  полностью покрытое размещение (частичное пересечение — скорее случайное совпадение геометрии и
  остаётся на старом пути). Вкладка перечисляет каждого кандидата (имя размещения, его целла,
  сколько компонентов/via/треков совпало) с чекбоксом, **включённым по умолчанию**; экстракция с
  отмеченным чекбоксом пишет размещение как ссылку `clone_placements:` в новую композитную целлу
  (`name`/`cell`/`xy`/`rotation_deg`/`mirror`/`layer`, xy = мировой origin размещения, переведённый
  в локальную систему новой целлы) и **исключает** его board-items из плоских
  `components:`/`vias:`/`tracks:` новой целлы — одна и та же геометрия не попадает туда дважды (и
  ссылкой, и плоско). Снятие галки возвращает старое плоское поведение. При включённом Cluster
  filter via/треки полностью покрытого размещения больше не выбрасываются молча registry-фильтром
  (они становятся частью ссылки); чужие/частично покрытые размещения по-прежнему исключаются как
  раньше. Выделение, ЦЕЛИКОМ покрытое Sub-placements, — легитимный **чисто композитный** Extract:
  новая целла получает только `clone_placements:` (пустые плоские списки), плоский экстрактор не
  вызывается. Origin целлы (bbox/роль/via-net) всегда считается по ПОЛНОМУ (до-исключения)
  выделению, поэтому `xy` Sub-placement-ссылки и плоская геометрия гарантированно в одной системе
  координат, даже если компонент-источник origin'а сам входит в исключаемый Sub-placement.
- **Existing (click to reuse a name)** — два списка (Cells/Profiles), читаются из назначенных
  файлов. Клик по записи переиспользует её имя целиком и подтягивает сохранённые алиасы сетей,
  выбор net-template-role и origin обратно в форму (сопоставление по алиасу, а не по литералу сети
  — так это работает и при переиспользовании профиля для аналогичного Cluster на другом рельсе,
  например `+2V5` вместо `-2V5`). То же самое срабатывает автоматически, если slug текущего
  Cluster совпадает с существующим ключом.
- **Also save as extract_profile** — дополнительно пишет воспроизводимый рецепт (name/output/
  params/origin/net_template_role) в секцию `extract_profiles:` файла-Extractor, чтобы ту же
  экстракцию можно было позже перезапустить из CLI (`kicadstamp_cli.py extract --profile <key>`)
  без повторного набора алиасов.
- **Re-extract from current board state** (2026-08-25) — для УЖЕ сохранённого Cell/extract-профиля:
  выберите его в списках **Existing**, затем выберите **Placement** (тот `clone_placement`, чей
  `cell:` — эта ячейка) в комбобоксе, и док заново захватит живые компоненты + зарегистрированные
  via/track этого размещения прямо с платы и перезапишет Cell — без ручного повторного выделения
  в pcbnew. Комбобокс перечисляет все `clone_placement`, ссылающиеся на выбранную ячейку; кнопка
  неактивна, когда ни одно размещение не использует эту ячейку (у голого Cell, никогда не
  размещавшегося через `clone_placement`, пересобирать нечего). Всё остальное (origin/алиасы цепей/
  рецепт `raw_selection` из сохранённого профиля) переиспользуется без изменений — отличается
  только источник извлекаемых элементов.
- Если назначен файл **Placer**, успешная экстракция заодно проверяет, что в `include:` этого
  файла есть и Cells-файл, и файл Extractor (дедуп по фактически резолвленному пути) — Placer-файл
  остаётся готов сразу использовать то, что только что извлекли.

## Placer

Строит и применяет `ClonePlacement` — GUI-эквивалент `kicadstamp_cli.py apply --only <name>`.
**Эта дока реально двигает футпринты на живой плате.**

**Source**/**Nets**/**Net overrides**/**Refs**/**Origin** лежат в табах (2026-08-06, Denis: «в
пласере точно надо табом. Он может быть длинный!» — та же причина, что и у Extract/Root/Rules/
Cells — минимальная высота стековой `QVBoxLayout` равна СУММЕ минимумов всех секций разом).
Nets/Net overrides/Refs изначально были секциями внутри одного таба «Nets», в тот же день разбиты
на три отдельных соседних таба (Denis, живьём: даже табами Params+Nets+Net overrides+Refs вместе
всё ещё не влезали — Params остался в паре с Nets, поскольку оба питают один и тот же шаг резолва
роли по сетям, и именно эта пара была явно одобрена как есть; Net overrides и Refs используются

Redraw/Save и строка сообщения остаются вне табов — они относятся ко всему размещению, а не к
одному табу.

- **Куда пишется** — размещение пишется в секцию `clone_placements:` (или `coordinate_placements:`)
  корневого файла проекта. Бывшие выпадашки Cells file/Placer file убраны (2026-08-21); комбобокс
  **Cell** внутри Source по-прежнему выбирает Cell из ВСЕГО include-графа.
- **Source** — **Cell** (по умолчанию), **Role** или **Cluster** (все добавлены 2026-08-06, Denis:
  «путь потрясающе длинный: создать экстрактор, извлечь шаблон, сделать cell и только потом,
  placement») — Role/Cluster оба полностью пропускают Extract/Cell для честного одиночного
  компонента, никакая запись `cells:` не читается и не пишется (`ClonePlacement.role`/`.cluster`,
  уже поддержаны бэкендом — этот переключатель просто первая GUI-поверхность для них). Годится
  только для голого компонента без via/track/второго компонента — как только появляется реальное
  содержимое, Cell + Extract остаётся цепейьным путём.
  - *Role* — выбираешь Role напрямую (тот же автодополняемый комбобокс, что и у Anchor's Role ниже).
    Role — КАТЕГОРИЯ, не уникальна — много компонентов законно делят одну Role — поэтому при
    неоднозначности на плате Redraw резолвит её так же, как настоящие role-слоты ячейки (выделение,
    затем сужение через собственный Cluster размещения — его `name`; с 2026-08-14 `anchor_cluster`
    сужает только якорь), либо честно падает со списком кандидатов.
  - *Cluster* — та же идея, но ищет цель по УЖЕ ПРОСТАВЛЕННОМУ полю Cluster на плате (протегируй
    заранее через дерево компонентов или fieldstool) — тот же день, Denis отдельно возразил против
    одной Role: «Условие уникальности у нас касается кластера, а не роли... ОДНУ деталь надо
    размещать просто по кластеру. Роль там не при делах». Без выделения и сужения: точное совпадение
    либо единственное (берётся сразу), либо ошибка тегирования — фатал в обоих случаях. Этот режим
    ещё и переиспользует выбранное значение Cluster как имя самого размещения — строка-имя
    «Cluster:» ниже (см. следующий пункт) в этом режиме полностью скрывается (найдено живьём
    2026-08-06, Denis: «Зачем нам два поля Existing Cluster и Cluster?» — второе, независимо
    введённое имя рисковало молча перетегировать компонент на другое значение при Redraw, раз тег
    Cluster и так задуман уникальным).
- **Cell** — выпадающий список закрытого множества (НЕ `configure_searchable()` — тот же урок, что
  и у CellDock's anchor_role_combo: редактируемый комбобокс на поле, значение которого обязано
  совпасть с существующим ключом — и риск зависания, и семантически неверно), заполняется ключами
  `cells:` из текущего выбранного файла Cells. Также выставляется кликом по Cell в категории Cells
  дерева конфига (`set_selected_cell`) — оба пути идут через один и тот же метод, так что любой из
  них держит второй в синхроне. Добавлено 2026-08-06 (Denis, живьём: «в пласере давай сделаем имя
  целла по выпадающему комбо-боксу... не удобно» — ходить в дерево конфига за каждым пиком было
  неудобно). Скрыто в режиме Role/Cluster.
- **Sheet** (добавлено 2026-08-15) — СОБСТВЕННЫЙ лист размещения, опционально: сужает
  неоднозначные Cluster+Role внутри целла, когда этот целл клонируется между переиспользуемыми
  листами. Поисковый комбобокс с автодополнением из schematic-файлов проекта
  (`schematic_dir`/`schematic_files`, через `RuntimeContext.sheet_names`) при смене root — это
  пикер, а не whitelist, тот же паттерн «populate, don't restrict», что у Cluster/Role/Nets
  (2026-08-15, см. plan_2026_08_15_sheet_combo_everywhere.md). Расположен ВЫШЕ «Cluster:» — та же
  конвенция (Sheet, Cluster, Role), что и в режиме Single component ниже.
- **Cluster** — тег Cluster размещения (ключ `name:`, которым помечаются компоненты на плате; он
  же кликается из дерева компонентов, см. выше). С 2026-08-15 это больше НЕ identity для
  сохранения — та переехала в **Placer name** ниже. Скрыто в режиме Source=Cluster (см. выше) —
  вместо запроса имени переиспользуется выбранное значение Existing Cluster.
  С 2026-08-31 (план placer_source_tab_gaps P.1) поле также авто-заполняется из ТЕКУЩЕГО выделения
  на плате, как ExtractDock заполняет имена Cell: выделите компоненты целого Cluster на живой
  плате — его имя подставится в это поле — только в Cell-режиме, только пока поле пустое и не
  принадлежит пользователю (никогда не перетирает введённое/выбранное), и затем тихо запускает
  пайплайн авто-заполнения Nets/Params.
- **Placer name** (добавлено 2026-08-15) — СОБСТВЕННАЯ identity записи для Save/`--only`
  (опциональный ключ `placer_name:` в `clone_placements:`), отдельная от тега Cluster: по ней
  `upsert_clone_placement` решает «заменить существующую запись» против «дописать новую», и ею
  адресуется `--only`. Автозаполняется из Cluster ТОЛЬКО при создании новой записи; после
  сохранения остаётся неизменной — правка Cluster на уже сохранённой записи больше не плодит
  дубль. Нужно только если хочется менять Cluster на сохранённой записи; если оставить равным
  Cluster — поле вообще не пишется в файл.
- **Single component** (Source-комбо — запись `coordinate_placements:`, без `cell:`) — её поля
  идентификации **Sheet**/**Cluster**/**Role**/**Name** живут здесь, на Source-табе (с 2026-08-13,
  Denis: «Cluster, Role, Name надо на первый таб перенести» — раньше они были на Coordinate-табе,
  вперемешку с полями позиционирования, и их было не найти). **Sheet** (добавлено 2026-08-15)
  опционально — сужает Cluster+Role до одного физического экземпляра, когда один и тот же лист
  клонируется/переиспользуется, а Cluster сам по себе одинаков на всех копиях (отличается от
  `anchor_sheet` в виджете Anchor — тот сужает ДРУГОЙ, якорный компонент). Оба поля Sheet —
  поисковые комбобоксы с автодополнением из schematic-файлов проекта при смене root — пикер, а
  не whitelist (см. plan_2026_08_15_sheet_combo_everywhere.md). На Coordinate-табе
  остаётся только «куда ставим» (Mode/X Y/Anchor/...). Метка «Cluster:» намеренно совпадает со
  строкой-именем Cell-режима выше — это другое поле, они никогда не видны одновременно.
- **Табы Nets / Net overrides / Refs** — все три таба целиком скрыты в режиме Role/Cluster (убраны
  из полосы табов через `setTabVisible`, а не просто опустошено содержимое — у синтетической
  однокомпонентной cell нет полей net у via/track, которые можно было бы шаблонизировать, а режим
  резолва по умолчанию для Role/Cluster — по выделению — вообще не читает `nets:`/`refs:`, только
  режим «по сетям» их читает; см. докстринг `_on_cell_mode_changed` про то, почему все три скрываются
  вместе — иначе можно молча заполнить поле, которое ни на что не повлияет):
  - **Таб Nets** —
    - **Params** — по строке на каждый `{PLACEHOLDER}`, найденный где угодно в YAML выбранной Cell
      (обнаруживается автоматически, не печатается руками) — литеральная сеть, в которую должен
      разрешиться этот placeholder для КОНКРЕТНОГО экземпляра.
    - **Nets** (добавлено 2026-08-06) — role → литеральная сеть, приоритетнее собственного
      `net_template:` ячейки при резолве роли по сетям. Редактируемая таблица (add/update по ключу,
      remove выбранной строки) — колонка Role автодополняется ролями `components:` ВЫБРАННОЙ
      ЯЧЕЙКИ, а не всеми ролями с живой платы (`nets:`/`refs:` вообще смотрят только на роли,
      которые реально есть среди компонентов самой ячейки, см. `resolve_roles_by_nets` в
      [docs/config_ru.md](config_ru.md); найдено живьём 2026-08-06 — список по всей плате был
      вводящим в заблуждение, в тот же день поправлено).
    - **Auto-fill from board** — кнопка «Auto-fill from board» (и её тихий авто-триггер при каждом
      выборе Cell/Cluster, план 2026-08-13) резолвит каждую роль НА ЖИВОЙ плате по префиксу Cluster
      плюс подсказкам `net_template_pad`/`net_template_same_as_role` ячейки (см.
      [docs/config_ru.md](config_ru.md)), заполняет пустые строки Nets и в том же воркер-прогоне
      считает по-ролевое сужение кандидатов для комбобокса роли в Nets И комбобоксов Params.
      С 2026-08-16 дополнительно сужает по СОБСТВЕННОМУ **Sheet** этого размещения (`sheet_edit`,
      т.е. `clone.sheet`) — та же конвенция (Sheet, Cluster, Role), что у apply-резолверов — так
      что целл, переиспользуемый между иерархическими листами (живое репро DAC_BUF: три
      `AD_DAC`+`DAC_BUF` инстанса, одинаковые Cluster/Role записаны в ФАЙЛ листа), сужается до
      нужного инстанса вместо отката на полный список цепей платы. Пустой/неизвестный `sheet_names`
      (не выбран Placer-файл, или не резолвится `schematic_dir`) — молчаливый no-op: тот же фолбэк
      на полный список, что и раньше, никогда неверная догадка. С 2026-08-27, если сужение
      Params-комбобокса сошлось ровно к ОДНОМУ кандидату, значение подставляется автоматически
      (только пока поле ещё пустое — уже введённое пользователем значение никогда не перетирается;
      при 2+ неоднозначных кандидатах поле остаётся пустым, та же дисциплина «не гадать», что у
      строк Nets). С 2026-08-28 (Фаза 2, шаг 2.4) бэкенд — ЖИВОЙ авто-вывод
      (`suggest_role_nets_live`): подсказки `net_template_pad`/`net_template_same_as_role`
      комбинируются с apply-side `_auto_derive_live_net` (live_pad), так что роль БЕЗ подсказок
      целла тоже заполняется, когда живая плата даёт детерминированную единственную цепь — одна
      цепь уникального инстанса, или ОДНА цепь, общая для всех её кандидатов на этом кластере
      (например, несколько C_IN_BULK на +3V3 в одном PI-фильтре). Таблица Nets показывает эти
      авто-значения и остаётся редактором OVERRIDE-ов — любую строку можно переопределить.
      Строка Params, оставшаяся пустой, может быть осознанным ограничением, а не «просто ещё не
      сработало» (2026-08-31, план placer_source_tab_gaps P.3): плейсхолдер сужаем только через
      роль, у которой `net_template:` РОВНО `{KEY}` — составной шаблон вида `/…/…/+3V3` нельзя
      обратным ходом свести к одной цепи, поэтому у такого поля появляется тултип с объяснением,
      что его нужно выбрать вручную.
  - **Таб Net overrides** (добавлено 2026-08-06) — разрешённая сеть → финальный override,
    применяется ПОСЛЕ подстановки Params/net_template (см. `resolve_net` в
    [docs/config_ru.md](config_ru.md)). Обе колонки автодополняются реальными именами сетей с живой
    платы.
  - **Таб Refs** (добавлено 2026-08-06, закрывает последний GUI-пробел, который раньше был явно
    помечен в докстринге этой доки) — role → явный ref, полностью пропускает поиск роли — последний
    довод, ломается при переразметке. Колонка Role автодополняется ролями `components:` выбранной
    ячейки, та же логика, что у Nets выше.
- **Origin**:
  - *Absolute XY* — буквальная позиция на плате.
  - *Anchor (ref/role)* — позиция относительно существующего компонента: Ref **или** Role
    (взаимоисключающе), опционально Sheet, опционально Pad, опционально Anchor cluster (сужает,
    какой именно компонент с этой Role имеется в виду, если их несколько). Role и Anchor
    cluster — списки на выбор, автодополняются с живой платы; Sheet — поисковый комбобокс с
    автодополнением из schematic-файлов проекта (пикер, а не whitelist); Ref — простое текстовое
    поле (в проекте предпочитается Role, а не refdes — Role переживает переразметку, refdes нет —
    поле Ref оставлено на редкий случай, когда оно реально нужно).
  - *Point* — позиция относительно именованной записи `points:`, автодополняется по всему проекту
    (любой ключ `points:`, достижимый через `include:`, не только из этого файла).
  - Режимы Anchor/Point также принимают плоский **сдвиг** по XY.
  - **Read current position** — заполняет текущую живую позицию/поворот. С 2026-08-31 (план
    placer_source_tab_gaps P.2), если поля идентичности Anchor/Point заполнены, а комбобокс режима
    всё ещё стоит на дефолтном Absolute (XY), режим автоматически переключается на заполненный
    набор Anchor/Point (молча, без диалога) — так чтение выражает origin как СДВИГ от этого якоря
    вместо молчаливой записи абсолютных координат.
- **Rotation / Layer / Mirror** — как в самих полях `ClonePlacement` (см.
  [docs/config_ru.md](config_ru.md)).
- **Redraw** — собирает размещение, валидирует и реально прогоняет его против живой платы
  (сначала грузится НАСТОЯЩИЙ, полный конфиг Placer-файла — так все остальные уже сохранённые
  размещения защищены, это не синтетическое превью из одной записи). После успеха реально
  размещённые компоненты помечаются `Cluster=<name>` (больше нигде в пайплайне этого не
  происходит — см. про то, что Cluster read-only при `apply`, в
  [docs/config_ru.md](config_ru.md)). С 2026-08-26 метятся ТОЛЬКО компоненты СВОЕГО уровня этого
  размещения: у композитной ячейки (вложенные `clone_placements:`) компоненты, разрешённые
  вложенным `CellPlacement`, сохраняют свой Cluster (`PIF_DVDD`, ...) вместо перезаписи именем
  верхнего размещения (живой баг tag_cluster_overtag — Redraw затирал Cluster каждого
  компонента вложенных суб-целлов). Поменял поле — жми Redraw снова, идемпотентно, повторять
  безопасно.
- **Redraw dependents** — каскад: это размещение плюс КАЖДАЯ запись, транзитивно на него анкорящаяся,
  в топологическом порядке (родитель всегда раньше тех, кто на него анкорится), каждая через свой
  отдельный прогон `ApplyPipeline --only`, чтобы зависимый прочитал анкор уже ПОСЛЕ перемещения.
  Граф анкоров строится из ROOT-конфига проекта (весь граф `include:`), так что зависимости из
  других подключённых файлов тоже находятся. Порядок и статус (успех/сбой) каждой записи пишутся в
  Log dock. Статическое разрешение анкоров — в
  [`kicadstamp/anchor_graph.py`](kicadstamp/anchor_graph.py), общий каскад — в
  [`gui/docks/cascade.py`](gui/docks/cascade.py).
- **Redraw & Save** (2026-08-25) — Redraw, затем — только если он реально успешен — Save, одним
  кликом. Redraw выполняется в воркер-потоке; Save дожидается его реального завершения (никакого
  наивного `_on_redraw(); _on_save()` — гонки нет), а при неудачном Redraw пропускается с явным
  сообщением в Log.
- **Save** — отдельно, пишет текущую форму в `clone_placements:` Placer-файла (замещает запись с
  тем же именем, никогда не дублирует). Redraw сам по себе **не сохраняет** — посмотрел, поцепей,
  снова Redraw, и Save только когда результат устраивает.
- **Select on board** (2026-08-25) — резолвит размещение из текущей формы в его живые элементы на
  плате (компоненты плюс все via/track, которые registry записал за этим размещением) и выделяет
  ровно их в pcbnew — визуальная проверка, что реально принадлежит этому размещению, без
  перемещения чего-либо. Ничего не найдено (ещё не размещено) — короткое сообщение в Log, не падение.
- **Undo** (2026-08-25) — сначала подтверждение, затем отмена САМОЙ ПОСЛЕДНЕЙ операции
  `operation_*.json` в каталоге журнала операций всего проекта (тот же выбор, что у CLI
  `kicadstamp undo` — не обязательно операция, которую запускала именно эта форма Placer).
  Перемещённые компоненты возвращаются, созданные переходы/дорожки удаляются; файл журнала
  удаляется, чтобы нельзя было отменить дважды. Нет журналов — сообщение «отменять нечего» без
  диалога подтверждения. Каталог берётся из `operation_log_dir` конфига (с фолбэком на корень
  проекта), иначе `logs/` — та же резолвия, что у `kicadstamp undo`.

Пока не покрыто в GUI (всё достижимо ручной правкой сохранённого YAML): режим `by_selection`.
Сужение по `anchor_sheet` РАНЬШЕ было в этом отложенном списке — закрыто 2026-08-15: теперь
каждое поле Sheet — поисковый комбобокс из schematic-файлов проекта (см.
plan_2026_08_15_sheet_combo_everywhere.md), включая Origin у ClonePlacement и anchor у
ThermalViaArrayConfig (у обоих поле было в модели, до формы оно просто не дотягивалось).

## Entity-режим (PlacerDock, 2026-08-30)

Сплит Entity/Placement (фаза 5.2) добавил в док Placer источник **Entity**. Выбор Entity (из всего
`include:`-графа) загружает запись `entities:` в форму — **Source** правит «что» (Cell/Nets/Params/
Cluster/Sheet/... — электрика и идентичность; секции позиции тут НЕТ, Entity никогда не несёт
`xy`/anchor/rotation), а таб **Origin** правит позицию, которая пишется в узел `trees:`, размещающий
эту Entity.

- **Save (Entity)** — валидирует и пишет запись `entities:` через `upsert_entity` в тот файл, где
  Entity реально живёт (Entity во включённом файле обновляется на месте, никогда не дублируется в
  корень). Merge сохраняет электрические поля (`nets`/`net_overrides`/`refs`), даже если форма их
  очистила (фикс merge-preserve, 2026-08-30).
- **Origin (Entity)** — тот же виджет позиции, что и в пути ClonePlacement (Absolute XY / Anchor /
  Point). При сохранении вызывается `upsert_entity_placement` (`kicadstamp/config_writer.py`): он
  находит дерево, чей анкор совпадает с выбранным началом координат (или создаёт одно-узловое
  дерево с именем Entity) и пишет/обновляет узел `kind "placement"`, чей `ref` — имя Entity. Метка
  статуса сообщает «Placed under tree …» или «Not placed — set an origin to place it.» (нет узла
  дерева = легально не размещено).
- **Табы** — в Entity-режиме табы Placer Nets/Net overrides/Refs скрыты (переехали в диалог
  **Tools**, следующий раздел); легаси-режим Cell/ClonePlacement их сохраняет.

## Tools (Nets / Net overrides / Refs, 2026-08-30)

Фаза 5.3 вынесла три электрических редактора Entity ИЗ дока Placer в форму **Tools**
(gui/docks/tools.py). С 2026-09-01 (план `plan_2026_09_01_tools_dialog_and_entity_roles.md`) это
отдельный **немодальный диалог** (не страница Detail): открывается из меню
**Инструменты → Редактировать шаблон...** или **двойным кликом** по листу **Entities** в дереве
Config (который загружает эту Entity в форму — одинарный клик по листу Entities по-прежнему
переключает Placer в Entity-режим). Диалог авто-закрывается после успешной правки.

- **Nets** — `role → net` (Params остаётся на табе Source у Placer — оба питают один и тот же шаг
  by-nets резолва ролей).
- **Net overrides** — `резолвленная цепь → override`.
- **Refs** — `role → явный refdes`.

Диалог ориентирован на Entity ровно как Entity-режим Placer: выберите Entity (по всему графу),
правьте три словаря, каждая запись валидируется через `load_entity` и пишется обратно тем же
merge-safe `upsert_entity` в файл самой Entity — так что диалог Tools и Source/Origin у Placer
правят одну и ту же запись, не затирая друг друга. С 2026-09-01 комбобоксы **Role** сужены до
компонентов Cell выбранной Entity (`entity.cell` → `cell.components[].role`, то же цепейо, что в
Cell-режиме PlacerDock), а комбобоксы **Net/Override** питаются именами сетей с живой платы
(`refresh_known_nets`, тот же ~2s поллинг, что и табы Placer) — раньше эти комбобоксы были пустым
свободным вводом.

## Points

Правит именованную запись `points:` (см. [docs/config_ru.md](config_ru.md) про схему Point) —
переиспользуемый якорь, на который по имени ссылаются другие `anchor_point:` (собственный режим
Point у Placer, Chain/ThermalViaArrayConfig). Добавлено 2026-08-05, после того как стало видно,
насколько форма Point уже совпадает с виджетом Origin у Placer.

С 2026-09-01 (план `plan_2026_09_01_points_dialog.md`) это отдельный **немодальный диалог** (а не
страница Detail-дока): открывается через меню **Инструменты → Add point...**, пункт контекстного
меню «Add point...» в дереве Config, или **двойной клик** по листу `points:` в дереве Config
(загружает эту точку в форму — одинарный клик по листу points: ничего не делает). В диалоге —
та же живая форма, что была на странице Detail-дока; после успешного Save диалог сам закрывается.

- **Origin** — **Absolute XY** / **Anchor (ref/role)**, теперь с полем **Sheet** (Denis: «нужен
  anchor_sheet в этой панели») — поисковый комбобокс с автодополнением из schematic-файлов
  проекта, не whitelist — рядом с Ref/Role/Pad/Anchor cluster / **Point** (цепочка на другую
  точку по имени — это поле автодополняется из `points:` текущего файла, закрывая пробел
  «автодополнение имён points:», ещё открытый у самого Placer в разделе выше) / **Board origin**
  (добавлено 2026-08-06, Denis: «точка 0,0 -- это левый верхний угол листа, никак не origin» —
  читает ЖИВОЙ origin-маркер платы через kipy вместо угаданного литерала: **Drill/place**, auxiliary
  axis, от которой всегда считаются drill/position-файлы (и Gerber — опционально, через свою галочку
  в диалоге экспорта), или **Grid**, чисто визуальный, Place > Set Grid Origin).
- **Shift X/Y** — плоский сдвиг в мм поверх базы Anchor/Point/Board origin (недоступен для
  Absolute XY — там просто правь координату напрямую).
- **Resolve** — считает, куда точка (и всё, через что она цепляется) резолвится ПРЯМО СЕЙЧАС, ничего
  не записывая и не двигая на плате (у Point нет собственного физического действия, в отличие от
  Redraw у Placer) — показывает буквальные X/Y в мм, и если точка срезолвилась через живой
  футпринт — выделяет его на плате (тот же highlight, что и клик по узлу в дереве Components).
  Другая, не связанная с этой, точка в том же файле, которая сейчас сломана, молча пропускается,
  а не блокирует превью — специально мягче, чем всё-или-ничего валидация реального `apply`.
  Сужение по Sheet в этом превью пока не подключено (нужен `schematic_dir` проекта — вторая
  зависимость по файлу, отложена в этом первом заходе) — само поле Sheet при этом сохраняется
  корректно, для настоящего `apply` сужение строится как положено.
- **Save** — пишет в секцию `points:` корневого файла проекта (словарь по имени, а не список словарей, как
  у Placer/Thermal via — существующее имя замещается на месте, не дублируется).

## Chains

Правит запись `chains:` (см. [docs/config_ru.md](config_ru.md) про Chain/ManualSpoke) — один общий
якорь (тут нет режима `xy`, в отличие от Points/Placer — только **Anchor (ref/role, + Sheet/
Cluster)** или **Point**; Sheet здесь — тот же поисковый комбобокс с автодополнением из
schematic-файлов проекта, не whitelist) плюс УПОРЯДОЧЕННЫЙ список spokes, каждая ставит Cell на
конкретный пад этого якоря со своим hand-tuned сдвигом/поворотом. Добавлено 2026-08-05 (как
«Rules»), после того как Denis подключил `fpga_spokes.sexp`/`fpga_cap_pair_spoke.sexp` к реальному
проекту и упёрся в давно известный пробел «у Rules вообще нет формы».

2026-09-01 (план rules_to_chains): форма теперь — отдельный **немодальный Chain-диалог**
(`gui/docks/chain_dialog.py`), а НЕ страница Detail-dock: запись `chains:` в дереве Config
редактируется ДВОЙНЫМ кликом, и пады больше не таблица — они ЛИСТЬЯ в дереве (категория →
якорь → цепь → пад). У диалога два режима в одном виджете:
- **Режим цепи** — Net/Name/Comment + **Origin** (комбобокс режима якоря + Sheet/Cluster, или
  Point) + **Retired**/**Skip**. Двойной клик по узлу цепи открывает его.
- **Режим пада** — поля одной спицы: **Pad**/**Cell**/**Cluster**/**Mode** (Cartesian/Polar)/
  **Shift X,Y** (или **Radius+Angle** в Polar)/**Rotation**/**Retired**/**Skip**. Двойной клик по
  листу пада открывает его; **Add spoke...** (контекстное меню / меню Tools) открывает пустой,
  чтобы добавить пад в выбранную цепь.

Порядок падов по-прежнему семантически значим (pool компонентов разбирает спицы в порядке
списка), но в дереве они сортируются по номеру пада; правка пада перезаписывает ВСЮ родительскую
цепь через `upsert_list_entry` (пад — не отдельная запись).

**Net**/**Origin**/**Spoke** лежат в табах (2026-08-05, та же причина, что и у Extract/Project —
минимальная высота стековой `QVBoxLayout` равна СУММЕ минимумов всех секций разом): Net несёт
собственные Net/Name/Retired/Skip самого Chain; Origin — комбобокс режима якоря и его две строки;
Spoke — все поля, в которые пишет строка-редактор под таблицей. Сама таблица spokes, строка move/
Add/Update/Remove и Redraw/Save остаются вне табов — они относятся ко всему Chain, а не к одному табу.

- **Таблица spokes + строка-редактор снизу** — выбрано вместо того, чтобы класть spokes в общее
  дерево Config (у spoke нет поля имени для подписи листа, порядок spokes семантически значим —
  pool компонентов разбирает их именно в порядке списка — а столбцы таблицы показывают
  shift/rotation/cluster каждой spoke сразу взглядом). Сама таблица только для чтения — всё
  редактирование идёт через строку снизу и её кнопки **Add spoke** / **Update selected** /
  **Remove selected** / **Move up** / **Move down** — отображаемая строка таблицы никогда не
  разъедется с тем, что реально провалидировано и сохранено. Любая из этих операций, а также
  *завершение редактирования* любого поля спицы (blur / Enter / выбор в комбобоксе), пишет
  цепейо на диск СРАЗУ (2026-08-20) — для работы на уровне спиц отдельный Save не нужен, а
  неудачная запись видна в доке Log, никогда не молча.
- **Cell** (у каждой spoke) — searchable-комбо со списком ВСЕХ ключей `cells:`, достижимых от root
  проекта через `include:`, а не только из этого файла — cell конкретной spoke обычно лежит в
  другом файле, чем сам chain. **Point** (якорь самого chain, не у отдельной spoke — spoke всегда
  цепляется к паду СОБСТВЕННОГО якоря этого chain) заполняется так же, по всему графу. Обоим нужен
  root проекта — подключено так же, как у панели Project.
- **Redraw chain** — весь chain целиком, все не-skip spokes, та же схема replace-by-identity +
  `ApplyPipeline(only=[...])`, что и у Redraw в Thermal via.
- **Redraw selected spoke** — то же самое, но в копию, отдаваемую в pipeline, временно
  проставляется `skip: true` всем ОСТАЛЬНЫМ spokes (в Save это никогда не попадает) — это корректно,
  потому что резолв spokes идёт через ОДИН общий pool компонентов на net на весь chain, поэтому
  одну spoke изолированно не зарезолвить, но pipeline можно попросить пропустить все, кроме нужной
  — именно для этого и существует `skip:`.
- **Save** — с 2026-08-20 единственная оставшаяся работа кнопки — собственные поля **Net/Origin**
  самого Chain (правки спиц автозаписываются сами, см. пункт про таблицу выше). Пишет весь chain в
  `chains:` корневого файла проекта, матчится по имени, если оно задано, иначе по net (`chains:` —
  единственная list-секция без обязательного `name:`, см. [docs/config_ru.md](config_ru.md)'s
  `chain_effective_name`).
- **Bulk set Cell for net…** (2026-08-20) — разом задаёт `cell:` всем спицам ВСЕХ цепей на
  выбранной сети, даже если эти цепи лежат в разных include-файлах (обычно так и есть — список
  сетей и превью в диалоге ходят по всему include-графу). Диалог показывает превью (какие
  цепи/пады затронет) ДО записи; частичный сбой записи докладывается явно (какие цепи
  записались, какие нет) — никогда не тихая половинчатая правка. Если загруженное сейчас цепейо
  на этой сети — его форма перезагружается с диска после применения.

## Net traces

Правит запись `net_traces:` (см. секцию `net_traces:` в [docs/config_ru.md](config_ru.md)) — GUI-лицо
команд `extract-net`/`apply --only=<net>` (план `techdocs/handoff/deepseek/plan_2026_08_21_
net_trace_dock.md`). Добавлен 2026-08-21.

- **Пикер сети** — поисковый комбобокс со списком сетей, у которых на живой плате ЕСТЬ медь,
 собранных из `adapter.get_tracks()` + `adapter.get_vias()` по ВСЕЙ плате — НЕ из выделения
 мышкой (это намеренно закрывает GUI-пробел из находки 5 ревью: старый комбобокс «Origin: Via
 net» в ExtractDock ограничен выделением; сеть теперь можно выбрать по имени, ничего не выделяя).
 Сети только на падах (без меди) исключаются.
- **Блок якоря** — общий `AnchorOriginWidget`, режим anchor с полями sheet/pad/cluster. `net_traces`
 якорится ТОЛЬКО по Role — заполнение Ref отклоняется явным сообщением.
- **Extract** — захватывает живую медь выбранной сети (поиск по всей плате) и пишет её под
 `net_traces:` в корневой файл проекта, затем обновляет Config-дерево. Геометрия (`tracks:`/`vias:`) —
 машинно-записанная и осознанно показывается только на чтение — правьте её повторным
 извлечением, а не вручную (то же цепейо, что у `cells:`).
- **Save** — правит управляемые поля (net/anchor/retired/skip) уже сохранённой записи и
 СОХРАНЯЕТ её машинно-записанную геометрию (Save не должен молча стирать `tracks:`/`vias:`).
- **Redraw** — `apply --only=<net>` для загруженной записи (тот же механизм `ApplyPipeline`, что у
 Redraw в RuleDock), так что сдвинутый якорь переставляет захваченную медь живьём.
- Клик по листу `net_traces:` в Config-дереве загружает эту запись в форму.

## Cells

Правит запись `cells:` (см. [docs/config_ru.md](config_ru.md) про `Cell`) — Components/Vias/Tracks
(локальные смещения `along`/`across` от собственного `(0,0)` ячейки) плюс, рекурсивно, вложенные
`clone_placements:`, ссылающиеся на другие ячейки/роли. Добавлено 2026-08-06 после того, как Denis
поймал живой баг из-за ЕДИНСТВЕННОГО существовавшего способа завести ячейку — пункт **Add cell...**
в дереве конфига писал сырой стаб `{"components": []}` прямо в YAML без какой-либо формы за ним
("создавать экстрактор под один компонент, прости, тупняк" — единственным способом добавить хотя бы
один слот компонента руками был полный цикл выделения на плате и экстракции).

Четыре таба, та же схема «таблица + строка-редактор снизу», что и у Spoke-редактора в Rules, по
одной паре на вид сущности (Components/Vias/Tracks/Nested cells), а не одно дерево на все четыре —
ни у одной пары нет общего набора колонок, так что объединённое дерево всё равно потребовало бы
формы снизу, переключающей вид при выборе, ничего не выигрывая у отдельных табов. (Denis изначально
предлагал дерево, раз вложенные ячейки могут рекурсировать — этим деревом стала собственная
категория Cells в дереве конфига: композитная ячейка теперь показывает свои вложенные
`clone_placements:` дочерними узлами для read-only навигации, а не внутренний редактор этого дока.)

- **Name**/**Layer** — собственное имя ячейки и абсолютный слой (`F.Cu`/`B.Cu`).
- **Anchor** — **(none)** / **XY** / **Role** (`+Pad`, опционально) — **чисто для отображения**, см.
  `Cell.anchor_xy`/`anchor_role`/`anchor_pad` в [docs/config_ru.md](config_ru.md): отмечает, какая
  точка уже И ЕСТЬ локальный `(0,0)` ячейки по построению, ни на что в резолве не влияет. **Role** —
  searchable-комбо, источник — список Components ЭТОЙ ЖЕ ячейки (не живая плата) — обязано называть
  один из них.
- **Components** — Role (searchable, автодополнение с живой платы по полю `Role`, тот же источник,
  что у anchor-role комбо в Chain), Offset along/across, Angle, Layer (inherit/`F.Cu`/`B.Cu`), Net
  template (только для матчинга ролей по сетям у `clone_placements:`).
- **Vias**/**Tracks** — собственные (spoke-level) via/треки ячейки, те же поля, что у
  `TemplateVia`/`TemplateTrack` в [docs/config_ru.md](config_ru.md).
- **Nested cells** — одна запись на `CellPlacement`: Name, **Cell** (searchable, все ключи `cells:`,
  достижимые от root проекта, тот же источник, что у spoke-cell комбо в Chain) **или** **Role**, X/Y,
  Rotation, Mirror, Layer.
- **Сознательные ограничения объёма** (сделано за один присест, не потому что не важно): свои via у
  компонента (`TemplateComponentSlot.vias`) здесь не редактируются — только собственные (cell-level)
  Vias ячейки; уже существующий список via у компонента переживает сохранение нетронутым, если сама
  строка не редактировалась. У Nested cells доступны только базовые поля —
  `nets:`/`params:`/`net_overrides:`/`refs:` сохраняются как есть, если уже были, но не редактируются
  из этой формы.
- Нет Redraw/Resolve — в отличие от Chain/Point/Placer, у Cell нет собственного якоря на живой плате;
  физическую позицию она получает только в контексте плейсмента/spoke, который на неё ссылается.
- **Save** — пишет в секцию `cells:` корневого файла проекта (dict по имени, та же форма, что у Points).

Пункт **Add cell...** в дереве конфига теперь открывает эту форму пустой (`new_cell()`) вместо
записи стаба — та же схема, что у любого другого действия Add. Редактирование СУЩЕСТВУЮЩЕЙ ячейки —
отдельное действие, правый клик **Edit cell...**, сознательно не тот же клик, что обычный левый клик
по листу Cell (который сохраняет исходный смысл — «выбрать эту ячейку как содержимое плейсмента»,
поле Cell у Placer), чтобы открытие формы плейсмента и открытие редактора ячейки никогда не
конфликтовали за один клик.

**Refresh geometry from selection** (2026-09-03) — кнопка на странице Cell И правый клик
**Update from selection...** по листу Cell в категории Cells дерева конфига (один клик из дерева —
не нужно сначала руками открывать док и искать кнопку). Перечитывает геометрию УЖЕ сохранённого
шаблона (смещения/углы Components, смещения Vias, start/end/width Tracks) из ТЕКУЩЕГО выделения на
плате и записывает её обратно в шаблон — способ «затянуть» изменение геометрии, сделанное руками
в одном физическом инстансе, обратно в общий шаблон, чтобы Redraw применил его ко всем инстансам.
Сначала выделите на плате весь кластер, затем запустите.

Меняются ТОЛЬКО геометрические числа. `role`, `net_template`/`net_template_pad`/
`net_template_same_as_role`, `net_from_role`/`net_from_role_pad`, `params`, `layer` и любые прочие
смысловые ключи копируются как есть — это сознательно НЕ повторная экстракция и она никогда не
угадывает сеть. Точка отсчёта — единственный zero-offset (локальный `(0,0)`) компонент шаблона,
резолвится живо из выделения. Via/треки матчатся по резолвленной сети (`net_from_role` — через
реальный пад роли, обычный литерал — как есть); параметризованный литерал (`{placeholder}`,
записанный при экстракции) матчится ПО ФОРМЕ, а не угадыванием значения параметра; `net: null`
via/трек (конвенция rule-net) матчится чисто по позиции против меди, оставшейся после именованных
сетей. Недостающая/лишняя роль компонента, несовпадение количества на сеть или медь, не описанная
шаблоном, — фатал: все проблемы показываются сразу, ничего не меняется, Apply не открывается.

Чистый матч открывает **preview-диалог** (старое/новое/Δ по записям, табы по видам) — **Apply**
мутирует загруженный шаблон в памяти и автостейджит его ровно как ручной Update строки; на диск
ничего не пишется до явного **Save** проекта.

**Import vias/tracks from selection** (2026-09-03) — аддитивное дополнение Refresh: кнопка рядом с
ним на странице Cell И правый клик **Import from selection...** по листу Cell в категории Cells
дерева конфига. Дополняет СУЩЕСТВУЮЩИЙ шаблон НОВЫМИ via/track-записями для живой меди, которую
текущие записи шаблона не описывают — способ добавить via/треки, которых не было при исходной
экстракции (например, ещё не разведены на тот момент — случай `fpga_oscill`), не трогая то, что уже
есть. Сначала выделите на плате весь кластер, затем запустите.

Где Refresh считает «медь, не описанную шаблоном» фаталом и отказывается, Import превращает тот же
leftover в НОВЫЕ записи. Поэтому он чисто АДДИТИВЕН: никогда не меняет и не удаляет существующую
запись и не может ДОБАВИТЬ компоненты. Тот же симметричный матч ролей и те же проверки
количества/имени сети остаются фаталом в обоих — не тот/неполный кластер отклоняется точно так же,
как в Refresh. Сеть новой записи классифицируется собственной эвристикой экстрактора (сеть на паде
выбранной роли -> `net_from_role`(+pad); rule-net вроде GND -> `net: null`; всё прочее -> литерал), а
геометрия — относительно той же zero-offset точки отсчёта.

Чистый план открывает **preview-диалог** со списком НОВЫХ записей (Kind / Position / Net) — **Apply**
дописывает их в загруженный шаблон в памяти и автостейджит ровно как ручной Add строки; на диск
ничего не пишется до явного **Save** проекта.

## Log

Read-only, копируемая, с поиском панель, питается от `logging.Handler`, подвешенного на **root**
логгер — сюда попадает вообще любой `logger.info`/`warning` из бэкенда, не только то, что пишет
сам GUI. **Verbose** переключает уровень именно этой панели между INFO и DEBUG (консольное/файловое
логирование, с которым был запущен `kicadstamp_gui.py`, если оно было, не трогается). **Find** /
**Prev** / **Next** ищут по накопленному тексту; **Clear** очищает. **Auto-scroll** (включён по
умолчанию, 2026-08-15) пока включён принудительно докручивает панель вниз после каждой новой
строки — собственный `QPlainTextEdit` в Qt докручивает только если вид уже был в самом низу до
добавления строки, так что прокрутка вверх для чтения истории раньше выглядела как «лог вообще
не прокручивается» во время живой ошибки. Сними галочку — вернётся обычное Qt-поведение (панель
перестанет выдёргивать вид вниз, пока читаешь историю).

С 2026-08-15 `logging.Handler` панели цепляется к живому `QueueListener`, запущенному
`setup_logging()` (очередное логирование, см. `techdocs/handoff/plan_2026_08_15_queue_based_logging.md`),
если он есть — тогда его `emit()` выполняется на единственном потоке listener'а и не может
заблокировать поток, который сделал лог-вызов; без listener'а хендлер цепляется напрямую к корневому
логгеру, как раньше.

Эта панель — чисто в памяти (с потолком по строкам, пропадает при убийстве/крахе процесса). Если у
открытого сейчас root-конфига задано `log_file:` (см. [docs/config_ru.md](config_ru.md)), GUI
теперь ТАКЖЕ пишет туда всё (уровень DEBUG, независимо от Verbose) — та же конвенция, что уже
использовал `kicadstamp_cli.py apply`, раньше только для CLI (найдено живьём 2026-08-06: `log_file:`
уже стоял в root.sexp проекта, но GUI его молча игнорировал). Переподключается заново при каждой
смене root-файла (Open/New/Recent), так что всегда указывает на ТЕКУЩИЙ открытый проект.

С 2026-08-15 этот `log_file:`-хендлер root-конфига цепляется тем же очередь-ориентированным
способом, что и собственный хендлер панели выше — к живому `QueueListener`, если тот запущен, так
что его запись тоже выполняется на единственном потоке listener'а и не может заблокировать GUI-поток
на handler-lock; без listener'а он цепляется напрямую к корневому логгеру, как раньше.

## Значок в трее

Галочка **Tray icon** в статус-баре создаёт значок в системном трее с настоящей иконкой
приложения (`images/kicadstamp.ico`, встроена base64 в `gui/app_icon.py` — та же иконка, что у
окна/панели задач Windows, без зависимости от файла в рантайме) с меню: **Show/Hide**,
**Open fieldstool**,
**Quit**. Пока галочка стоит, закрытие окна крестиком сворачивает его в трей вместо выхода —
достать обратно можно оттуда (клик/двойной клик по значку, либо пункт меню Show/Hide). Без
галочки закрытие ведёт себя ровно как без трея вообще — настоящий выход. Пункт меню **Quit**
всегда делает настоящий выход, независимо от галочки.

Guard от повторного запуска (`gui/single_instance.py`, на `QLocalServer`/`QLocalSocket`) следит,
чтобы повторный запуск `kicadstamp_gui.py`, пока один экземпляр уже работает, не открывал второе
окно — вместо этого поднимает уже существующее и сразу завершается. Этот guard работает всегда,
независимо от галочки Tray icon.

Состояние галочки сохраняется между запусками (`tray_enabled` в `gui_state.json`) — если её
включили в прошлой сессии, следующий запуск стартует уже с включённой галочкой, и крестик на
заголовке свернёт окно в трей с первого же закрытия, без какого-либо напоминания на экране, что
так и будет. На Windows свежепоявившийся значок в трее часто сразу уходит в скрытые
(стрелка "^" рядом с часами), а не в видимый ряд — «окно пропало, и значка нигде не видно» **не**
означает, что процесс умер; сначала проверь стрелку "^". Если значка всё равно не найти — повторный
запуск `kicadstamp_gui.py` (тот самый guard выше) поднимет уже существующее спрятанное окно, не
запуская второй процесс — не обязательно искать его через Диспетчер задач.

## Открыть fieldstool

Кнопка **Open fieldstool** в статус-баре (и одноимённый пункт меню трея) разворачивает основное
окно, если оно было свёрнуто в трей, и выводит вперёд [таб fieldstool](#таб-fieldstool) — полезно,
если активен другой правый таб, либо эта дока была закрыта по отдельности.

## Что запоминается между запусками

Обычный JSON в `gui/gui_state.json` (в `.gitignore`, человекочитаемый, сознательно не бинарный
blob `QSettings`/`saveGeometry()` из Qt): позиция/размер окна, Always on top, Tray icon,
группировка дерева компонентов и переключатель живая/«не применённые», корневая директория и
последний клик в доке Files, все три назначения ролей файлов (Cells/Extractor/Placer). У таба
fieldstool своё отдельное состояние (`gui/fieldstool_gui_state.json`).

## Тесты

`tests/gui/` — офлайн (`QT_QPA_PLATFORM=offscreen`, выставляется автоматически), живой KiCad не
нужен, часть обычного прогона `pytest`. Логика, реально двигающая плату (Redraw в Placer),
тестируется с замоканными `ApplyPipeline`/`PlacementPlanner` — проверяется, что дока цепейьно
собирает конфиг и вызывает пайплайн, а не что она реально что-то передвинула. Фикстуры — в
`tests/gui/conftest.py`: `qapp`, `main_window` (голая заглушка, для тестов на уровне отдельных
док), `real_main_window` (настоящий `MainWindow`, нужен для тестов трея/закрытия/встраивания
fieldstool), `isolated_settings`, `log_dock`.
