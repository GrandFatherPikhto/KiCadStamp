# Дверь к плате — как коду GUI можно трогать плату KiCad

**English version:** [board_door.md](board_door.md)

GUI говорит с KiCad по ОДНОМУ IPC-сокету, а UI-поток Qt-приложения блокировать нельзя. **Дверь к плате** —
единственный путь кода GUI к плате и правила пользования им. Им следует каждая фича, которая читает или пишет
плату, — назвало это её задание или нет.

## 1. Что такое дверь

- **`connection.board`** — свойство `BoardConnection` (`gui/connection.py`). ЕДИНСТВЕННЫЙ способ получить в
  GUI плату (и её `adapter`). Не кэшировать хендл в доке и не передавать `board` / `adapter` по цепочке в
  обход геттера.
- **Сторож живёт в этом геттере.** Чтение на UI-потоке без *знака* (§3) — нарушение.
- **Два режима отказа**, выбираются там, где сторож вооружается (`set_ui_thread_predicate(…, refusal=…)`):
  - `raise` — тесты и диагностические стенды: чтение бросает `UiThreadBoardReadRefused`;
  - `log` — боевой GUI (`kicadstamp/gui_main.py`): одна красная строка ERROR в Лог на место за сессию, чтение
    проходит. **`raise` в бою запрещён**: исключение внутри Qt-слота роняет PyQt6 (измерено, `EXIT=134`).
    Поэтому в бою сторож не *останавливает*, а свидетельствует; порядок средств (§2) держится на людях и на
    переписи (§5).

## 2. На UI-потоке — порядок средств

Брать первое, что отвечает на вопрос:

1. **Присутствие** — спросить соединение: `connection.is_connected`, а не `connection.board is not None`.
2. **Данные** — ответить из `connection.snapshot`, синхронного кэша, который строит поток опроса. Пустой снимок —
   не снимок: `if snapshot:`, никогда `is not None` (до первого опроса там `[]`). Опознание — из снимка; вопрос
   «где оно СЕЙЧАС» — к живому адаптеру.
3. **Работа** — в воркер: `start_long_op(connection, widgets, fn, on_success, on_error, *args)`
   (`gui/worker.py`). Функция воркера берёт плату сама, на потоке воркера.
4. **Только потом** — подписанное чтение на UI-потоке, с замером рядом:

   ```python
   with ui_thread_board_read(reason="передать адаптер воркеру; замер 0.2 мс"):
       board = connection.board
   ```
   `reason` обязателен и объясняет, ПОЧЕМУ чтение осталось на UI-потоке, а не что оно делает.

## 3. У сокета один владелец

- Всё по общему сокету — через `start_long_op`. `LongOpController` ставит `connection.long_op_active` до старта
  воркера и снимает после; тики опроса, пока флаг стоит, пропускаются.
- `socket_busy(connection)` (`gui/worker.py`) — ЕДИНСТВЕННОЕ определение «занято». Прямое обращение сначала
  спрашивает его и отказывается или откладывается (`defer_while_socket_busy`, одна попытка, очереди нет) — не
  молча. Симптом нарушения: *«Error receiving reply from KiCad: Operation canceled»*.
- Операция, строящая СВОЙ адаптер (конвейер, перерисовка, CLI — `create_board_adapter`), закрывает его на обоих
  путях — успехе и исключении (`finally`). Измерено: 23 незакрытых сокета на клик давали шесть секунд зависания.
- Таймауты воркеров — из `worker_timeout_ms(connection)`, не константой.
- К плате — только методами адаптера: новый вид чтения — новый метод на шве `IBoardAdapter`
  (`kicadstamp/kicad/interfaces.py`) и реализация, никогда `adapter._board`.

## 4. Неудавшееся чтение платы — не ответ

Чтение, которое НЕ УДАЛОСЬ (сокет занят, KiCad думает, личность платы неизвестна), нельзя превращать в «нет»,
меняющее состояние. Пример: фича, чьё состояние зависит от файла по пути платы, при непрочитанном пути
оставляет состояние как есть — прочесть «неизвестная плата» как «файла нет» значит молча снять запрет или
потерять журнал.

## 5. Сторожа

| сторож | ловит |
|---|---|
| `tests/repo/test_board_access_door.py` | обращение к `adapter._board` (в том числе через `getattr(…, "_board")`) |
| `tests/repo/test_board_door_guard.py` | сам страж геттера: предикат, знак, оба режима, одна строка на место |
| `tools/door_lint.py` + `tests/repo/test_door_lint.py` | статическую перепись ниже |

**Статическая перепись — `tools/door_lint.py`.** Читает весь `gui/` и раскладывает каждое чтение `.board`:

- `worker` — внутри функции, отданной воркеру (`fn` у `start_long_op` / `PollWorkerHandle.submit` /
  `<controller>.start`, переданные туда лямбда или `partial`, или помощник, которого зовут ТОЛЬКО такие функции);
- `signed` — внутри `with ui_thread_board_read(...)`;
- `suspect` — всё остальное: чтение на UI-потоке или помощник, которого зовут оба потока.

```sh
.venv/bin/python tools/door_lint.py                   # подозрительные + проверка храповика
.venv/bin/python tools/door_lint.py --all             # все чтения с корзинами
.venv/bin/python tools/door_lint.py --update-baseline # опустить храповик после починки
```

Храповик (`tools/door_lint_baseline.py`) держит нынешнее число подозрительных по файлам: файлу расти нельзя,
новому файлу — ни одного. Это перепись, а не доказательство: статически не видно, какой поток на деле зовёт
помощника, — поэтому починка опускает базу в том же коммите.

**Сторож новой фичи пишется на НАСТОЯЩЕМ `BoardConnection`** с предикатом в режиме `raise` (фикстура
`ui_thread` в `tests/repo/test_board_door_guard.py`): прогнать UI-пути фичи и ждать ни одного
`UiThreadBoardReadRefused`. Сторож на подделке без двери ничего не доказывает.

## 6. Вооружённый GUI в режиме `raise` руками не запускать

Исключение внутри Qt-слота убивает PyQt6 (SIGABRT, измерено дважды). Живые сессии — в режиме `log`; `raise` —
для тестов и offscreen-стендов.
