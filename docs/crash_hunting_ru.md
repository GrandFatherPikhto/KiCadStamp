# Охота за крашами KiCad (issue #24966 / #24970)

## Назначение

Этот документ описывает набор инструментов, которыми в KiCadStamp ловят и локализуют два разных,
подтверждённых падения KiCad 10 (Windows и Linux/Flatpak), и порядок их совместного использования.
Один из двух (#24970) на 2026-08-03 уже пофикшен в апстриме — см. его собственный раздел ниже; сам
набор инструментов остаётся актуален для #24966 и для будущей охоты.
Инструменты живут в двух местах: `kicadstamp/diagnostics/` (детальная пошаговая диагностика через `python -m`)
и `tools/` (операционные скрипты — чистка состояния и статистика по сериям запусков). В конце документа —
как снять и символизировать реальный core dump на любой ОС, если один из инструментов воспроизвёл краш.

Это не абстрактный риск «на будущее» — оба бага реально ловились на боевой плате `3CH-AWG-TIA`, см.
`techdocs/issues/` (внутренний, не в git, архив полных описаний и дампов).

## Два разных бага — не путать

### #24966 — краш IPC API на первой записи в сессии

Null-разыменование в `API_HANDLER_EDITOR::checkForBusy()` (`m_frame == nullptr`), достижимое из нескольких
IPC-точек входа, мутирующих редактор. Симптом со стороны KiCadStamp — обрыв соединения (`ConnectionError`),
а не вежливый `ApiError`.

**Точный триггер (уточнено 2026-07-26):** не любая мутирующая операция, а именно **первый
`begin_commit()`/`push_commit()`-транзакция сессии**. Интерактивные GUI-действия вроде флипа
(`run_action("pcbnew.InteractiveEdit.flip")`) идут отдельным API-путём мимо commit — они не «прогревают»
уязвимое состояние, поэтому серия флипов перед первой реальной транзакцией не спасает.

**Эмпирически подтверждённое условие (прямое наблюдение, воспроизведено многократно):** падение происходит,
только если в сессии открыт **Schematic Editor**. Если открыт только PCB Editor — тот же сценарий
(clean start → одна no-op транзакция) проходит без падений. Это совпадает с условием из оригинального
GitLab-отчёта.

**Практическое следствие (прямое наблюдение):** уязвимое окно — именно первая запись сессии, а не «открытый
Schematic Editor» как постоянное условие. Если первый прогон `apply` сделать при открытом только PCB Editor
(так что первая транзакция `begin_commit()`/`push_commit()` сессии проходит чисто), то открытие Schematic
Editor *после* этого обычно безопасно — KiCad, как правило, не падает. Отсюда практичный порядок работы:
первый прогон расстановки по IPC — только с PCB Editor, а Schematic Editor открывать уже потом, на
оставшуюся часть сессии.

Статус: воспроизведено на KiCad 10.0.4 и 10.0.5, Windows и Linux (Flatpak). Находка про «10.0.5 тоже
падает» и про точный триггер (`begin_commit`, а не любая запись) — в бэклоге на дозаявку в тикет; пока
собираем данные, в GitLab не постим (см. `techdocs/status/`).

**Измеренная точка данных (2026-07-27, нативный Windows, KiCad 10.0, `repeat_first_write_crash.py` после
портирования на Windows + фикса `AS_BUSY` выше):** 10 прогонов с открытыми и Schematic Editor, и PCB Editor
— 1/10 упало (10%), остальные `ok`. Отдельный прогон с открытым только PCB Editor — 10/10 `ok`, 0% — чистое
подтверждение условия про Schematic Editor выше, на этот раз на нативном Windows, а не Linux/Flatpak.

### #24970 — краш в `LIB_BUFFER::GetDerivedSymbolNames` — **ПОФИКШЕН**

Отдельный null-deref, не связанный с IPC-путём: срабатывает в корутине `SELECTION_TOOL` при
переоценке условного пункта контекстного меню (`SYMBOL_EDITOR_CONTROL`) во время **интерактивной** массовой
правки пользовательских полей символов (`Role`) на множестве символов сразу. Изначально был по ошибке
приложен к треду #24966 — это два разных `_eeschema.dll`-падения по разным адресам, разнесены на отдельные
тикеты. Подробности и полная транскрипция страницы — `techdocs/issues/issue_24970_description.md`.

**Статус (2026-08-03): пофикшен в апстриме.** Закрыт `Done`/`fix-committed` Сетом Хиллбрандом
(Seth Hillbrand), коммит `dbb096e4`, milestone 10.0.6, помечен `needs-cherry-pick` (значит попадёт
и в какой-то стабильный бэкпорт, не только в релиз 10.0.6). Этот краш срабатывал только внутри
собственного Symbol Editor KiCad при ручной интерактивной массовой правке — никогда не был вызван
нашими собственными IPC-вызовами, так что менять код/обходы здесь не нужно: как только в ходу
окажется сборка KiCad с этим фиксом, именно этот класс крашей просто исчезнет.

## Набор инструментов

### 1. `kicadstamp/diagnostics/diagnose_first_write_crash.py` — пошаговая лесенка (один прогон)

Диагностирует **где именно** в цепочке read→write умирает процесс: connect → ping → version →
open_documents → get_board → чтение футпринтов → повторное чтение → **no-op транзакция**
(`begin_commit()` → `update_items([fp])` → `push_commit()`, ровно боевой путь `adapter.commit_with_retry()`).
Различает три гипотезы (H1 — гонка инициализации, H2 — зомби-инстанс прошлой сессии, H3 — падение уже на
чтении).

Полное описание, параметры (`--until`, `--delay`, `--repeat`, `--log`, `--timeout-ms`), вывод и зависимости —
отдельным документом в [docs/diagnose_first_write_crash_ru.md](diagnose_first_write_crash_ru.md), здесь не
дублируется.

```bash
python -m kicadstamp.diagnostics.diagnose_first_write_crash            # полная лесенка (может уронить KiCad)
python -m kicadstamp.diagnostics.diagnose_first_write_crash --until 8   # только чтения, безопасно
```

### 2. `tools/clean_kicad_crash_state.py` — чистка хвостов рухнувшей сессии

После segfault Flatpak-версия KiCad не всегда убирает за собой IPC-сокет/лок и project-lock-файлы — это
мешает следующему запуску начать с чистого листа (следующая попытка ловит "занято" вместо честного
воспроизведения). Скрипт чистит:

1. Протухший IPC-сокет/лок Flatpak (`~/.var/app/org.kicad.KiCad/cache/tmp/kicad/{api.sock,api.lock}`).
2. Протухшие записи в `cache/tmp/org.kicad.kicad/instances/`.
3. Project lock-файлы (`*.lck`) в указанной директории плат (по умолчанию `test_boards/`).

**Безопасность:** проверяет `pgrep -x kicad` перед стартом и **отказывается работать, если KiCad сейчас
запущен** — иначе можно выдернуть сокет из-под живой сессии. (Важно: `-x`, точное имя процесса, не `-f` —
полнострочный поиск ловит сам этот скрипт, т.к. в имени файла тоже есть «kicad».)

```bash
python tools/clean_kicad_crash_state.py                          # почистить
python tools/clean_kicad_crash_state.py --dry-run                # только показать, что будет удалено
python tools/clean_kicad_crash_state.py --boards-dir path/to/boards
```

**Зависимости:** только стандартная библиотека + `pgrep` в `PATH` (Linux). Скрипт Linux/Flatpak-специфичный.

### 3. `tools/repeat_first_write_crash.py` — серия прогонов и доля падений

Баг #24966 интермиттентный (сам оригинальный отчёт: «на свежеперезагруженной Windows падает надёжно, на
прогретой системе становится случайным») — единичный прогон (упало/не упало) статистически ничего не
доказывает. Этот скрипт гоняет N одинаковых итераций подряд и считает процент падений — превращает
анекдот в измеримую величину.

**Кросс-платформенный (Windows/Linux)** — до 2026-07-27 был только Linux/Flatpak; `kill_kicad()`/
`launch_kicad()` теперь разветвляются по `os.name`, та же договорённость, что и у `list_kicad_pids()` в
`diagnose_first_write_crash.py`.

Цикл на одну итерацию:

1. Убить KiCad, если запущен — `taskkill /IM kicad.exe /F` на Windows, `pkill -x kicad` на Linux — затем
   **дождаться, пока он реально исчезнет** (`wait_until_dead()`, tasklist на Windows / psutil на остальных,
   до ~25с). С 2026-08-22 форсированному kill больше не верят вслепую: зависший `kicad.exe` на этой машине
   наблюдали «доживающим» десятки секунд даже после `taskkill /F`, а запуск следующей попытки поверх
   выжившего процесса молча портил сообщаемую долю падений. Та же проверка выполняется и один раз в начале
   сессии — оставшийся зомби, который не хочет умирать, прерывает прогон, а не засоряет его.
2. Почистить хвосты — вызывает `tools/clean_kicad_crash_state.py` как подпроцесс. **Сам он пока
   по-прежнему только Linux/Flatpak** (см. ниже) — на Windows это безопасный no-op (печатает
   предупреждение, не падает), просто реально ничего не чистит.
3. Запустить KiCad с указанным проектом — на Linux `flatpak run org.kicad.KiCad <project>` (по app id, путь
   не нужен); на Windows такого запуска по id нет, поэтому запускается `<kicad_exe> <project>` с явным,
   обязательным путём из конфига/`--kicad-exe` — сознательно без автоопределения по установленным версиям
   (та же договорённость «явно лучше, чем угадывать», что и в остальном проекте).
4. Дождаться готовности IPC — **не только `ping()`**, а ещё и успешный `get_board()` (иначе гонка:
   `ping()` отвечает, как только поднялся базовый API-сервер, задолго до того, как pcbnew реально загрузит
   плату и зарегистрирует свой обработчик — раньше это давало ложные `ApiError: no handler available`,
   принимавшиеся за краш).
5. Одна no-op транзакция (`begin_commit → update_items → push_commit`) — тот же боевой путь, что и в
   ступени 9 `diagnose_first_write_crash.py`. `ApiError` с кодом `AS_BUSY` («KiCad is busy and cannot
   respond...») — это **не** краш #24966, а отдельная гонка готовности: `get_board()` (чтение) в шаге 4 уже
   отвечает раньше, чем pcbnew готов принимать команды **редактирования**, и это окно оказалось заметно шире
   на живом Windows, чем на Linux/Flatpak, где вообще не проявлялось (найдено 2026-07-27, на прогоне,
   показавшем 100% «crash» на Windows при чистых 100% OK на той же плате на Linux). Ретраится с бэкоффом
   прямо здесь, тем же приёмом, что `commit_with_retry` в проде (`kicadstamp/kicad/adapter.py`) — не
   считается падением.
6. Записать исход: `ok` / `crash` (обрыв соединения — вот это настоящий #24966) / `busy` (не отпустило за
   все ретраи — сообщается отдельно, не как падение) / `zombie` (предыдущий `kicad.exe` так и не умер в
   пределах таймаута `wait_until_dead()` — попытка пропускается, новый экземпляр поверх него не запускается;
   сообщается отдельно, не как падение).
7. Убить KiCad, следующая итерация.

**Конфиг:** по умолчанию читает `crash_config.yaml` из корня репозитория — не нужно каждый раз набирать
`--project`/`--kicad-exe` руками. Общие поля (`project`, `boards_dir`, `runs`, `startup_wait`,
`settle_delay`) — на верхнем уровне, одно значение на обе ОС; Windows-специфичный `kicad_exe` — во
вложенном ключе `windows:`, читается только если `os.name == "nt"` — на Linux такого поля вообще нет (запуск
по Flatpak app id, путь не нужен). Проекты KiCad живут в `test_boards/`, который целиком в `.gitignore`
(тестовые платы у каждого свои/локальные), но сам `crash_config.yaml` — обычный трекаемый файл, в нём
только пути-строки, а не сам проект:

```yaml
# crash_config.yaml
project: test_boards/3CH-AWG-TIA/3CH-AWG-TIA.kicad_pro
boards_dir: test_boards
runs: 10
startup_wait: 30.0
settle_delay: 0.0

windows:
  kicad_exe: "C:\\Users\\<вы>\\AppData\\Local\\Programs\\KiCad\\10.0\\bin\\kicad.exe"
```

Любой CLI-флаг переопределяет соответствующее поле конфига.

```bash
python tools/repeat_first_write_crash.py                       # всё из crash_config.yaml
python tools/repeat_first_write_crash.py --runs 20              # конфиг + переопределение runs

# Тест гипотезы H1 (гонка) — пауза перед транзакцией после готовности IPC
python tools/repeat_first_write_crash.py --settle-delay 30

# Свой конфиг (например, для другой тестовой платы)
python tools/repeat_first_write_crash.py --config crash_config_power_board.yaml

# Windows, kicad_exe вне конфига (например, вторая версия KiCad рядом)
python tools/repeat_first_write_crash.py --kicad-exe "C:\Program Files\KiCad\9.0\bin\kicad.exe"
```

**Параметры:**
- `--config` — путь к YAML-конфигу (по умолчанию `crash_config.yaml`).
- `--project` — путь к `.kicad_pro` для запуска (переопределяет `project` из конфига; ошибка, если не задан
  ни там, ни там).
- `--runs` — число итераций (по умолчанию 10 / из конфига).
- `--boards-dir` — прокидывается в `clean_kicad_crash_state.py` (по умолчанию `test_boards` / из конфига).
- `--startup-wait` — таймаут ожидания готовности IPC, секунды (по умолчанию 30 / из конфига).
- `--settle-delay` — пауза после готовности IPC перед транзакцией, секунды (проверка гипотезы H1).
- `--kicad-exe` — путь к `kicad.exe` (переопределяет `kicad_exe` из конфига; **обязателен на Windows**,
  фатал с подсказкой, если не задан; на Linux игнорируется).

**Вывод:** построчно `OK`/`CRASH`/`BUSY`/`ZOMBIE` на каждую попытку, в конце — сводка (число прогонов,
вошедших в долю падений, сколько не поднялось вовремя, сколько так и осталось busy после всех ретраев,
сколько пропущено как зомби, доля падений в процентах — считается только по `ok + crash`, `busy`/тайм-аут/
зомби не размывают и не завышают статистику #24966 посторонним шумом).

**Важно про условие «Schematic Editor открыт»:** открывается ли редактор схем автоматически при запуске
проекта — зависит от того, запомнил ли сам `.kicad_pro`-проект открытые окна с прошлого раза. Если нет —
откройте Schematic Editor руками один раз и сохраните проект (File → Save Project); тогда KiCad будет
переоткрывать его сам на каждом следующем старте цикла. Без этого шага серия прогонов молча тестирует
**другой** сценарий (только PCB Editor), где баг не воспроизводится.

**Зависимости:** на Linux — `flatpak`, `pkill`/`pgrep` в `PATH`; на Windows — ничего, кроме стандартной
библиотеки (`taskkill` идёт с самой Windows) и правильного пути `kicad_exe`. Вызывает
`tools/clean_kicad_crash_state.py` как подпроцесс (путь жёстко зашит относительно корня репозитория —
запускать из корня) — сам этот скрипт пока по-прежнему только Linux/Flatpak (см. выше).

## Рекомендованный порядок работы

1. **Почистить состояние** — `tools/clean_kicad_crash_state.py`, если предыдущая сессия падала.
2. **Один точный прогон** — `diagnose_first_write_crash.py` без `--until 8`, чтобы увидеть, на какой именно
   ступени и с какой гипотезой (H1/H2/H3) падает *в этот раз*.
3. **Серия прогонов** — `repeat_first_write_crash.py --runs N`, чтобы получить долю падений при конкретном
   условии (например, «Schematic Editor открыт» vs «только PCB Editor»), а не единичный анекдот.
4. **Если упало и нужен полный разбор** — снять core dump и получить символизированный бэктрейс, см.
   [следующий раздел](#как-снять-и-разобрать-core-dump-windows--linux).

## Как снять и разобрать core dump (Windows + Linux)

KiCadStamp работает через IPC-API живого KiCad (`kipy`), поэтому падения самого KiCad — не абстрактная
угроза, а то, с чем реально приходится разбираться (см. `techdocs/issues/` — историю обоих багов выше).
Дальше — не общая теория, а то, что реально сработало при живой охоте за краш-дампом на обеих ОС.

### Windows

Инструментарий — [HuntProc](https://github.com/GrandFatherPikhto/HuntProc) поверх ProcDump + WER.

1. **Ловим дамп**: `ProcDump` в режиме first-chance-мониторинга на `kicad.exe`, либо WER сам пишет
   полный дамп при падении (см. `%LOCALAPPDATA%\CrashDumps`, если включён `LocalDumps` в реестре).
   HuntProc автоматизирует именно это — сидит и ждёт, забирает дамп сразу после падения.
2. **Символы** — публичный символьный сервер KiCad:
   `SRV*<локальный кэш>*https://symbols.kicad.org/kicad-stable`.
3. **Разбор** — `cdb`/WinDbg:
   ```
   cdb -z <dump.zip\dump.dmp> -y SRV*C:\symbols*https://symbols.kicad.org/kicad-stable -c "!analyze -v; q"
   ```
   `!analyze -v` даёт вердикт (`FAILURE_BUCKET_ID`), адрес исключения, символизированный стек — этого
   обычно достаточно для репорта, без ручного разбора дизассемблера.

### Linux

Разбор реальной охоты (KiCad 10.0.5, Flatpak `org.kicad.KiCad`, Ubuntu). Три места, где можно
споткнуться — все настоящие, все встретились по пути.

#### 0. Определить, как установлен KiCad

```bash
flatpak list --all | grep -i kicad   # Flatpak?
dpkg -l | grep -i kicad               # или родной apt-пакет?
```
На системе может оказаться сразу оба варианта (Flatpak + старый apt-пакет). Дальнейшие шаги — под
Flatpak; для apt-пакета всё проще (символы через `apt install kicad-dbgsym` или debuginfod, без
плясок с сэндбоксом).

#### 1. Символы

Для Flatpak — отдельное `.Debug`-расширение той же ветки. **Важно**: оно НЕ показывается в обычном
`flatpak remote-ls` (Flatpak по умолчанию скрывает debug-расширения из листинга) — ставить надо по
точному имени, не полагаясь на то, что `remote-ls | grep debug` ничего не нашёл:

```bash
flatpak install <remote> org.kicad.KiCad.Debug//stable   # имя remote — своё, см. `flatpak remotes`
```

```bash
# Проверить, что вообще есть на remote для kicad (включая debug-расширения)
flatpak remote-ls <remote> | grep -i kicad
```

Если расширения нет вообще (или лень ставить ~2 ГБ) — fallback на `debuginfod` (Flathub держит свой
сервер, `gdb` сам подтягивает по build-id, ничего ставить не надо):
```bash
export DEBUGINFOD_URLS="https://debuginfod.flathub.org/"
```

#### 2. Ловля самого core

Первая, бесплатная проверка (работает всегда, без всякой настройки) — ядро само пишет segfault в
журнал, даже если core-файл никуда не попал:
```bash
journalctl -k | grep -i segfault
# ... kernel: kicad[26482]: segfault at 0 ip ... in _eeschema.kiface[...] ...
```
Уже даёт адрес и модуль — полезно как быстрый сигнал "оно и правда падает", но без символов.

Для полного core с бэктрейсом: на Ubuntu краши по умолчанию идут через **apport**
(`cat /proc/sys/kernel/core_pattern` — увидишь `.../apport ...`). С Flatpak-сэндбоксом apport часто
не справляется (namespace текущего процесса отличается от того, что видит обработчик) — в `/var/crash/`
может быть пусто, даже когда `journalctl -k` честно показал сегфолт. Обход — направить `core_pattern`
на простой абсолютный путь (кладётся ядром в файловой системе САМОГО падающего процесса, без пайпа
во внешний обработчик — сэндбокс тут не мешает, если путь у процесса виден, например внутри `$HOME`):

```bash
mkdir -p ~/coredumps
echo "$HOME/coredumps/core.%e.%p.%t" | sudo tee /proc/sys/kernel/core_pattern
```

**Критично**: `ulimit -c unlimited` нужно выставить В ТОМ ЖЕ терминале, из которого запускается
KiCad — если запускать через иконку/gnome-shell, процесс наследует лимиты systemd-сессии, а не твоего
шелла, и `ulimit -c 0` (дефолт на многих системах) тихо запретит запись core вообще:

```bash
ulimit -c unlimited
flatpak run org.kicad.KiCad
```

Дальше — воспроизвести краш как обычно и проверить `ls -la ~/coredumps/`.

#### 3. Анализ

Для Flatpak-приложения gdb надо гонять ВНУТРИ того же сэндбокса — тогда пути к бинарникам/библиотекам
резолвятся сами, руками искать `/var/lib/flatpak/app/...` не нужно:

```bash
flatpak run --command=gdb org.kicad.KiCad -batch -ex "bt full" -ex quit -c ~/coredumps/<файл>
```
Для нативного (apt) пакета — обычный `gdb /usr/bin/kicad <corefile>`.

#### Нужен ли отдельный демон-охотник (аналог HuntProc)?

Нет — ловля самого краша на Linux синхронна и встроена в ядро (`core_pattern` срабатывает в момент
падения сам, никакой службы держать не надо, в отличие от Windows, где WER/ProcDump и есть отдельный
сервис). Единственное, что реально экономит время при частых повторных охотах — маленький вотчер
(`inotifywait` на директорию с core + автозапуск `gdb -batch -ex "bt full"` на новый файл), чтобы не
гонять шаг 3 руками каждый раз. Для разовой/редкой охоты — оверинжиниринг, ручных шагов выше достаточно.
